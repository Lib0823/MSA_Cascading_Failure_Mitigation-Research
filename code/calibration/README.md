# 게이트 ①.5 — S1 미니 캘리브레이션

연구에서 **가장 위험한 주장의 부호 하나**를, K8s 구축(60h)에 착수하기 전에 가장 싸게 확인한다.

> **H4 전반부** — S1(DB 커넥션 고갈) 조건에서 인스턴스를 늘리면 성능이 **나빠진다** (`m_scale-out < 0`).
> 이 부호가 재현되지 않으면 §4-3 의 baseline 비교와 §2-B 비용함수의 유도가 함께 무너진다.

절대 수치는 목표가 아니다. 노트북에서 돌고, K8s·HPA·Prometheus 가 필요 없다.
여기서 만드는 Spring 서비스는 [§4-1](../../docs/proposal.md) 의 단일 이미지 그대로이므로 버려지는 코드가 없다.

---

## 왜 대조군이 필수인가

인스턴스를 2→4 로 늘리면 **호스트 CPU 경합만으로도** 지연이 악화된다. 그 상태에서 실험군만
보면 H4 가 재현된 것처럼 보이지만 실제로는 아무것도 보인 게 아니다 — 이것이 §4-1 이 경고하는
가짜 양성이다.

따라서 순서가 고정되어 있다.

| 단계 | 하는 일 | 실패 시 |
|---|---|---|
| **1. `band`** | **대조군(DB 미제약)** 에서 2→4 가 **개선되는** 부하 수준을 찾는다 | 그런 구간이 없으면 이 머신에서는 **판정 불가**. 실험 데스크톱으로 이월하고 **12h 에서 멈춘다** |
| **2. `compare`** | 그 부하에서 대조군·실험군 × 2·4 를 반복 측정한다 | 대조군이 개선되고 실험군만 악화될 때에만 부호를 DB 에 귀속시킨다 |

1 단계를 건너뛰면 2 단계 결과는 해석할 수 없다.

## 구성

```
code/
  services/app/        단일 이미지 Spring (SERVICE_NAME / WORKLOAD / DOWNSTREAM)
  calibration/
    docker-compose.yml   db 1개 + app1~app4 (프로파일 s2 / s4)
    loadGen.py           표준 라이브러리 폐루프 부하기
    runCalibration.py    조건 기동 · 측정 · 판정
    results/             실행 기록 (JSON)
```

**설계상의 선택 세 가지**

- **`--scale` 대신 app1~app4 를 명시한다.** 호스트 포트가 고정되어 부하기가 인스턴스에
  결정론적으로 균등 분배할 수 있고, 로드밸런서 프로세스가 호스트 CPU 를 먹지 않는다.
- **앱당 CPU 를 고정 상한으로 준다.** 상한이 없으면 2→4 가 실제 연산량 증가로 이어지지 않아
  대조군에서도 개선이 나타나지 않고, 1 단계가 구조적으로 실패한다.
- **두 군은 `max_connections` 하나만 다르다.** DB CPU 상한까지 군마다 다르게 주면 조건별
  호스트 CPU 총량이 달라져 대조군이 대조군 역할을 못 한다.

## 실행

Docker 와 Python 3.11+ 만 있으면 된다 (부하기는 표준 라이브러리만 쓴다).

```bash
cd code/calibration

# 이미지 빌드 (최초 1회, 약 2분)
docker compose -p gate15 --profile s2 build

# 1 단계 — 부하 구간 탐색
python3 runCalibration.py band --workers 32,64,96,128

# 2 단계 — 1 단계가 권한 부하로 귀속 측정
python3 runCalibration.py compare --workers 96 --repeats 3
```

판정은 `results/compare-*.json` 의 `verdict` 에 남는다.

| `verdict` | 의미 | 다음 행동 |
|---|---|---|
| `h4-reproduced` | 대조군은 개선, 실험군만 악화 | 게이트 ② (K8s 구축) 로 진행 |
| `h4-not-reproduced` | 실험군도 악화되지 않음 | **S1 정의를 재설계한다.** K8s 60h 이전에 이 답을 얻은 것이 이 게이트의 성과다 |
| `undecidable` | 대조군이 개선되지 않음 | 1 단계로 돌아간다. 결론을 내지 않는다 |

## 부호가 안 나올 때 움직일 손잡이

순서대로 본다. 전부 환경변수이며 `compare` 재실행만 하면 된다.

| 손잡이 | 방향 | 기전 |
|---|---|---|
| `--treatMaxConnections` | 4 인스턴스 요구(`4 × poolSize`)는 넘고 2 인스턴스 요구는 넘지 않는 값 | 부호를 가장 선명하게 만드는 값. **여기부터 본다** |
| `DB_SLEEP_MILLIS` | ↑ | 커넥션 보유시간이 늘어 인스턴스당 동시 커넥션 요구가 커진다 |
| `HIKARI_MIN_IDLE` | ↑ | 인스턴스가 기동만으로 확보하는 커넥션이 늘어난다 |
| `APP_CPUS` | 호스트 코어 수에 맞춘다 | `4 × APP_CPUS + DB_CPUS` 가 코어 수를 넘으면 대조군이 개선되지 않는다 |

**`HIKARI_MAX_POOL_SIZE` 는 줄이지 않는다.** 앱 측 풀을 조이면 인스턴스 2→4 에서 총 풀 용량이
함께 늘어 대기가 *줄어들고*, H4 가 뒤집힌다 — 이것이 2026-09-24 에 정정한 S1 정의의 핵심이다
([proposal.md §4-6](../../docs/proposal.md)).

`DB_BURN_ROWS` 는 **올리지 않는다.** 실측에서 20,000 행은 요청당 약 50ms 의 DB CPU 를 먹어
DB CPU 를 천장으로 만들었고(2코어 → 약 50 rps), 그 상태에서는 대조군에서조차 증설이 무의미해
부호를 커넥션에 귀속시킬 수 없었다. 기본값 1,000 은 그 실측 이후 잡은 값이다.

## 이 게이트가 확인하지 않는 것

- **S2 (LLM 노드 포화).** `LlmWorkload` 는 세마포어로 *"레플리카를 늘려도 처리량이 안 는다"* 를
  심어 둔 자리표시일 뿐이므로 그 자체로는 `m_scale-out = 0` 의 증거가 되지 않는다.
- **HPA 의 실제 거동.** 여기서는 인스턴스 수를 사람이 바꾼다. 오토스케일러가 스스로
  그 지점에 도달하는지는 게이트 ② 이후의 문제다.
- **조치 효과 `mₐ` 의 절대 크기.** 확인 대상은 부호뿐이다.
