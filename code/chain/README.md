# S1↔S3 증상 동형성 + 전파성 판정 검증

게이트 ② 의 확인 항목 6개 중 **K8s 가 필요 없는 4개**를 노트북에서 미리 처리한다.
동시에, 연구의 **컷 불가 항목**인 H5b 를 가장 싸게 확인한다.

| 게이트 ② 확인 항목 | 여기서 | 비고 |
|---|---|---|
| 서비스별 feature 수집 | ✅ | `/actuator/prometheus` 1Hz |
| 이웃 집계 feature 구성 | ✅ | 4단 사슬로 1-hop·2-hop 이 존재 |
| `[t, t+Δ]` 역라벨링 동작 | ✅ | `relabel.py` |
| **전파성 판정 규칙 (§4-2)** | ✅ | `relabel.py` — 종이 위에만 있던 규칙 |
| 클래스 불균형 실제 비율 | △ | 참고치만 |
| CPU 헤드룸 실측 | ❌ | 대상 머신 필요 |

---

## 왜 이 두 가지를 함께 보는가

연구는 **상충하는 두 가지**를 동시에 주장한다.

- **H5b** — S1 과 S3 는 **표준 지표로 구분되지 않는다.** 구분된다면 *"진단이 원리적으로
  어려운 구간"* 이라는 전제가 깨지고 신뢰도 기반 조치 선택이라는 기여가 약해진다.
  **동형성은 좋은 소식이다.**
- **H7** — 그러나 **어떤 지표를 추가하면 구분된다.** 구분되지 않으면 *"측정했다"* 에서
  멈추고 실무 처방이 나오지 않는다.

둘이 같은 데이터에서 함께 성립해야 [§4-4](../../docs/proposal.md) 의 서술이 실측으로
뒷받침된다. 그래서 한 실험에서 같이 본다.

---

## 구성

```
부하 → gateway → orders → payment → postgres
      (passthrough) (passthrough) (db)
```

의존 깊이 4단. 연쇄의 본질은 노드 개수가 아니라 **전파 경로**이므로 노드 수를 늘리는
대신 깊이로 성립시킨다(§4-1).

장애는 **전부 payment 에** 주입하되 기전을 다르게 한다.

| 시나리오 | 주입 기전 | 상류가 보는 것 |
|---|---|---|
| **S1** | DB 커넥션 예산을 외부에서 점유 → payment 의 풀이 굶는다 | payment 가 느려짐 |
| **S3** | payment 의 필터가 응답을 지연 | payment 가 느려짐 |

**상류에서 보면 같다.** 그것이 H5b 의 전제이고, 구분자를 찾는 것이 H7 이다.

## 설계상 되짚을 지점 넷

**① 주입은 런타임이어야 한다.** §4-2 의 전파성 판정은 *"상류가 **먼저** 열화했는가"*
라는 **순서** 문제다. 기동 시점부터 장애가 켜져 있으면 판정할 onset 이 없다. 그래서
`FaultState` + `POST /fault` 로 에피소드 중간에 건다.

**② S1 도 런타임으로 걸어야 한다.** `max_connections` 는 재기동 없이 못 바꾸므로,
외부에서 세션을 점유해 커넥션 예산을 먹는 방식으로 건다. 이는 게이트 ①.5 에서 확인한
기전 — *"총 커넥션 요구가 `max_connections` 를 넘으면 풀이 굶는다"* — 과 동일하다.
실제 실험에서 그 요구를 만드는 것은 HPA 가 늘린 레플리카들이고, 여기서는 점유 세션이
그 역할을 대신한다.

**③ 분위수를 앱이 추정하게 두면 안 된다.** Micrometer 의 `percentiles` 는 감쇠 윈도우
추정값이라 과거를 30초 가까이 끌고 온다. 전파성 판정의 허용 시간창 `W` 가 30초인데
지표 자체가 그만큼 번지면 onset 순서를 집을 수 없다. 그래서 **누적 히스토그램 버킷**을
내보내고 수집기가 구간 차분으로 참 분위수를 만든다.
> 실측: 감쇠 윈도우에서는 p95 가 1132 → 400ms 로 28초 내내 하강해 기준선이 성립하지
> 않았다. 버킷 차분으로 바꾸니 t+3s 부터 134ms 로 평평해졌다.

**④ 점유 세션은 비-superuser 로 붙인다.** superuser 로 붙이면
`superuser_reserved_connections` 까지 먹어 관측용 psql 이 들어가지 못한다 —
게이트 ①.5 에서 겪은 *"고갈이 관측을 같이 죽이는"* 문제의 재발이다.

## 실행

```bash
cd code/chain
docker build -t cascade-app:0.1.0 ../services/app      # 최초 1회

# 에피소드 3종 (약 9분)
python3 runChain.py --scenarios normal,s1,s3 --warmup 60 --normalSeconds 40 --faultSeconds 60

# H5b·H7 판정
python3 compareSymptoms.py --episodes results/episodes-<stamp>.json

# §4-2 역라벨링 + 전파성 판정
python3 relabel.py --episodes results/episodes-<stamp>.json
```

### 판정 읽는 법

**`compareSymptoms.py`**

| `verdict` | 의미 |
|---|---|
| `h5b-and-h7-supported` | 표준 지표로는 안 갈리고 추가 지표로는 갈린다. §4-4 서술이 실측으로 지지됨 |
| `h5b-only` | 추가 지표로도 구분 안 됨. H7(25h) 의 산출이 *"측정했다"* 에서 멈출 위험 |
| `h5b-violated` | 표준 지표가 이미 가른다. **동형성은 자연히 성립하는 성질이 아니라 주입 강도를 맞춰 설계해야 하는 조건**이다 |

**`relabel.py`** — 가장 직접적인 증거는 **주입 지점(payment)이 positive 에서 제외되는가**
다. 1차 장애의 onset 은 외생적이라 상류 선행 열화가 없고, 규칙상 자동으로 빠져야 한다.
빠지지 않으면 상류 방향이 뒤집혔거나 임계값이 느슨한 것이다.

> **상류의 방향**: 호출 간선은 호출자→피호출자로 저장하지만 전파는 그 반대로 흐른다.
> 따라서 v 의 1-hop 상류는 **v 가 호출하는 쪽**이다 — orders 의 상류는 payment 다.
> 뒤집으면 라벨이 통째로 뒤집힌다([smokeTest.py](../model/smokeTest.py) C7 이 실증).

## 이 실험이 확인하지 않는 것

- **HPA 의 실제 거동.** 인스턴스 수를 바꾸지 않는다. S1 의 주입도 커넥션 점유로 대신한다
- **S2 (LLM 노드 포화).** GPU 가 필요해 실험 데스크톱 확보 전에는 불가
- **Δ·W·임계값의 최종값.** §4-2 가 *"실측으로 조정할 값"* 으로 남긴 것들이며, 여기서
  정하는 것은 **규칙이 작동한다는 사실**이지 운영값이 아니다
