## 0. 변경의 성격

### 0-1. 무엇을 바꾸는가

| 구분 | 내용 | 출처 |
|---|---|---|
| **유지** | GAT(정적), Deep Ensemble(N=5), 신뢰도 3티어 구조, 이질적 조치 4종, 단일 Policy Engine, GRAF·FIRM·AGQ·GraphGRU 4자 비교 구도, Online Boutique 메인 벤치마크, RL·STGNN 미채택 | 🟢 |
| **확장** | 대상 시스템에 LLM 추론 서비스 1개 추가 → 조치 4종의 실행 방식이 노드 타입별로 분기 | 🟢 |
| **수정** | 노드 피처 정의, Actuator 명칭, 비용 함수에 품질 축 추가, 관련연구 3분할 | 🟡 |
| **미채택** | ① LLM 에이전트를 Policy Engine으로 사용 ② LLM 서빙 인프라 전용 프레임워크로 전면 전환 | 🟡 |

### 0-2. 왜 바꾸는가 (방어 논리) 🔴

> 기존 3축(위상 인지 예측 / 이질적 조치 / 신뢰도 구간별 대응)은 "GRAF + FIRM의 조합"으로 읽힐 여지가 있었으나, LLM 추론 서비스가 포함된 MSA에서는 세 축 각각이 **선택이 아니라 필연**이 된다.

- **위상 인지**: LLM 노드의 지연은 RPS가 아니라 토큰 길이·KV 캐시 점유·큐 깊이에 좌우되어, 노드 단위 시계열 모델로는 상류 전파를 포착할 수 없음
- **이질적 조치**: 추론 자원은 기동 리드타임이 길고 비용이 커서 자원 할당 단일 축으로 대응 불가 → 품질을 낮춰 지연을 지키는 조치가 필수
- **신뢰도 구간**: 리드타임이 긴 조치는 확신이 설 때까지 기다리면 이미 늦음 → 조치별로 다른 신뢰도 임계값이 구조적으로 요구됨

### 0-3. 미채택한 두 방향 🟡

**(A) LLM 에이전트를 Policy Engine으로 사용**
- 비결정적 출력 → 반복 실험 기반 정량 비교와 재현성 확보 불가
- "GNN과 LLM을 왜 둘 다 쓰는가"에 대한 설계 정당화 곤란
- 프롬프트 설계·평가 체계 추가로 7~10개월 일정 초과

**(B) LLM 서빙 인프라 전용 프레임워크로 전면 전환**
- 연구 분야 자체가 이동한다. 전 노드가 LLM인 시스템은 LLM serving systems 영역(vLLM·SGLang 계열)이며, 본류는 스케줄러 설계·KV 캐시 관리이지 서비스 그래프 위상 예측이 아니다. GNN 접근의 정당성을 처음부터 재방어해야 함
- 기존 확정 사항 대부분(벤치마크, 비교 논문 4편, 커넥션풀 논거, GAT 근거)이 무효화됨
- 심사위원이 LLM 서빙 전문가 기준으로 평가하게 되어 KCI 목표 대비 요구 수준 과도

채택 방향은 둘의 중간 — **혼합 그래프(일반 서비스 + LLM 노드 1개)를 대상으로 하되, 프레임워크 골격과 기여 구조는 유지.**

### 0-4. 무게중심 유지 원칙 🔴

- 주장은 어디까지나 **"GNN 기반 위상 인지 선제 대응"**이며, LLM 노드는 그 필요성을 증폭시키는 **대상**이다
- "LLM 시대의 MSA"를 전면에 내세우지 않는다
- 라우팅·캐스케이딩 자체는 **기여가 아니라 Actuator 구현체**로 위치시킨다

**제목·초록에서 LLM을 어떻게 다룰 것인가** 🔴 **[미결정 — 결정 필요]**

원칙만으로는 답이 안 나오는 실무적 결정이다. 세 가지 선택지가 있고 각각 대가가 다르다.

| 안 | 예시 | 장점 | 단점 |
|---|---|---|---|
| (a) 제목·초록 모두 미언급 | "GNN 기반 마이크로서비스 선제적 장애 예측 및 이기종 완화 프레임워크" | 무게중심 완전 유지 | "왜 LLM 실험을 했나"가 본문에서 뜬금없이 등장. 심사위원이 실험 파트에서 혼란 |
| (b) 초록에만 언급 | 제목은 기존 유지, 초록에서 "LLM 추론 서비스를 포함한 이기종 워크로드 환경에서 검증" | 균형. **권장** | — |
| (c) 제목에도 포함 | "...LLM 서비스를 포함한 마이크로서비스를 위한..." | 트렌디함, 검색 노출 | 심사위원이 LLM 서빙 전문가 기준으로 평가 시작. R4 리스크 현실화 |

권장 🔴: **(b)**. 제목은 기존 프레임을 지키되, 초록에서 "이기종 워크로드"라는 중립적 표현으로 대상 확장을 명시한다. 본문 §1에서 LLM 노드의 세 가정 붕괴를 근거로 제시하면 실험 파트가 자연스럽게 연결된다.

## 1. 문서 A(연구계획 작업본) 수정분

### 1-1. §1 연구 배경 — 추가 문단 🔴

> **다섯 번째 한계: 이질적 워크로드 노드의 등장**
>
> 최근 마이크로서비스 아키텍처에는 LLM 추론 서비스가 일반 서비스와 동일한 그래프 위에 배치되는 사례가 증가하고 있다. LLM 추론 노드는 기존 오토스케일링이 전제하는 세 가지 가정을 위반한다.
>
> 1. **부하 지표 가정의 붕괴** — 기존 HPA는 CPU 사용률 또는 RPS를 부하 대리지표로 사용하나, LLM 추론 노드의 지연은 요청 수가 아니라 입력·출력 토큰 길이, KV 캐시 점유율, 대기 큐 깊이에 지배된다. 동일 RPS에서도 지연이 수 배 달라질 수 있다.
> 2. **스케일아웃 가정의 붕괴** — 추론 인스턴스 기동은 일반 컨테이너 대비 리드타임이 길고 단위 비용이 크다. GRAF는 일반 마이크로서비스 인스턴스 생성에도 평균 5.5초가 소요되며 오토스케일러 결정 주기와 맞물려 cascading effect가 발생함을 관측했는데, 추론 자원에서는 이 갭이 더 벌어진다.
> 3. **가역성 가정의 붕괴** — 일반 서비스는 조치 결과가 성공/실패의 이분법이지만, LLM 노드는 "낮은 품질로 성공"이라는 제3의 상태를 가진다. 기존 비용 모델(자원 비용·가용성 손실)로 표현되지 않는 축이다.
>
> 나아가 LLM 노드는 단일 요청이 하위 서비스에 대한 다중 툴콜로 증폭되는 특성이 있어, 상류 노드의 부하 증가가 하위 상태성 자원 소진으로 이어지는 새로운 연쇄 경로를 만든다.

> ⚠️ 위 3가지 중 2번의 "리드타임" 논거는 **실측이 필요하다.** 로컬 CPU 추론 환경에서는 GPU 기동 리드타임을 실증할 수 없으므로, 문헌 인용 또는 인위적 지연 모델링으로 대체할지 결정해야 한다 (아래 3-5 리스크 R7 참조).

### 1-2. §2-A 노드 피처 정의 (신규 소절)

**방향** 🟡 — 노드 타입별 전용 차원 + 제로 패딩이 아니라, 의미 기준 일반화 통일 + 노드 타입 임베딩
**세부 매핑** 🔴 — 아래 7슬롯 구성은 Claude 작성

> 전체 12~13개 노드 중 LLM 노드가 1개뿐이므로, 전용 차원은 약 92%의 노드에서 0이 되고 이 값이 GAT attention 연산에 참여해 노이즈로 작용한다. 또한 단일 노드 분량의 신호로 전용 차원의 표현을 학습시키는 것은 비현실적이다. 따라서 의미 기준으로 일반화된 공통 슬롯을 정의하고, 학습 가능한 노드 타입 임베딩(4~8차원)을 연결한다.

| # | 공통 슬롯 | 의미 | 일반 서비스 | LLM 추론 노드 |
|---|---|---|---|---|
| f1 | 상태성 자원 포화율 | 스케일아웃으로 즉시 해소되지 않는 유계 자원의 점유율 | DB 커넥션풀 active/max (HikariCP), Redis 풀 사용률 | KV 캐시 점유율 |
| f2 | 큐 대기율 | 처리 대기 작업의 적체 | 스레드풀 큐 깊이/용량, gRPC 동시 스트림/최대 동시성 | 대기 요청 수 / 최대 배치 크기 |
| f3 | 처리량 대비 용량비 | 현재 처리량의 포화도 | RPS / 측정 최대 용량 | 토큰 처리율 / 최대 토큰 처리율 |
| f4 | 지연 분위수(정규화) | 지연의 상대적 악화 | p95 / SLO 기준값 | TTFT/TTFT SLO, TPOT/TPOT SLO |
| f5 | 자원 사용률 | 계산 자원 점유 | CPU·메모리 사용률 | GPU 사용률·메모리 |
| f6 | 에러율 | 실패 비율 | 5xx / 전체 | 추론 실패·타임아웃 / 전체 |
| f7~ | 노드 타입 임베딩 | 학습 가능 타입 표현 | type=service | type=llm |

모든 피처는 [0, 1] 정규화.

**부수 효과 (본문 명시 권장)** 🔴: f1에서 DB 커넥션풀 소진과 KV 캐시 소진이 **"스케일아웃으로 해소되지 않는 유계 자원의 포화"라는 동일 현상으로 통합 표현**된다. 기존 커넥션풀 논거(D2)와 LLM 논거가 하나의 일반화된 주장으로 결합되어, 피처 설계 자체가 문제 인식을 반영한다는 근거가 된다.

> ⚠️ **A1(예측 라벨 정의)과 연동 필요.** f4의 SLO 기준값이 무엇인지는 라벨 정의에 달려 있다.

### 1-4. §2-C Actuator 4종 재정의 🟡

| # | 조치 (변경 후) | 변경 전 | 일반 서비스 구현 | LLM 노드 구현 |
|---|---|---|---|---|
| 1 | **Circuit Breaking** | Circuit Breaker | Resilience4j 차단 + fallback | LLM 호출 우회(룰 기반·캐시), 툴콜 루프 차단 |
| 2 | **Load Shedding** | Traffic Shedding | Istio/Gateway rate limit, 저우선순위 드롭 | max_tokens 상한, RAG top-k 축소 |
| 3 | **Capacity Scale-up** | K8s Scale-up | HPA 레플리카 증가 | 추론 인스턴스 복제, 배치 크기 조정 |
| 4 | **Degraded-path Redirection** | Read Redirection | read replica·캐시 리다이렉트 | 소형 모델 라우팅, semantic cache |

**개명 사유** 🟡
- `Read Redirection`은 DB 읽기 한정으로 읽혀 모델 다운그레이드를 포괄하지 못함
- `Traffic Shedding`은 요청 수 감소를 뜻하나, LLM에서는 요청당 작업량 축소가 핵심

**Redirection과 Shedding의 경계** 🔴 (예상 질문: "이질적 조치라면서 강도 차이 아닌가")

| | Degraded-path Redirection | Load Shedding |
|---|---|---|
| 조작 대상 | **경로** — 어디서 처리하는가 | **작업량** — 얼마나 처리하는가 |
| 요청의 운명 | 온전히 처리됨 (다른 경로에서) | 응답 자체가 삭감·절단 |
| 부하 처리 | 다른 곳으로 **옮김** | **없앰** |

**Load Shedding 구현 유의** 🔴: `max_tokens` 상한은 decode만 줄이고 prefill은 그대로인 반면, RAG top-k 축소는 prefill을 줄인다. 효과 발현 지점이 다르므로 분리 측정하고, 기본 구현은 예비 실험으로 결정.

**구현 구조** 🟡: `Actuator` 인터페이스 → 조치별 추상 클래스 → 노드 타입별 구현체 주입(전략 패턴). 예: `DegradedPathRedirection` → `ReadReplicaRedirect` / `ModelDowngradeRedirect`.

**단일 엔진 유지** 🟡: LLM 전용 Policy Engine을 별도로 두지 않는다. 분리하면 "LLM 노드에 위험이 예측되었으나 조치는 하위 노드에 적용해야 하는" 경우를 처리할 수 없으며, 이는 그래프 전체를 보고 조치 지점을 선택하는 핵심 능력을 포기하는 것이다. (조치 지점 선택 로직 자체는 A2 참조 — 기존 갭)

### 1-5. §2-D 비용 함수 — 품질 축 추가 🟡

비용 함수의 골격은 `01_기존_설계갭_정리.md` A5 참조. **LLM 확장으로 추가되는 것은 세 번째 축뿐이다.**

```
C_exec(a,v) = w_r · R(a,v) + w_a · A(a,v) + w_q · Q(a,v)
                                            └─ LLM 도입으로 신규
```

| 항 | 의미 | 측정 |
|---|---|---|
| `R` | 자원 비용 | 추가 CPU·메모리·GPU 점유 시간 (직접 측정) |
| `A` | 가용성 손실 | 차단·드롭된 요청 비율 (직접 측정) |
| `Q` | **품질 저하** | 모델 다운그레이드·토큰 제한으로 인한 응답 품질 손실 |

**`Q(a)`의 처리 — 절대 품질을 측정하지 않는다** 🟡

응답 품질의 절대 측정은 LLM 평가 방법론이라는 별개 영역이며 스코프를 벗어난다. `Q(a)`를 조치별 상수(소형 모델 라우팅 = 1.0, max_tokens 50% 제한 = 0.5, 조치 없음 = 0)로 고정하고 **가중치 `w_q`에 대한 민감도 분석**을 수행한다.

- `w_q`를 0.1~1.0에서 변화시키며 조치 선택 분포 변화 측정
- 다운그레이드 선호 → Scale-up·차단 선호로 전환되는 경계점 제시
- **품질을 측정하지 않고도 품질-지연 트레이드오프를 정량 제시**

심사 대응: "품질을 어떻게 측정했나" → "측정하지 않았으며, 운영자가 설정하는 정책 파라미터로 두고 그 영향을 분석했다"

**순환 논리 방어** 🔴: `Q`가 상수이고 `w_q`만 흔들면 "스칼라 하나 조정한 것 아닌가"로 읽힐 수 있다. 다운그레이드가 실제로 응답을 어떻게 바꾸는지 **정성적 사례 1~2개**(동일 질의에 대한 주 모델/폴백 모델 응답 대조)를 부록에 제시. 정량 평가가 아니므로 스코프 부담 없음.

### 1-6. §3 관련연구 3분할 구조 🟡

**3-1. 비교 대상** — GRAF · FIRM · AGQ · GraphGRU. 기존 4자 비교표 그대로 유지.

**3-2. 본 연구가 활용하는 기존 기법** 🟢 (본인 제안)

- FrugalGPT (Chen, Zaharia, Zou, arXiv:2305.05176, 2023): 저렴한 모델부터 순차 질의하고 응답 신뢰도가 임계값 미달일 때만 상위 모델로 escalate하는 캐스케이드. 최상위 단일 모델 대비 최대 98% 비용 절감 보고. **프리프린트(정식 게재 없음)**
- RouteLLM (Ong et al., UC Berkeley·Anyscale, **ICLR 2025**, arXiv:2406.18665): 인간 선호도 데이터로 학습한 라우터가 강/약 모델을 이진 선택. 강 모델 호출 14%로 품질 95% 유지

**두 논문 모두 판단 근거가 질의 난이도와 응답 품질이며, 시스템 부하 상태를 사용하지 않는다.** 즉 "언제 발동할 것인가"라는 축이 비어 있다.

서술 방식 🔴: *"질의를 소형 모델로 우회시켜도 상당 범위에서 품질을 유지할 수 있음은 선행연구가 실증했다. 본 연구는 이를 Degraded-path Redirection Actuator의 구현 근거로 채택하며, 라우팅 기법 자체를 기여로 주장하지 않는다."*

**3-3. 인접하나 문제 범위가 다른 연구** 🔴

키워드가 겹쳐 심사에서 반드시 제기된다. 회피하면 "몰랐거나 숨겼다"로 읽히므로 정면 처리.

**(a) 부하 인지 LLM 라우팅** — HW-Router (Kabir, Xue, Zheng, Lou / UCF, **DAC 2026**, arXiv:2608.14575)는 큐 길이·KV 캐시 사용률·최근 TTFT/TPOT를 경량 지연 예측기에 입력해 SLO 인지 라우팅을 수행. 베이스라인 CARROT·IRT, 오버헤드 약 200μs.

구분 논리:
| 축 | HW-Router 계열 | 본 연구 |
|---|---|---|
| 관측 범위 | 단일 LLM 서비스 내부 (GPU 간 요청 배분) | 서비스 호출 그래프 전체 |
| 시점 | 현재 상태 반응 | 예측 기반 선제 |
| 조치 공간 | 라우팅 단일 | 4종 중 선택 |
| 신뢰도 | 없음 | 티어별 대응 |

> venue가 DAC(하드웨어 설계 자동화)이고 대상이 서빙 플랫폼 내부 GPU 배분이라, 문제 영역 분리가 명확해 구분이 용이하다.

**(b) GraphRouter** — Feng, Shen, You (UIUC, **ICLR 2025**, arXiv:2410.03834). 태스크·질의·LLM 이종 그래프에 엣지 예측으로 각 LLM 응답의 효과와 비용을 예측하는 inductive 프레임워크. 기존 라우터 대비 최소 12.3% 개선.

구분 논리 🔴: *"GraphRouter의 그래프는 질의–모델 적합도 관계이며 서비스 호출 토폴로지가 아니다. 본 연구의 예측 대상은 라우팅 적합도가 아니라 SLO 위반 위험의 전파다."*

> ⚠️ 저자 Jiaxuan You는 GNN 분야 저명 연구자이고 venue가 ICLR이므로 **심사위원이 알고 있을 가능성이 높다.** 구분 서술 누락 시 리스크가 가장 큰 문헌.

> ✅ 위 4편 모두 원문 확인 완료 (2026-09-05).

### 1-7. §4-1 실험 환경 — 벤치마크 구성 🟢/🔴

**변경 1: LLM 어시스턴트 서비스 추가** 🟢

`assistantservice` 신규 추가. frontend가 호출하고, 상품 정보 조회를 위해 productcatalogservice를 호출한다.

배치 위치 근거 🔴: 말단 노드에 배치하면 상류 전파가 없어 연쇄 장애 예측이라는 문제 설정이 성립하지 않는다. frontend 하위 + productcatalog 상위에 두어야 **LLM 포화 → frontend 스레드풀 고갈**(상류)과 **호출 증폭 → 커넥션풀 소진**(하류)의 양방향 경로가 형성된다. 기존 recommendationservice와 병렬 위치이며 원본 호출 패턴을 따르므로 인위적이라는 지적을 피할 수 있다.

**변경 2: PostgreSQL 도입** — `01_기존_설계갭_정리.md` A3 참조. **붙이기(신규 서비스) vs 교체(productcatalog) 미확정.**

**Ablation** 🔴: vanilla(11노드)와 확장 구성(13노드)을 모두 실행하여 LLM 노드 존재가 예측 정확도와 조치 선택에 미치는 영향을 비교.

> ⚠️ **누락 지점**: vanilla 구성에는 LLM 타입 노드가 없으므로 노드 타입 임베딩 학습이 불완전하다. 두 구성에 **별도 모델을 학습**해야 하는지, 아니면 확장 구성 모델을 vanilla에 적용할지 결정 필요 🔴

**토폴로지 (확장 구성)** 🔴

```
loadgenerator
     │
     ▼
  frontend ──────┬──────────────┬─────────────┬──────────────┐
     │           │              │             │              │
     ▼           ▼              ▼             ▼              ▼
 adservice  cartservice  recommendation  assistantservice  checkoutservice
                 │            │             │ (LLM)          │
                 ▼            │             │                ├─► paymentservice
           redis-cart         │             │                ├─► shippingservice
                              │             │                ├─► emailservice
                              ▼             ▼                ├─► currencyservice
                       productcatalogservice ◄────────────────┘
                              │
                              ▼
                         PostgreSQL
                       (HikariCP pool)
```

**LLM 서빙 구성** 🔴: 2티어 캐스케이드. 절대 파라미터 규모보다 **티어 간 지연·품질 격차 비율**이 본질이므로, 가용 하드웨어에 맞춰 소형 모델 2종(예: 1.5B 주 / 0.5B 폴백)으로 구성. 본문에 *"대상은 계층 간 상대적 격차이며 절대 규모는 실험 환경 제약에 따른 선택"*임을 명시.

**호출 구현 — LLM 출력에 의존하지 않는다** 🔴

assistantservice의 productcatalog 호출을 LLM의 function calling 출력에 맡기지 않는다. 0.5B~1.5B급은 function calling 신뢰도가 낮아 호출 발생 자체가 불안정해지고 재현성을 훼손한다.

**결정적 파이프라인**으로 구현: 질의 수신 → 사전 정의 규칙에 따라 카탈로그 조회 N회 → 조회 결과를 컨텍스트로 LLM 요약 → 응답. 이 구조는 (1) 호출 횟수 `N`이 실험 파라미터로 통제되어 S3 시나리오 주입이 정확해지고, (2) LLM 품질 변동이 부하 패턴에 영향을 주지 않아 변수가 분리된다.

한계 섹션 기재: 실제 에이전트는 동적 툴콜을 수행하므로, 본 구현은 증폭 현상을 통제된 형태로 재현한 것이다.

**부하 생성 — loadgenerator 확장** 🔴 **[미결정]**

원본 Online Boutique의 loadgenerator(Locust)는 정해진 사용자 여정(상품 조회 → 장바구니 → 결제)을 반복한다. assistantservice를 포함시키려면 아래를 정의해야 한다.

| 항목 | 결정 필요 사항 |
|---|---|
| 호출 비율 | 전체 사용자 여정 중 어시스턴트를 호출하는 비율 (예: 20%) |
| 프롬프트 소스 | 고정 프롬프트 세트 순환 / 상품 카탈로그 기반 템플릿 생성 / 합성 |
| 프롬프트 길이 분포 | S2 시나리오의 "긴 프롬프트 버스트"를 정의하려면 정상 상태 분포가 먼저 필요 (G3와 연동) |
| 호출 횟수 `N` | S3 주입 파라미터. 정상 상태 기본값과 주입 시 증가폭 |

권장 🔴: 상품 카탈로그의 실제 데이터를 기반으로 템플릿에서 프롬프트를 생성(예: *"{카테고리} 중에 {조건}인 상품 추천해줘"*). 재현 가능하고, 카탈로그 조회 횟수를 템플릿으로 통제할 수 있어 S3 주입과 자연스럽게 연결된다.

### 1-8. §4-2 장애 시나리오 3종 🔴 **[전적으로 Claude 작성]**

기존 커넥션풀 단일 편중 문제를 3종으로 해소. 각 시나리오가 서로 다른 Actuator를 최적해로 갖도록 설계하여 이질적 조치 공간의 필요성을 실증한다.

| # | 시나리오 | 주입 방법 | 전파 경로 | 기대 최적 조치 | 검증 대상 |
|---|---|---|---|---|---|
| S1 | DB 커넥션풀 소진 | HikariCP max pool 축소 + 슬로우 쿼리 (Chaos Mesh) | productcatalog → 다중 상류 | Degraded-path Redirection | 자원할당 접근의 역효과 (Thundering Herd) |
| S2 | LLM 노드 포화 | 긴 프롬프트 버스트 (Locust) | assistant → frontend 스레드풀 고갈 | 중간신뢰도: 다운그레이드 / 고신뢰도: Shedding | 리드타임 논거, 품질-지연 트레이드오프 |
| S3 | 호출 증폭 연쇄 | 요청당 카탈로그 조회 횟수 N 증가 | assistant → 커넥션풀 → frontend (2단) | Circuit Breaking 또는 Shedding | **위상 인지 필요성 — 조치 지점 ≠ 예측 지점** |

**S3의 전략적 중요성** 🔴: 위험이 예측되는 노드(productcatalog)와 조치를 적용할 노드(assistantservice)가 다르다. 노드 단위 시계열 모델이나 단일 서비스 내부 최적화로는 원리적으로 불가능한 조치 선택이며, **그래프 전체를 보는 단일 Policy Engine이어야 하는 이유**를 실증한다. 3-3(a)에서 구분한 부하 인지 라우팅 연구군이 다룰 수 없는 영역이기도 하다.

> ⚠️ **S3는 A2(조치 대상 노드 선택 로직)에 전적으로 의존한다.** A2가 해결되지 않으면 S3가 성립하지 않고, 그러면 단일 엔진 유지 근거도 함께 무너진다.

> ⚠️ **S2의 리드타임 논거는 실험 환경과 충돌 가능** — CPU 소형 모델 환경에서는 GPU 기동 리드타임을 실증할 수 없다. R7 참조.

### 1-9. §4-3 Baseline 🔴

| Baseline | 설명 | 목적 |
|---|---|---|
| K8s HPA (반응형) | CPU 기반 기본 오토스케일러 | 사후 대응의 한계 |
| 규칙 기반 Policy | 고정 임계값 룰 | 예측의 가치 |
| LSTM baseline | 노드별 시계열 예측 | **핵심 검증: 위상 정보의 가치** |
| GRAF류 baseline | GNN 예측 + 자원 할당 단일 조치 | 이질적 조치 공간의 가치 |
| FIRM류 baseline (선택) | 이질적 조치 + 위상 미반영 | 두 축의 결합 효과 |
| **신뢰도 미사용 ablation** 🔴 | 동일 GNN 예측 + 티어 게이팅 없이 argmax | **신뢰도 축 단독 기여 분리** |

> 신뢰도 구간별 대응이 유일한 신규 축이므로, 제거 시 성능 저하를 정량으로 보이는 것이 기여 입증의 핵심이다. 컷라인에서 **가장 마지막에 잘라야 할 실험**.

### 1-10. §4-4 평가 지표 (신규 소절) 🔴 **[누락 보완]**

baseline과 시나리오는 정의했으나 **무엇을 측정해 비교할 것인가**가 정의되지 않았다. 지표 없이는 실험 설계가 완성되지 않으며, 프로포절에서도 반드시 질문이 나온다.

**(1) 예측 성능 — GNN 자체의 품질**

| 지표 | 정의 | 비교 대상 |
|---|---|---|
| Precision / Recall / F1 | 노드별 SLO 위반 예측 (A1의 라벨 정의에 의존) | LSTM baseline, GRAF류 |
| 조기 탐지 시간 (lead time) | 실제 위반 발생 시점 − 예측 시점 | LSTM baseline |
| 신뢰도 캘리브레이션 (ECE) | 예측 확률과 실제 발생률의 일치도 | 신뢰도 미사용 ablation |

> ECE(Expected Calibration Error)는 **신뢰도 축의 정당성을 직접 뒷받침하는 유일한 지표**다. 앙상블이 산출한 신뢰도가 실제로 의미 있는 값임을 보여야 티어 게이팅이 근거를 갖는다.

**(2) 시스템 성능 — 조치의 결과**

| 지표 | 정의 |
|---|---|
| SLO 위반율 | 전체 요청 중 SLO 초과 비율 (노드별·전체) |
| p95/p99 지연 | 일반 노드: 응답시간 / LLM 노드: TTFT, TPOT |
| 실패 요청 비율 | 차단·드롭·타임아웃 |
| 복구 시간 | 장애 주입 시점 → SLO 정상 복귀 시점 |

**(3) 비용 지표 — 조치의 대가**

| 지표 | 정의 |
|---|---|
| 자원 사용량 | 누적 CPU·메모리·(GPU) 점유. GRAF의 §V-E와 대응 |
| 조치 발동 횟수 | 조치 종류별 발동 빈도 |
| 오탐률 | 조치를 발동했으나 실제 위반이 없었던 비율 |
| 다운그레이드 비율 | 소형 모델로 처리된 요청 비율 (품질 저하의 대리 지표) |

**LLM 노드의 SLO 기준값 설정** 🔴 **[미결정]**

일반 서비스는 원본 Online Boutique의 관측값으로 기준을 잡을 수 있으나, assistantservice는 신규 노드라 SLO 기준을 **임의로 정해야 한다.** 근거 없는 값을 쓰면 "기준을 유리하게 잡은 것 아닌가"라는 지적이 나온다.

권장 접근 🔴: 무부하 상태에서 주 모델의 TTFT·TPOT를 실측하고, 그 값의 일정 배수(예: p95의 2배)를 SLO로 설정한 뒤 설정 근거를 본문에 명시. 절대값이 아니라 **자체 실측 대비 상대값**이므로 방어 가능하다.

### D. 관련연구

**D13. LLM 캐스케이드·라우팅 연구군 — 활용 기법으로 채택** 🟢
- FrugalGPT·RouteLLM 모두 판단 근거가 질의 난이도와 응답 품질이며 시스템 부하를 사용하지 않음. "언제 발동할 것인가" 축이 비어 있음. 경쟁 논문이 아니라 활용 기법으로 처리하여 라우팅 효과를 직접 실증할 부담 제거. [원문 확인 완료]
- FrugalGPT는 arXiv 프리프린트만 존재(정식 게재 이력 없음). 인용 시 명시.

**D14. 부하 인지 LLM 라우팅 — 인접 연구로 명시적 구분** 🔴
- HW-Router(Kabir et al., DAC 2026, arXiv:2608.14575) 확인. "시스템 상태를 보고 라우팅한다"는 아이디어는 이미 존재. venue와 대상 영역이 분리되어 구분은 용이. 4축 구분 논리 확보. [원문 확인 완료]

**D15. GraphRouter — 명칭·키워드 충돌 주의** 🔴
- Feng, Shen, You (UIUC, ICLR 2025, arXiv:2410.03834). 그래프의 정의가 근본적으로 다름(질의–모델 적합도 vs 서비스 호출 토폴로지). 저자 인지도와 venue를 고려할 때 **구분 서술 누락 시 리스크 최대**. [원문 확인 완료]

**D16. 관련연구 3분할 구조 확정** 🟡
- 문헌이 4편 → 7~8편으로 늘면서 동일 비교표에 넣으면 같은 축 비교를 요구받아 방어 부담 급증. 3분할(비교 대상 / 활용 기법 / 인접 연구)로 격리. **4자 비교표에는 LLM 라우팅 연구를 추가하지 않는다.**

### E. 모델 아키텍처

**E1. GAT 채택 논거 강화** 🔴 **[Claude 제안, 미검토]**
- 기존 근거는 "GRAF·AGQ가 attention 차등 집계를 쓰지 않았다"는 문헌 공백 + "서비스별 중요도가 균일하지 않다"는 일반론.
- 변경 제안: 혼합 그래프에서는 이웃 간 중요도 불균일이 **구조적 사실**이 된다. 동일 노드의 이웃에 밀리초 단위 stateless 서비스와 초 단위 LLM 노드가 공존하므로, 균등 합산은 두 유형의 신호를 같은 무게로 섞는다.
- 확장 제안: attention weight 시각화로 "LLM 노드가 실제로 더 큰 가중치를 받는가" 검증 (§4 해석 가능성 보강, 선택 항목).
- **유의**: 실측이 기대와 다르게 나오면 논거를 철회하고 기존 문헌 근거로 복귀할 것.

**E5. 이질적 노드 피처 표현 — 일반화 통일 + 타입 임베딩** 🟡
- 전용 차원 + 제로 패딩은 92% 노드에서 0이 되어 attention 노이즈가 되고, 단일 노드 신호로 전용 차원 학습은 비현실적. 의미 기준 공통 슬롯 7종 + 타입 임베딩 채택. 정보 손실이 아니라 의미 정렬.
- 부수 효과: f1에서 커넥션풀 소진과 KV 캐시 소진이 동일 현상으로 통합 표현되어, D2 논거와 LLM 논거가 하나로 결합.

**E6. Actuator 4종 재정의 및 개명** 🟡
- 개수 유지, 2종 개명. Load Shedding은 FIRM의 브라운아웃과 개념이 겹치므로 관련연구에서 "브라운아웃을 LLM 맥락으로 확장"으로 서술하면 방어 용이.

**E7. 단일 Policy Engine 유지** 🟡
- 엔진 분리 시 예측 노드와 조치 노드가 다른 경우를 처리 불가하고, "통합 Policy Engine" 기여가 쪼개짐. 노드 타입별 차이는 Actuator 레이어에서 전략 패턴으로 흡수.

### F. 학습·평가

**F3. 학습 데이터 수집과 평가 실행의 분리** 🟡
- 기각된 안: "소형 모델로 학습, 대형 모델로 서빙"은 부적절. 모델을 바꾸면 TTFT·처리율·KV 캐시 증가 속도 등 **메트릭 분포 자체가 변해** 학습 시 관측하지 않은 분포에서 추론하게 됨.
- 채택: 모델 크기가 아니라 **실행 방식**을 분리. 학습 데이터는 운영과 동일 구성(2티어)을 실측 분포로 보정한 에뮬레이션으로 대량 수집, 평가는 동일 구성을 실제 모델로 20~30 에피소드.
- 방어 논거 🔴: 에뮬레이터가 실측 분포를 재현하도록 보정되었음을 §4에 명시. 보정 절차와 실측 대비 오차를 별도 표로 제시.

**F4. `w_q` 민감도 분석 — 품질 측정 회피** 🟡
- `Q`를 조치별 상수로 두고 `w_q`를 정책 파라미터로 정의. 0.1~1.0 변화 시 조치 선택 분포 변화와 전환 경계점 제시.
- 보강 🔴: 정성적 응답 대조 사례 1~2개 부록 제시로 순환 논리 방어.

### G. 오픈 이슈 (LLM 확장 고유)

**G9. [신규] 에뮬레이터 학습 → 실제 모델 평가의 전이 검증** 🔴

- 문제: F3에서 학습은 에뮬레이션, 평가는 실제 모델로 분리했다. 그런데 **"에뮬레이터로 학습한 모델이 실제 환경에서도 예측 정확도를 유지한다"는 전제 자체가 검증되지 않았다.** 이것은 F3의 성립 조건이며, 검증 없이는 전체 실험 결과의 신뢰성이 무너진다.
- 필요한 것: 전이 검증을 **하나의 독립 실험으로** 설계해야 한다. 예 — 실제 모델 환경에서 소량(예: 500샘플)을 수집하고, 에뮬레이터 학습 모델의 예측 성능을 (a) 에뮬레이터 테스트셋, (b) 실제 환경 소량 셋에서 각각 측정해 성능 격차를 제시.
- 격차가 크면 대안: 에뮬레이터 사전학습 → 실제 소량 데이터로 파인튜닝(transfer learning).
- 상태: 오픈. **F3에 직결되므로 에뮬레이터 구현과 동시에 설계 필요.**

**G10. [신규] LLM 노드가 1개뿐인 구조적 한계** 🔴

- 문제: E5에서 제로 패딩을 기각한 근거가 "단일 노드 분량의 신호로 전용 차원을 학습시키는 것은 비현실적"이었다. 그런데 **노드 타입 임베딩도 같은 문제를 일부 겪는다** — `type=llm` 임베딩의 학습 신호가 노드 1개에서만 온다. "임베딩은 되고 전용 차원은 안 되는 이유가 무엇인가"라는 반문이 가능하다.
- 부분적 반론: 임베딩은 차원이 작고(4~8) 시간축으로 다수의 샘플이 쌓이므로 전용 피처 차원보다 유리하다. 다만 완전한 답은 아니다.
- 검토할 대안: LLM 노드를 **2개로 확장**(예: assistantservice + 임베딩/요약 전용 서비스). 타입 임베딩 학습 신호가 늘고, "이질적 노드가 서로 다른 위치에서 각각 전파를 일으킨다"는 그림도 강해진다. 다만 구현 부담과 일정이 추가된다.
- 상태: 오픈. **1차는 1개로 진행하고, 학습 결과에서 타입 임베딩이 유의미하게 학습되지 않으면 2개로 확장하는 단계적 접근 권장.**

**G4. LLM 에뮬레이터 보정 기준** 🔴
- 실측 분포를 어느 수준까지 재현해야 "보정되었다"고 주장 가능한지 미정. TTFT·TPOT·큐 깊이 3개 지표의 분포 일치도(KS 검정 또는 분위수 비교) 제시 방향 검토.

**G5. LLM 서빙 하드웨어 — 대응 방침 확정** 🟢
- 로컬 불가 시 **시간단위 과금 클라우드 대여로 처리**하기로 확정. A2("메인 실험은 로컬 유지")의 예외로 기록하며, 근거는 LLM 추론이 하드웨어 요구가 이산적이라 경량화로 우회 불가하다는 점.
- 실행 순서: CPU 소형 모델로 로컬 시도 → 불가 시 학습 데이터는 에뮬레이터로 로컬 유지, 평가만 단기 클라우드 → 종료.

**G7. [신규] 리드타임 논거의 실증 방법** 🔴
- 문제: §1과 A4의 핵심 논거가 "추론 자원 기동 리드타임이 길다"인데, CPU 소형 모델 환경에서는 이를 실측할 수 없다.
- 선택지: (a) 문헌값 인용 + 주장 수위를 "설계상 고려"로 낮춤, (b) 인위적 기동 지연을 주입하여 모델링, (c) 클라우드 GPU 환경에서 리드타임만 별도 측정.
- 상태: 오픈. **S2 시나리오와 A4의 티어 하향 근거에 직결되므로 조기 결정 필요.**

**G8. [신규] vanilla / 확장 구성의 모델 학습 분리 여부** 🔴
- vanilla 11노드 구성에는 LLM 타입 노드가 없어 노드 타입 임베딩 학습이 불완전. 두 구성에 별도 모델을 학습할지, 확장 구성 모델을 vanilla에 적용할지 미정.

**G2·G3 상태 변화**
- G2(추론 레이턴시): 조치별 리드타임 편차가 커져 우선순위 상향. A4의 원칙이 부분 해법.
- G3(트래픽 프로파일): 프롬프트 길이 분포와 호출 횟수 분포 파라미터 추가 필요. S2·S3 설계와 직결.

> **절대 컷하지 않을 항목**: 신뢰도 미사용 ablation. 유일한 신규 축의 기여 입증.
>
> ⚠️ **4번 주의**: Actuator를 2종으로 줄이면 "이질적 조치 공간"이라는 기여 자체의 실증이 약해진다. 2종만 남길 경우 남기는 2종이 **서로 다른 성격**(경로 변경 vs 차단)이어야 최소한의 이질성을 보일 수 있다.
