## 1. 신뢰도 축 유일성 — 검증 범위가 3편에 한정 ✅

**갭**: [challenges](../../research/challenges.md) D12는 GRAF·FIRM·AGQ 3편만 확인하고 *"신뢰도 구간별 대응이 문헌상 완전히 비어 있다"*는 **무한정 주장**으로 결론냈다. proposal §3은 "세 논문 모두 …"로 범위가 한정되어 있었으나, README·overview·D12 결론은 한정 없이 서술해 심사 리스크가 있었다.

**원문 확인 결과 ✅ (2026-09-06)** — 서지사항부터 당초 기재와 달랐다.

| 논문 | 실제 서지 | 임계값 결정 방식 | 조치 공간 | 도메인 |
|---|---|---|---|---|
| **CP-Router** | Su, J. et al., **AAAI 2026**, arXiv:2505.19970 | **Conformal Prediction으로 유도** (커버리지 보장) + FBE로 적응적 선택 | 이진 동질 (LLM↔LRM) | MCQA·QA |
| **Ramírez et al.** | **COLM 2024 정식 게재** (프리프린트 아님), arXiv:2405.02134 | 초기 질의로 잡은 뒤 **동적 보정**. 목표는 비용식 `c = ĉ_s + p_c·ĉ_l`의 예산 | 이진 동질 (small↔large) | NLP 9개 태스크 |

> ⚠️ **당초 세운 구분 논리 1번("2티어 선택은 임계값을 손으로 긋는다")은 사실과 반대였다.** 두 논문 모두 임계값을 원리적으로 유도한다. 이 논거를 그대로 심사에 들고 갔으면 핵심 기여 축에서 반박당했을 항목이다 — D14(FIRM 브라운아웃 오기재)와 같은 유형의 사고이며, 원문 우선 원칙을 재확인시킨다.

**재정의된 구분선** — 원문 확인으로 오히려 더 정확한 선이 잡혔다.

1. **임계값의 개수와 유도 근거** — 두 선례는 단일 불확실성 축 위에 임계값을 **하나** 두고, 근거는 통계적 커버리지(CP-Router) 또는 비용 예산(Ramírez)이다. 본 연구는 **조치마다 다른** `θₐ = Dₐ·Rₐ / (mₐ·L − Dₐ(1−Rₐ))`가 유도되며, 근거는 커버리지도 예산도 아닌 **조치별 완화효과 `mₐ`·가역성 `Rₐ`·disruption `Dₐ`의 트레이드오프**다. 결과적으로 *장애 유형이 바뀌면 같은 신뢰도에서도 선택이 달라진다*(상태성 병목에서 `m_scale-up` 급락 → Scale-up 자동 배제). 선택지 간 완화효과 차이가 없는 2티어 구조에서는 원리적으로 불가능한 거동이며, **가장 방어력 있는 선이다.**
2. **조치 공간** — 둘 다 이진 동질. "무엇을 할까"가 아니라 "누구에게 시킬까"만 고른다. 본 연구는 질적 이질 5종. **확인 후에도 그대로 유효.**
3. **도메인** (1차 방어선) — 두 선례의 조치 대상은 자기 자신의 추론 경로다. 본 연구는 그래프 상의 **다른 노드**다(항목 4). 문제 설정이 겹치지 않는다.

**반영** ✅: 주장 수위를 "장애 예측·자원 관리 도메인에서 비어 있다"로 한정(proposal §3, README, overview, D12 결론). 두 논문은 회피하지 않고 **인접 연구로 §3·참고문헌에 명시**. 경위는 challenges **D15**.

**잔여**: 없음. 다만 LLM 라우팅은 신규 논문 유입이 빠르므로 **심사 직전 재검색 1회 권장**.

## 2. 요약 문서에 낡은 티어 서술이 남아 있다 ✅

**갭**: proposal §2-B에서 `θₐ` 유도로 대체된 산문이 세 곳에 그대로 남아 있었다 — "고신뢰도 = 적극적 조치 / 중간신뢰도 = 저비용·가역적 조치 / 저신뢰도 = 보류". 이 산문만 읽으면 *"무엇이 '적극적'인지 정의가 없다"*는 지적이 그대로 성립하고, 심사위원이 README부터 읽으면 같은 질문이 나온다.

**반영** ✅: proposal §2-B·README·overview 세 곳 모두 "구간을 손으로 긋지 않고 비용함수에서 조치별 임계값 `θₐ`가 유도된다"로 갱신. 기존 산문은 유도의 *결과 요약*이지 정의가 아님을 명시. 설계 변경이 아니라 문서 동기화다.

## 3. 상태성 병목 — 단일 지점 + 스코프 불일치 ✅

> **주의**: 이 항목의 출발점이었던 *"Online Boutique에 상태성 병목을 실증할 대상이 없다"*는 주장은 **사실이 아니다.** proposal §4-5에 cartservice→Redis 경로가 주입 방법까지 명시되어 있었다. **Redis 경로는 폐기하지 않고 1차 병목으로 그대로 유지한다.** 아래가 실제 문제였다.

**갭 1 — Read Redirection의 구현 경로 미검증 ✅ [1순위 근거]**

컷 우선순위상 최후까지 남기는 Actuator 2종은 CB + Read Redirection이다. 그런데 Read Redirection의 유일한 실증 대상이 "Redis primary/replica + Envoy `read_policy`"였고, **Envoy 공식 문서 확인 결과 `read_policy`는 "currently supported for Redis Cluster"로 명시**되어 있다. Online Boutique의 `redis-cart`는 단일 인스턴스라, 이 경로를 쓰려면 `redis-cart`를 Cluster 모드로 전환하고 `cartservice`의 Redis 클라이언트도 cluster-aware로 바꿔야 한다 — **즉 원본 서비스 변형이 필요하다.** 이는 (a) 방식이 지키려던 "원본 보존"(우려 6 방어의 토대)과 정면 충돌한다.

> 쟁점은 하드웨어 부담이 아니라 **벤치마크 충실도**다. 실험용 PC를 별도로 마련하더라도 이 논거는 그대로 성립한다.

**갭 2 — 단일 지점 의존** 🔴: 상태성 병목 실증 지점이 하나뿐이라, 그 시나리오가 실패하면 핵심 차별점(D2)에 대체재가 없다.

**갭 3 — 스코프와 벤치마크 불일치 ✅**

| 위치 | 선언 | 현실 |
|---|---|---|
| proposal §5 | "Thread-per-request 모델 한정 / Java·Spring 실증 한정" | cartservice는 **C#/.NET** |
| proposal §4-4 | 평가지표에 "톰캣 스레드 덤프" | Java 서비스는 adservice뿐이고 **gRPC라 서블릿 컨테이너 아님** |

Online Boutique 저장소 서비스 표로 확인(frontend·checkout·productcatalog·shipping = Go, recommendation·email = Python, currency·payment = Node.js, cart = **C#**, ad = **Java/gRPC**). 즉 현재 구성으로는 선언한 스코프와 지표를 실증할 노드가 없었다.

**결정** 🟢 **(a) 신규 서비스 추가로 확정** — Spring + HikariCP + PostgreSQL 서비스 1개를 별도 노드로 붙인다(총 12~13개). 원본 서비스와 호출 관계는 보존.

| 방식 | 판정 |
|---|---|
| **(a) 신규 서비스 추가** | **채택.** Postgres primary/replica는 어차피 새로 붙이는 노드라 복제 구성이 원본 충실도를 훼손하지 않고, 스트리밍 복제 + 읽기 라우팅이 표준이라 구현 부담도 낮다 |
| (b) productcatalogservice 교체 | 미채택. fan-in 3의 이득보다 원본 변형 비용(우려 6 방어 약화, Go→JVM 지연 특성 변화)이 크다 |

판단 기준은 "fan-in 크기"가 아니라 **"Read Redirection의 구현 경로를 원본 변형 없이 확보하는가"**다.

**반영** ✅: proposal §2-C(Envoy 제약 + Postgres를 Redirection 1차 대상으로), §4-1(벤치마크 구성 + 근거 3순위), §4-5(두 번째 병목), §5(스코프 정합), 우려 6(원본 부분그래프 보존 단서). 경위는 challenges **B6**, 일정은 timeline(구현 항목 2~3주).

**잔여(미결정)** ⚠️: 추가 서비스의 **배치(어느 서비스가 호출하는가)·명칭·API.** 배치가 fan-in과 전파 경로를 결정하므로 실험 환경 구축 착수 전 확정. 확정 후 노드 수 표기("12~13개")를 최종값으로 고정한다.

## 4. 조치 적용 지점 — §2-C와 §2-E 알고리즘의 불일치 ✅

**갭**: proposal §2-E 의사코드는 `emit(대상=v, …)`로 조치 대상을 **위험 노드 자신**으로 고정했다. 그러나 §2-C의 Actuator 서술은 이미 "조치 지점 ≠ 위험 지점"이었다.

| Actuator | 위험 노드 | 실제 적용 지점 |
|---|---|---|
| Brownout | adservice / recommendationservice | **frontend** (호출을 조건부 생략) |
| Read Redirection | 상태성 백엔드 (Postgres primary, Redis primary) | **백엔드를 호출하는 서비스** |
| Circuit Breaker | 피호출 노드 | **호출자** (Resilience4j는 호출 측) |
| Traffic Shedding | 과부하 노드 | **v의 인그레스** |
| K8s Scale-up | 자원 부족 노드 | **v 자신** (5종 중 유일) |

심사에서 §2-E 의사코드를 제시하면 *"Brownout은 adservice에 거는 겁니까?"*에 문서가 자기모순을 일으킨다.

**반영 — 최소 변경** ✅

1. proposal §2-E — `emit(대상=apply_point(a*, v), …)`로 수정 + `apply_point` 설명 추가
2. proposal §2-C — **조치별 적용 지점 표** 신설 (위 표를 정식화)
3. proposal §4-2 — "어느 서비스에 조치할지" → "어느 서비스가 **위험한지**" (예측 대상과 적용 지점의 분리)

적용 지점은 탐색 대상이 아니라 조치 종류에 따라 **구조적으로 결정**되므로, 후보 집합 탐색(k-hop 상류 등)은 도입하지 않는다. 그런 안은 `argmin E[비용]` 구조와 달라 채택 시 `θₐ` 유도와 Safety Guard를 함께 버려야 한다(G1·G4 역행). **비용함수는 불변** — `p̄_v`·`u_v`·`p_eff`·`θₐ`·`mₐ` 모두 그대로. 경위는 challenges **E7**.

**부수 효과**: "위상 인지가 예측에만 쓰이고 조치 선택에는 안 쓰인다"는 예상 반론에 답이 생겼다.

## 5. 비용함수에 조치 실행 리드타임 항이 없다 ✅

**갭**: proposal §2-B의 `Dₐ`·`Rₐ`·`mₐ`는 모두 조치의 *결과*를 다루며, 조치가 실제로 완료되기까지의 **실행 리드타임**이 없다(표의 "대상 전파속도"는 장애 쪽 속도다). 리드타임이 긴 조치(Scale-up: 인스턴스 기동·워밍업)는 `θₐ`를 넘긴 시점에 발동해도 완료 시점에는 이미 늦을 수 있다.

> 🔴 **미확인**: 관련 논거로 "GRAF가 인스턴스 생성 평균 5.5초 + 오토스케일러 결정 주기와 맞물린 cascading effect를 관측했다"는 수치가 거론되었으나 **원문 미확인이다.** 본문 인용 전 GRAF 원문(CoNEXT'21 / ToN'24) 확인 필요 — 확인 전에는 논거로 쓰지 않는다(D14의 원문 우선 원칙). proposal 본문에는 이 수치를 넣지 않았다.

**검토 방향**: 신뢰도 티어 표를 손으로 다시 긋는 방식은 채택하지 않는다(G1의 "구간을 손으로 긋지 않고 유도" 철학에 역행). 조치별 리드타임 `ℓₐ`를 예측 지평 `Δ`와 비교하는 제약(`ℓₐ < Δ`)으로 넣는다 — §4-2가 이미 "Δ의 하한 = 폐루프 응답시간"이라 적고 있으므로 이를 **조치별로 분해**하는 확장이 된다.

**반영** ✅: proposal §2-B에 "미반영 항목"으로 명시, challenges **G5**로 등재, timeline 오픈 이슈에 [이관] 기록.

**잔여**: 조치별 리드타임 실측. G3와 같은 논리로 **실험 설계로 이관**(실측 없이 미리 확정하면 근거가 약한 값이 된다). 프로포절 심사 필수 아님.
