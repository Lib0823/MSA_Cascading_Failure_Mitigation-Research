## 0. 결정 요약

### 0-1. 무엇을 바꾸는가

| 구분 | 내용 |
|---|---|
| **유지** | GAT(정적) · Deep Ensemble(N=5) · **비용함수 전체**(`p_eff`·`θₐ`·`mₐ`·`Dₐ`·`Rₐ`) · 2계층 제어 · `apply_point` 사상 · **조치 5종** · 단일 Policy Engine · 5자 비교표 · Online Boutique 메인 · TA-GAT · RL·STGNN 미채택 |
| **확장** | 대상 시스템에 LLM 추론 서비스 1개 추가 → **조치 5종의 실행 방식이 노드 타입별로 분기** |
| **수정** | 노드 피처를 의미 기준 공통 슬롯으로 일반화(+타입 임베딩), `Read Redirection` 개명, 관련연구 3분할 |
| **미채택** | ① LLM 에이전트를 Policy Engine으로 사용 ② LLM 서빙 인프라 전용 프레임워크로 전면 전환 |

> **비용함수는 손대지 않는다.** 품질 비용이 들어갈 자리는 이미 `Dₐ`(조치의 즉시 비용 — 정상 트래픽 손실·자원 소모)이며, Brownout이 `Dₐ = 중`으로 표에 있다. LLM 조치도 `Dₐ`·`Rₐ`·`mₐ`만 정하면 되고 새 항·새 가중치가 필요 없다(§1-4).

### 0-2. 왜 바꾸는가 — 방어 논리

> 기존 3축(위상 인지 예측 / 이질적 조치 / 신뢰도 구간별 대응)은 LLM 없이도 성립한다. LLM 노드는 **세 축을 새로 정당화하는 것이 아니라, 이질성이 실재하는 환경에서 검증 범위를 넓히는 것**이다.

| 축 | LLM 노드가 더하는 것 |
|---|---|
| 위상 인지 | LLM 노드의 지연은 RPS가 아니라 토큰 길이·KV 캐시 점유·큐 깊이에 좌우된다 → 이웃 노드와 **부하 지표의 의미 자체가 다른** 그래프에서도 전파 예측이 성립하는지 검증 |
| 이질적 조치 | 품질 저하 레버가 한 노드(adservice/recommendation)에만 있던 것에서 **두 종류**(기능 생략 / 토큰·컨텍스트 축소)로 늘어 조치 공간의 이질성이 실증 범위에서 넓어진다 |
| 신뢰도 구간 | 조치 간 실행 리드타임 편차가 커져 `θₐ` 차등의 실효가 두드러진다 |

> ⚠️ **"LLM 때문에 세 축이 필연이 된다"고 주장하지 않는다.** 심사에서 *"LLM 없이도 필요하다면서 왜 넣었나"*로 되돌아온다. 정확한 표현은 *"세 축은 LLM 없이도 성립하며, LLM 노드는 그 적용 범위가 동질 워크로드에 한정되지 않음을 보이는 검증 대상"*이다.

### 0-3. 미채택한 두 방향

**(A) LLM 에이전트를 Policy Engine으로 사용** — 비결정적 출력이라 반복 실험 기반 정량 비교·재현성 확보 불가. "GNN과 LLM을 왜 둘 다 쓰나"에 대한 설계 정당화 곤란. 프롬프트 설계·평가 체계로 일정 초과.

**(B) LLM 서빙 인프라 전용 프레임워크로 전면 전환** — 연구 분야가 이동한다. 전 노드가 LLM인 시스템은 LLM serving systems 영역(vLLM·SGLang 계열)이고 본류는 스케줄러·KV 캐시 관리이지 서비스 그래프 위상 예측이 아니다. 기존 확정 사항 대부분(벤치마크, 비교 논문 5편, 커넥션풀 논거, GAT 근거)이 무효화되고, 심사위원이 LLM 서빙 전문가 기준으로 평가하게 되어 KCI 목표 대비 요구 수준이 과도해진다.

채택 방향은 둘의 중간 — **혼합 그래프(일반 서비스 + LLM 노드 1개)를 대상으로 하되, 프레임워크 골격과 기여 구조는 유지.**

### 0-4. 무게중심 유지 원칙

- 주장은 어디까지나 **"GNN 기반 위상 인지 선제 대응"**이며, LLM 노드는 **검증 대상**이다.
- "LLM 시대의 MSA"를 전면에 내세우지 않는다.
- 라우팅·캐스케이딩 자체는 기여가 아니라 **Actuator 구현체**로 위치시킨다.

**제목·초록에서의 위치**: **(b) 초록에만 언급**을 권장. 제목은 기존 프레임을 지키고, 초록에서 "LLM 추론 서비스를 포함한 **이기종 워크로드** 환경에서 검증"이라는 중립적 표현으로 대상 확장을 명시한다. 제목에 넣으면 심사위원이 LLM 서빙 전문가 기준으로 평가하기 시작해 R2가 현실화되고, 아예 빼면 실험 파트에서 LLM이 뜬금없이 등장한다.

## 1. proposal 수정분

### 1-1. §1 연구 배경 — 다섯 번째 한계 추가

> **이질적 워크로드 노드의 등장**
>
> 최근 마이크로서비스 아키텍처에는 LLM 추론 서비스가 일반 서비스와 동일한 그래프 위에 배치되는 사례가 증가하고 있다. LLM 추론 노드는 기존 오토스케일링이 전제하는 세 가지 가정을 위반한다.
>
> 1. **부하 지표 가정의 붕괴** — 기존 HPA는 CPU 사용률 또는 RPS를 부하 대리지표로 쓰나, LLM 추론 노드의 지연은 요청 수가 아니라 입력·출력 토큰 길이, KV 캐시 점유율, 대기 큐 깊이에 지배된다. 동일 RPS에서도 지연이 수 배 달라질 수 있다.
> 2. **스케일아웃 가정의 붕괴** — 추론 인스턴스 기동은 일반 컨테이너 대비 리드타임이 길고 단위 비용이 크다.
> 3. **가역성 가정의 일반화** — 조치 결과가 성공/실패의 이분법이 아니라 "낮은 품질로 성공"이라는 제3의 상태를 갖는 노드가, 기존에는 optional 경로를 가진 일부 서비스에 한정되었으나 LLM 노드에서는 모든 요청으로 확대된다.
>
> 나아가 LLM 노드는 단일 요청이 하위 서비스에 대한 다중 호출로 증폭되는 특성이 있어, 상류 부하 증가가 하위 상태성 자원 소진으로 이어지는 새로운 연쇄 경로를 만든다.

> ⚠️ **2번의 리드타임 논거는 실측이 필요하다.** GRAF의 인스턴스 생성 시간 수치가 자주 인용되나 **원문 미확인 상태이므로 쓰지 않는다**(D14의 원문 우선 원칙). 인용하려면 GRAF 원문 확인이 선행되어야 한다 — G5에 등재됨. 로컬 환경에서는 **모델 로드 시간**(3.1GB → VRAM, 수 초)을 컨테이너 재기동 관점의 리드타임으로 실측할 수 있다(G7).
>
> ⚠️ **3번은 "신규 축"이 아니라 "일반화"로 서술해야 정확하다.** Brownout(품질 저하)이 이미 조치 5종에 있으므로 제3의 상태는 기존 설계에 존재한다.

### 1-2. §2-A 노드 피처 — 의미 기준 공통 슬롯 + 타입 임베딩

**방향** — 노드 타입별 전용 차원 + 제로 패딩이 아니라, 의미 기준 일반화 통일.

> 전체 13~14개 노드 중 LLM 노드가 1개뿐이므로, 전용 차원은 90% 이상의 노드에서 0이 되고 이 값이 GAT attention 연산에 참여해 노이즈로 작용한다. 또한 단일 노드 분량의 신호로 전용 차원의 표현을 학습시키는 것은 비현실적이다. 따라서 의미 기준으로 일반화된 공통 슬롯을 정의하고, 학습 가능한 노드 타입 임베딩(4~8차원)을 연결한다.

| # | 공통 슬롯 | 의미 | 일반 서비스 | LLM 추론 노드 |
|---|---|---|---|---|
| f1 | 상태성 자원 포화율 | 스케일아웃으로 즉시 해소되지 않는 유계 자원의 점유율 | HikariCP active/max, Redis 풀 사용률 | KV 캐시 점유율 |
| f2 | 큐 대기율 | 처리 대기 작업의 적체 | 스레드풀 큐 깊이/용량, gRPC 동시 스트림/최대 동시성 | 대기 요청 수 / 최대 배치 크기 |
| f3 | 처리량 대비 용량비 | 현재 처리량의 포화도 | RPS / 측정 최대 용량 | 토큰 처리율 / 최대 토큰 처리율 |
| f4 | 지연 분위수(정규화) | 지연의 상대적 악화 | p95 / SLO 기준값 | TTFT/TTFT SLO, TPOT/TPOT SLO |
| f5 | 자원 사용률 | 계산 자원 점유 | CPU·메모리 사용률 | GPU 사용률·VRAM |
| f6 | 에러율 | 실패 비율 | 5xx / 전체 | 추론 실패·타임아웃 / 전체 |
| — | 노드 타입 임베딩 | 학습 가능 타입 표현 | type=service | type=llm |

**TA-GAT 유지** ✅ — 공통 슬롯은 **현재값만이 아니라** 슬라이딩 윈도우 통계량을 함께 담는다(H5 결정 보존, §4-3 ablation 성립 조건).

```
x_v(t) = [ f1..f6 의 현재값 (6) ]
       ⊕ [ f1..f6 의 윈도우 평균·slope·표준편차 (18) ]
       ⊕ [ 노드 타입 임베딩 (4~8) ]
```

기존 제약도 그대로 지킨다 — 윈도우는 라벨 창 `[t, t+Δ]`과 겹치지 않게 t 이전만, self SLO 위반 이력은 제외(§4-2 라벨 누수 방지). 모든 피처는 [0, 1] 정규화.

**부수 효과 (본문 명시 권장)**: f1에서 **DB 커넥션풀 소진과 KV 캐시 소진이 "스케일아웃으로 해소되지 않는 유계 자원의 포화"라는 동일 현상으로 통합 표현**된다. 커넥션풀 논거(D2)와 LLM 논거가 하나의 일반화된 주장으로 결합되어, 피처 설계 자체가 문제 인식을 반영한다는 근거가 된다.

### 1-3. §2-C Actuator — 5종의 LLM 노드 매핑

조치 개수는 5종 그대로 유지한다. LLM 매핑이 5종 각각에 자연스럽게 대응한다.

| # | 조치 | 일반 서비스 구현 | **LLM 노드 구현** | `apply_point` (위험 노드 = assistantservice일 때) |
|---|---|---|---|---|
| 1 | Circuit Breaker | Resilience4j 차단 + fallback | LLM 호출 우회(룰 기반·캐시 응답), 호출 루프 차단 | **frontend** (호출자) |
| 2 | Traffic Shedding | Istio rate limit, 저우선순위 드롭 | 요청 자체를 거부·큐 드롭 | **assistantservice 인그레스** |
| 3 | **Degraded-path Redirection** (개명) | read replica 우회 | **소형 모델 라우팅**, semantic cache | **assistantservice 자신** (라우팅 결정 주체) |
| 4 | K8s Scale-up | HPA 레플리카 증가 | **vLLM 용량 파라미터 조정**(`max_num_seqs`, KV 캐시 블록) — 레플리카 증설은 VRAM 8GB 제약으로 스코프 밖 | **assistantservice 자신** |
| 5 | **Brownout** | frontend가 optional 호출 생략 | **`max_tokens` 상한, RAG top-k 축소** | **assistantservice 자신** (요청 파라미터 주체) |

> ⚠️ **일반 서비스와 LLM 노드에서 `apply_point`가 달라진다.** 일반 서비스에서 Redirection·Brownout은 *호출자*에 걸리지만(cartservice 이그레스, frontend의 dimmer), LLM 노드에서는 라우팅·토큰 제한이 **서빙 노드 자신의 요청 파라미터**이므로 `apply_point = v`다. §2-C의 적용 지점 표에 **노드 타입별 분기**를 명시해야 한다 — 현재 표는 단일 사상만 담고 있다.

**개명은 1건만**: `Read Redirection` → `Degraded-path Redirection`. "DB 읽기 한정"으로 읽혀 모델 다운그레이드를 포괄하지 못하기 때문이다. 나머지 4종은 LLM 맥락에서도 이름이 그대로 통하므로 개명하지 않는다.

**Redirection과 Brownout의 경계** (예상 질문: "둘 다 품질을 낮추는데 뭐가 다른가")

| | Degraded-path Redirection | Brownout |
|---|---|---|
| 조작 대상 | **경로** — 어디서 처리하는가 | **작업량** — 얼마나 처리하는가 |
| 요청의 운명 | 온전히 처리됨 (다른 모델에서) | 응답이 삭감·절단됨 |
| 부하 처리 | 다른 곳으로 **옮김** | **없앰** |
| 원 벤치마크 대응 | Redis replica 우회 | adservice 호출 생략 |

이 구분이 성립하므로 5종의 이질성이 LLM 노드에서도 유지된다.

**Brownout 구현 유의**: `max_tokens` 상한은 decode만 줄이고 prefill은 그대로인 반면, RAG top-k 축소는 prefill을 줄인다. 효과 발현 지점이 다르므로 분리 측정하고, 기본 구현은 예비 실험으로 결정.

**구현 구조**: `Actuator` 인터페이스 → 조치별 추상 클래스 → 노드 타입별 구현체 주입(전략 패턴). 예: `DegradedPathRedirection` → `ReadReplicaRedirect` / `ModelDowngradeRedirect`.

**단일 Policy Engine 유지**: LLM 전용 엔진을 따로 두지 않는다. 분리하면 "LLM 노드에 위험이 예측되었으나 조치는 다른 노드에 적용해야 하는" 경우를 처리할 수 없다. 이 능력은 [E7](../../research/challenges.md)의 `apply_point`로 이미 형식화되어 있다.

### 1-4. §2-B 비용함수 — 행 추가만, 구조 변경 없음 ✅

```
E[비용|a] = p·[(1−mₐ)·L + Dₐ] + (1−p)·[Dₐ·Rₐ]      ← 그대로
θₐ = Dₐ·Rₐ / (mₐ·L − Dₐ(1−Rₐ))                      ← 그대로
```

LLM 조치는 §2-B 표에 행을 추가하고 `Dₐ`·`Rₐ`·`mₐ`만 정한다.

| 조치(LLM 구현) | `Dₐ` | `Rₐ` | `mₐ` |
|---|---|---|---|
| 모델 다운그레이드 (Redirection) | 중 (품질 저하) | 낮음 (즉시 원복) | 중~높음 |
| `max_tokens` 제한 (Brownout) | 중 | 낮음 | 중 |
| 추론 용량 파라미터 증대 (Scale-up) | 높음 (GPU 점유) | 높음 (재기동 리드타임) | 상황의존 |

**품질을 측정하지 않는다**: 응답 품질의 절대 측정은 LLM 평가 방법론이라는 별개 영역이며 스코프를 벗어난다. `D_downgrade`를 **운영자가 설정하는 정책 파라미터**로 두고 민감도 분석을 수행한다.

- `D_downgrade`를 변화시키며 조치 선택 분포 변화 측정
- 다운그레이드 선호 → Scale-up·차단 선호로 전환되는 **`θₐ` 교차점** 제시
- 품질을 측정하지 않고도 품질-지연 트레이드오프를 정량 제시

심사 대응: "품질을 어떻게 측정했나" → "측정하지 않았고, 운영자가 설정하는 비용 파라미터로 두고 그 영향을 분석했다."

**순환 논리 방어**: `D_downgrade`만 흔들면 "스칼라 하나 조정한 것 아닌가"로 읽힐 수 있다. 다운그레이드가 실제로 응답을 어떻게 바꾸는지 **정성적 사례 1~2개**(동일 질의에 대한 주 모델/폴백 모델 응답 대조)를 부록에 제시. 정량 평가가 아니므로 스코프 부담 없음.

### 1-5. §3 관련연구 3분할 구조

문헌이 5편 → 9편으로 늘면서 동일 비교표에 넣으면 같은 축 비교를 요구받아 방어 부담이 급증한다. 3분할로 격리한다.

**3-1. 비교 대상** — GRAF · FIRM · DeepScaler · AGQ · GraphGRU. **기존 5자 비교표 그대로 유지하며, LLM 라우팅 연구는 여기에 넣지 않는다.**

**3-2. 본 연구가 활용하는 기존 기법** (본인 제안)

- **FrugalGPT** (Chen, Zaharia, Zou, **TMLR 2024**, arXiv:2305.05176): 저렴한 모델부터 순차 질의하고 응답 신뢰도가 임계값 미달일 때만 상위 모델로 escalate하는 캐스케이드. 최상위 단일 모델 대비 최대 98% 비용 절감 보고.
- **RouteLLM** (Ong et al., UC Berkeley·Anyscale, **ICLR 2025**, arXiv:2406.18665): 인간 선호도 데이터로 학습한 라우터가 강/약 모델을 이진 선택. 강 모델 호출 비율을 크게 낮추며 품질 유지.

**두 논문 모두 판단 근거가 질의 난이도와 응답 품질이며, 시스템 부하 상태를 사용하지 않는다.** 즉 "언제 발동할 것인가"라는 축이 비어 있다.

서술 방식: *"질의를 소형 모델로 우회시켜도 상당 범위에서 품질을 유지할 수 있음은 선행연구가 실증했다. 본 연구는 이를 Degraded-path Redirection Actuator의 구현 근거로 채택하며, 라우팅 기법 자체를 기여로 주장하지 않는다."*

**3-3. 인접하나 문제 범위가 다른 연구** — 키워드가 겹쳐 심사에서 반드시 제기된다. 회피하면 "몰랐거나 숨겼다"로 읽히므로 정면 처리.

**(a) 부하 인지 LLM 라우팅 — HW-Router** (Kabir, Xue, Zheng, Lou, **DAC**, arXiv:2608.14575) ✅: 큐 길이·KV 캐시 사용률·최근 TTFT/TPOT를 경량 지연 예측기에 입력해 SLO 인지 라우팅.

| 축 | HW-Router 계열 | 본 연구 |
|---|---|---|
| 관측 범위 | 단일 LLM 서비스 내부 (GPU 간 요청 배분) | 서비스 호출 그래프 전체 |
| 시점 | 현재 상태 반응 | 예측 기반 선제 |
| 조치 공간 | 라우팅 단일 | 5종 중 선택 |
| 신뢰도 | 없음 | `θₐ` 유도 |

> venue가 DAC(하드웨어 설계 자동화)이고 대상이 서빙 플랫폼 내부 GPU 배분이라 문제 영역 분리가 명확하다.

**(b) GraphRouter** (Feng, Shen, You / UIUC, **ICLR 2025**, arXiv:2410.03834) ✅: 태스크·질의·LLM 이종 그래프에 엣지 예측으로 각 LLM 응답의 효과와 비용을 예측하는 inductive 프레임워크.

구분 논리: *"GraphRouter의 그래프는 질의–모델 적합도 관계이며 서비스 호출 토폴로지가 아니다. 본 연구의 예측 대상은 라우팅 적합도가 아니라 SLO 위반 위험의 전파다."*

> ⚠️ 저자 Jiaxuan You는 GNN 분야 저명 연구자이고 venue가 ICLR이므로 심사위원이 알고 있을 가능성이 높다. **구분 서술 누락 시 리스크가 가장 큰 문헌.**

> ✅ 위 4편 모두 원문·서지 확인 완료(2026-09-06).

### 1-6. §4-1 실험 환경

**LLM 어시스턴트 서비스 추가** — `assistantservice`. frontend가 호출하고, 상품 정보 조회를 위해 productcatalogservice를 호출한다.

배치 근거: 말단에 두면 상류 전파가 없어 연쇄 장애 예측이라는 문제 설정이 성립하지 않는다. frontend 하위 + productcatalog 상위에 두어야 **LLM 포화 → frontend 스레드풀 고갈**(상류)과 **호출 증폭 → 커넥션풀 소진**(하류)의 양방향 경로가 형성된다. recommendationservice와 병렬 위치이며 원본 호출 패턴을 따르므로 인위적이라는 지적을 피한다.

**토폴로지 (확장 구성)**

```
loadgenerator
     │
     ▼
  frontend ──┬────────────┬───────────────┬─────────────────┬──────────────┐
     │       │            │               │                 │              │
     ▼       ▼            ▼               ▼                 ▼              ▼
 adservice cartservice recommendation assistantservice  orderservice   checkoutservice
               │           │            │ (LLM)         (Spring)          │
               ▼           │            │                  │              ├─► paymentservice
         redis-cart        │            │                  ▼              ├─► shippingservice
                           ▼            ▼             PostgreSQL          ├─► emailservice
                    productcatalogservice (Go, 원본)   (HikariCP)          ├─► currencyservice
                                                                          └─► (orderservice)
```

> Spring/Postgres 노드의 **명칭·배치·API는 미확정**(B6). 위 그림의 `orderservice`는 예시이며, 확정 시 이 그림과 노드 수를 함께 고정한다.

**LLM 서빙 구성**: 2티어 캐스케이드(예: 1.5B 주 / 0.5B 폴백, FP16). VRAM 개산과 제약은 [environment.md](../../research/environment.md) §2. 절대 파라미터 규모보다 **티어 간 지연·품질 격차 비율**이 본질이므로, 본문에 *"대상은 계층 간 상대적 격차이며 절대 규모는 실험 환경 제약에 따른 선택"*임을 명시한다.

**호출 구현 — LLM 출력에 의존하지 않는다**: assistantservice의 productcatalog 호출을 LLM의 function calling 출력에 맡기지 않는다. 0.5B~1.5B급은 function calling 신뢰도가 낮아 호출 발생 자체가 불안정해지고 재현성을 훼손한다.

**결정적 파이프라인**으로 구현 — 질의 수신 → 사전 정의 규칙에 따라 카탈로그 조회 N회 → 조회 결과를 컨텍스트로 LLM 요약 → 응답. 이 구조는 (1) 호출 횟수 `N`이 실험 파라미터로 통제되어 S3 주입이 정확해지고, (2) LLM 품질 변동이 부하 패턴에 영향을 주지 않아 변수가 분리된다. 한계 섹션에 "실제 에이전트는 동적 툴콜을 수행하므로 본 구현은 증폭 현상을 통제된 형태로 재현한 것"이라고 기재.

**부하 생성 — loadgenerator 확장** **[미결정]**: 호출 비율(예: 여정의 20%), 프롬프트 소스, 프롬프트 길이 분포(S2 정의의 선행 조건), 호출 횟수 `N`의 정상 상태값·주입 증가폭을 정해야 한다. 권장 — 상품 카탈로그 실제 데이터 기반 템플릿 생성(*"{카테고리} 중에 {조건}인 상품 추천해줘"*). 재현 가능하고 조회 횟수를 템플릿으로 통제할 수 있어 S3와 자연스럽게 연결된다.

> Locust는 **맥북에어에서 원격 실행**한다(CPU 경합에 의한 측정 오염 방지, [environment.md](../../research/environment.md) §3-1).

### 1-7. §4-2 장애 시나리오 3종

각 시나리오가 서로 다른 Actuator를 최적해로 갖도록 설계해 이질적 조치 공간의 필요성을 실증한다.

| # | 시나리오 | 주입 방법 | 전파 경로 | 기대 최적 조치 | 검증 대상 |
|---|---|---|---|---|---|
| S1 | DB 커넥션풀 소진 | HikariCP `maximumPoolSize` 축소 + 슬로우 쿼리 | Spring/Postgres 노드 → 상류 | Degraded-path Redirection (replica 우회) | 자원할당 접근의 역효과 (Thundering Herd, D2) |
| S2 | LLM 노드 포화 | 긴 프롬프트 버스트 (Locust) | assistant → frontend 스레드풀 고갈 | `p_eff`가 낮을 때는 `θₐ`가 낮은 Brownout만 발동, 높아지면 Redirection·Shedding까지 열림 | 품질-지연 트레이드오프, `θₐ` 차등의 실효 |
| S3 | 호출 증폭 연쇄 | 요청당 조회 횟수 `N` 증가 | assistant → 커넥션풀 → frontend (2단) | Circuit Breaker 또는 Shedding | **위상 인지 필요성 — `apply_point` ≠ 위험 노드** |

**S2가 LLM 확장의 핵심 실증이다**: LLM 노드 고유의 포화 메커니즘(KV 캐시·토큰 길이)과 품질 레버가 함께 동작하는 유일한 시나리오다. S1은 LLM 없이도 성립하고, S3의 호출 증폭도 원리적으로는 일반 서비스로 재현 가능하다. **S2를 컷하면 확장의 실증 근거가 대부분 사라지므로 컷 우선순위 하위에 둔다**(§3).

**S3의 전략적 중요성**: 위험이 예측되는 노드(Spring/Postgres)와 조치를 적용할 노드(assistantservice)가 다르다. 노드 단위 시계열 모델이나 단일 서비스 내부 최적화로는 원리적으로 불가능한 조치 선택이며, **그래프 전체를 보는 단일 Policy Engine이어야 하는 이유**를 실증한다. 3-3(a)의 부하 인지 라우팅 연구군이 다룰 수 없는 영역이기도 하다. 조치 지점 선택 로직은 [E7](../../research/challenges.md)의 `apply_point`로 이미 형식화되어 있으므로 S3는 그 위에서 바로 성립한다.

### 1-8. §4-3 Baseline 추가

기존 6종에 더한다.

| Baseline | 설명 | 목적 |
|---|---|---|
| **신뢰도 미사용 ablation** | 동일 GNN 예측 + `θₐ` 게이팅 없이 `p̄` argmin | **신뢰도 축 단독 기여 분리** |
| **vanilla 구성** | LLM 노드 없는 원본 구성 | **시나리오 커버리지 대조** — 아래 참조 |

**vanilla 구성의 목적은 성능 비교가 아니다**: vanilla에는 LLM 타입 노드가 없어 타입 임베딩 학습이 불완전하므로, 두 구성에 별도 모델을 학습해 성능을 비교하면 "LLM 노드의 영향"이 아니라 "서로 다른 두 모델의 차이"를 보게 된다. 대신 **확장 구성에서 학습한 단일 모델**을 두 구성에 적용하고, *"S2가 vanilla에서는 재현조차 되지 않는다"*를 보이는 **커버리지 대조**로 쓴다. 이것이 우려 14("유행 편승 아닌가")에 대한 직접적 답이다.

> 신뢰도 구간별 대응이 유일한 신규 축이므로, 제거 시 성능 저하를 정량으로 보이는 것이 기여 입증의 핵심이다. 컷라인에서 **가장 마지막에 잘라야 할 실험**.

기존 **7~10개월**에 **약 1~1.5개월 추가** 예상(Spring/Postgres 서비스는 병행 가능으로 합계 불변).

**컷 우선순위 삽입** — 기존 목록에 아래를 배치한다.

1. Train Ticket 서브셋 보조 실험
2. FIRM류 baseline
3. 부하 스케일업 실험
4. **vanilla 커버리지 대조** ← 신규
5. Actuator 5종 → 3종(Redirection + Circuit Breaker + Brownout)
6. **LLM 시나리오 S2** ← 신규. **여기까지 오면 LLM 확장 자체를 재고할 것**

> **절대 컷하지 않을 항목**: 신뢰도 미사용 ablation.
>
> ⚠️ 5번 주의: 조치를 줄일 경우 남기는 것들이 **서로 다른 성격**(경로 변경 / 차단 / 품질 저하)이어야 최소한의 이질성을 보인다.
>
> ⚠️ 6번 주의: S2는 LLM 확장의 핵심 실증이다(§1-7). 이것을 컷해야 할 상황이면 확장을 유지할 실익이 없으므로, 컷 대신 **확장 철회**를 검토하는 편이 낫다.
