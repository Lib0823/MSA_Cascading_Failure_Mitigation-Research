# 연구 과정의 문제 해결 기록 (Challenges)

> 프로포절 준비 과정에서 겪은 시행착오, 팩트체크, 기술적 의사결정을 기록한다. 논문 본문에는 모두 담기 어려운 근거와 검토 과정을 남기는 공간이다. 각 항목은 원본 의사결정 로그를 "문제 → 확인/분석 → 결론" 형식으로 재구성한 것이다.

> ⚠️ **2026-09-24 범위 재설계**: 가용 시간 실측(주 4시간, 총 400~500h)이 기존 계획(1,000~1,800h)과 6~9배 어긋나 범위를 재설계했다. 아래 항목 중 일부는 **결론이 변경되었으며, 변경된 항목에는 그 자리에 정정 표시를 달았다.** 재설계 전체 경위·대안 검토·미채택 안은 [0923_scope_redesign_proposal.md](../docs/feedback/0923_scope_redesign_proposal.md), 신규 결정은 §J에 있다.

## A. 실험 환경 및 인프라

### A1. AWS 프리티어 정책 변경
- **문제**: "신규 계정을 만들어 12개월 무료로 쓴다"는 기존 전제가 여전히 유효한지 확인 필요.
- **확인**: 2025년 7월 15일 이후 신규 계정은 12개월 무료가 아니라 200달러/6개월 크레딧 방식으로 변경됨. 레거시(그 이전 생성) 계정만 12개월 혜택 유지.
- **결론**: "신규 계정으로 12개월 무료 사용" 전제는 틀림. 클라우드 사용 시 변경사항을 반영해야 함.

### A2. 로컬 vs 클라우드 — 메인 실험 환경
- **문제**: 메인 실험 환경을 로컬로 할지 클라우드로 할지 결정 필요.
- **분석**: (1) 예산 리스크(크레딧 소진), (2) 재현성(클라우드는 통제 안 되는 변수 증가), (3) 시간 대비 가치(인프라 학습 시간이 핵심 기여와 무관).
- **결론**: 메인 실험은 **로컬 전용 데스크톱**(A3)에서 수행한다. 클라우드는 사용하지 않는다 — 전용 장비를 갖추면 예산·재현성·학습시간 세 축이 모두 로컬에 유리하다. 보조 실험(Train Ticket 서브셋)의 VPS 대여 필요 여부는 서브셋 규모 확정 후 판단한다([environment.md](environment.md) §6).

### A3. 실험 장비 — 전용 데스크톱 사양 확정
- **문제**: K8s 클러스터(Online Boutique + Spring/Postgres + LLM 노드 + Istio 사이드카 = 25+ 컨테이너)와 장애주입·트래픽 생성·LLM 서빙을 감당할 장비 사양을 정해야 한다.
- **분석**: GNN/LSTM 모델 자체는 그래프가 작고(13~14노드) 데이터 볼륨도 작아 연산량이 가볍다. **실제 부담은 모델 학습이 아니라 클러스터 구동 쪽**이며, 세 가지가 결정 요소다 — (1) 컨테이너 25개+를 동시에 띄울 시스템 메모리, (2) LLM 2티어 서빙을 담을 VRAM, (3) 서비스·사이드카·부하생성기가 공유할 CPU 코어.
- **결론**: 전용 데스크톱을 구성한다 — **Ryzen 5 7500F(6C/12T) / DDR5 32GB / RTX 5060 Ti 8GB / 1TB NVMe**. Linux 네이티브 + K3s 단일 노드. 사양 근거와 자원 배분 계획은 [environment.md](environment.md) §1·§2.
  - **RAM 32GB·VRAM 8GB는 고정 제약**으로 두고 설계를 여기 맞춘다(증설 비용·불가).
  - VRAM 8GB에서 LLM Capacity Scale-up은 레플리카 증설이 아니라 **vLLM 용량 파라미터 조정**으로 구현하고 한계로 명시한다.
  - GPU를 로컬에 확보하므로 **GPU 클라우드·에뮬레이션은 사용하지 않는다.** 학습 데이터는 실측으로 수집한다.
- **이 사양의 핵심 제약은 CPU다**: 6코어를 서비스·사이드카·Prometheus·JVM·vLLM 호스트 프로세스가 공유한다. 호스트 CPU 포화가 전역 지연 증가를 만들면 §4-2의 "전파에 기인한 위반"과 구분되지 않아 **라벨이 오염**된다 — 상세와 완화책은 A5.

> 🔄 **정정 (2026-09-24, J1·J7)** — 위 세 하위 결론 중 둘이 변경되었다.
> | 종전 | 변경 후 |
> |---|---|
> | K3s 단일 노드 | **표준 K8s 배포판(kubeadm, 폴백 minikube)** — baseline이 HPA인 이상 현장과 같은 컨트롤 플레인 위에서 동작해야 한다 |
> | RAM·VRAM은 고정 제약 | **전제 해제** — 증설·대여로 해소 가능한 탄력적 제약. 구속 제약은 시간이다. **예외는 CPU 코어 수**(측정 타당성 직결) |
> | LLM Scale-up = vLLM 용량 파라미터 조정 | **Scale-up을 아예 하지 않는다** — LLM 노드는 *"Scale-out이 불가능한 노드"* 를 구현하는 것이 설계 목적이 되었다. 남는 레버는 Brownout |
> | 컨테이너 25개+ (OB 11 + 사이드카 11 + …) | **자작 Spring 6~7개** — Istio·Chaos Mesh·Online Boutique 제거로 CPU·메모리 압력이 크게 감소. 단 표준 컨트롤 플레인이 idle 0.3~0.5코어를 상시 점유 |

### A4. 트래픽 생성 도구
- **문제**: Chaos Mesh/Istio만으로 실험에 필요한 트래픽까지 만들 수 있는지 확인 필요.
- **확인**: Chaos Mesh/Istio 장애주입 ≠ 트래픽 생성. Locust가 백그라운드 트래픽+주기적 버스트를 재현하는 방식으로 실제 연구에서 쓰인 사례 확인.
- **결론**: Locust/k6로 트래픽 프로파일 생성 + Istio/Chaos Mesh로 장애주입, 2-레이어 조합으로 확정([docs/proposal.md](../docs/proposal.md) §4-1). 구체적 트래픽 프로파일 파라미터는 실험 설계([docs/proposal.md](../docs/proposal.md) §4-5)에서 상세화(구 G3, 실험 이관).

### A5. CPU 경합에 의한 라벨 오염 리스크 — 실험 프로토콜 확정
- **문제**: 단일 머신 6코어(A3)를 Online Boutique 11개 + Envoy 사이드카 11개 + Prometheus + JVM + vLLM 호스트 프로세스가 공유한다. 여기에 부하생성기까지 같은 머신에서 돌리면 CPU 경합이 발생한다.
- **왜 심각한가**: 호스트 CPU가 포화하면 **모든 서비스의 지연이 동시에 증가**한다. 이는 [proposal.md](../docs/proposal.md) §4-2가 정의한 "이웃 서비스의 선행 열화에 뒤따르는 위반"(전파성 조건)과 **시간 패턴이 유사해 보이지만 전파가 아니다.** 자동 역라벨링이 이를 positive로 잡으면 가짜 양성이 학습 데이터에 섞이고, GNN이 위상 전파가 아니라 **호스트 부하**를 학습하게 되어 LSTM 대비 우위라는 핵심 주장의 근거가 흐려진다.
- **발견이 어렵다는 점이 특히 위험하다**: 메모리 부족은 OOM으로 즉시 드러나지만 CPU 경합은 조용히 라벨만 오염시킨다. 결과가 그럴듯하게 나오므로 대규모 수집을 마친 뒤에야 드러날 수 있고, 그러면 전체 재수집이 필요하다.
- **결론 — 완화 3종을 실험 프로토콜로 확정** ([environment.md](environment.md) §4):
  1. **부하 생성기 분리** — Locust를 별도 머신에서 원격 실행해 대상 시스템과 CPU를 공유하지 않게 한다.
  2. **CPU 헤드룸 캘리브레이션** — 본 실험 전 부하를 단계적으로 올리며 호스트 CPU를 측정하고, 실험 부하 범위를 포화 이전 구간으로 제한한다.
  3. **에피소드 유효성 기준** — 에피소드마다 호스트 CPU·메모리를 기록하고 임계 초과 구간은 라벨링에서 제외하거나 에피소드를 폐기한다.
- **부수 효과**: 3번을 프로토콜에 명시하면 심사에서 *"측정 환경이 결과를 오염시키지 않았음을 어떻게 보장하나"*에 대한 직접적 답이 된다. [proposal.md](../docs/proposal.md) §4-1·§4-4에 반영.
- **잔여**: 호스트 CPU 임계값의 구체 수치는 캘리브레이션 후 확정.

> 🔄 **보강 (2026-09-24, J7)** — 이 항목의 진단은 유효하며 오히려 중요해졌다.
> - **개선된 부분**: Envoy 사이드카 11개와 Chaos Mesh가 제거되어 CPU 압력이 크게 줄었다.
> - **악화된 부분**: K3s 통합 바이너리 → 표준 컨트롤 플레인(apiserver·etcd·controller-manager·scheduler 분리)으로 **idle 상시 점유가 0.3~0.5코어 늘었다.** 헤드룸 계산에서 이를 먼저 제해야 한다.
> - **완화책 4번 추가**: cpuset으로 컨트롤 플레인·Prometheus를 특정 코어에 고정해 피험 서비스와 분리한다. 그래도 부족하면 **코어를 증설한다** — 자원 투자가 실제로 값을 하는 유일한 지점이며, RAM보다 우선순위가 높다.

## B. 벤치마크 규모 및 선정

### B1. 벤치마크 규모(11개) — "너무 작지 않은가?" 팩트체크
- **문제**: Online Boutique(11~12개 서비스) 규모가 연구 목적에 충분한지 우려.
- **확인**: Online Boutique 11~12개, Sock Shop 11~15개, Train Ticket 40~64개(가장 큰 벤치마크). 한 선행연구는 이런 벤치마크들이 실제 프로덕션보다 몇 자릿수 작다고 명시하며 100만 서비스 규모의 시뮬레이션 벤치마크를 별도 제작한 사례도 있음.
- **우려 사항**: (1) 실무 일반화 가능성, (2) 그래프가 작으면 GNN vs LSTM 비교에서 GNN의 우위가 약하게 나올 위험 — 핵심 논거(그래프 구조가 필요하다)를 스스로 약화시킬 수 있음.

### B2. Option A(Train Ticket 전체 전환) 타당성 검토
- **문제**: 더 큰 벤치마크(Train Ticket)로 전환하는 것이 타당한지 검토.
- **확인**: Train Ticket 40~64개 서비스, 서비스당 0.2~1 CPU/200MB~1GB RAM 요구. 선행 연구자 대부분 5노드 클러스터(80코어/160GB RAM 등) 사용. 단일 머신 32GB로는 전체 배포가 불가능하다(A3).
- **결론**: (1) 보조 실험이므로 투자 대비 효과를 먼저 검토, (2) 전체 64개가 아닌 대표 워크플로우 관련 서브셋(15~25개)으로 축소 가능, (3) 필요 시 AWS 대신 시간단위 과금 VPS(Hetzner/DigitalOcean/Vultr)를 며칠만 대여해 데이터만 뽑고 종료하는 방식 권고.

### B3. Vast.ai 및 벤치마크 재검토
- **문제**: 클라우드 GPU 마켓플레이스(Vast.ai) 활용 가능성 및 최종 메인 벤치마크 확정 필요.
- **확인**: Vast.ai는 GPU 마켓플레이스로 K8s 클러스터 호스팅(CPU/RAM 중심 니즈)에는 맞지 않음. 필요한 것은 일반 VPS(Hetzner/DigitalOcean/Vultr). 가장 직접적인 비교 대상인 GRAF도 메인 실험에서 Online Boutique와 Social Network 두 벤치마크를 사용함. Train Ticket은 주로 RCA 계열 연구(BARO, RCAEval, TORAI)에서 사용되며 대형 멀티노드 클러스터가 필요.
- **결론**: 메인 실험은 Online Boutique로 확정. GRAF와 동일 벤치마크 사용이 "직접 비교 가능성 확보"라는 근거가 되어 오히려 방어력이 강해짐. Train Ticket은 보조 실험으로만 남김.

### B4. GRAF의 벤치마크 규모 재확인
- **문제**: GRAF가 실제로 어느 규모까지 검증했는지 확인 필요.
- **확인**: GRAF 메인 실험은 Online Boutique와 Social Network 두 벤치마크 기준(원문 확인). "large-scale experiment"(§V-E)는 대규모 배포 환경에서의 확장성 검증으로, CPU 자원 21.6%, 메모리 자원 25.4% 절감을 달성했다고 명시(IEEE/ACM ToN 2024판 Abstract 및 §V-E). 다만 이 확장 실험이 서비스 종류 확장인지 부하/레플리카 규모 확장인지 세부 조건까지는 확인 안 됨.
- **결론**: 11개 위상 유지가 이 분야의 표준적 선택이라는 근거 확보. 저비용으로 "부하 스케일업 실험"을 추가하는 방안 제시.

### B5. GRAF·FIRM·AGQ 원문 재확인 — 실제 GNN 입력 그래프 규모
- **문제**: GRAF·FIRM·AGQ가 실제로 GNN 입력에 사용한 그래프 규모가 얼마나 되는지 정밀 확인 필요.
- **확인(GRAF, 2021 CoNEXT 원문 + 2024 ToN 확장판)**: GRAF는 2021년부터 Online Boutique와 Social Network 두 벤치마크를 함께 사용했으며 2024년 확장판에서 새로 추가된 것이 아님. 다만 GNN 입력으로 실제 사용한 그래프는 벤치마크 전체가 아니라 특정 요청 체인(critical chain)만 잘라낸 서브그래프: Online Boutique는 6개 노드(MS1~MS6, 카트 페이지 체인), Social Network는 10개 노드(MS1~MS10, post-compose 체인). 즉 본 연구가 채택한 11개 노드(Online Boutique 전체 위상)는 GRAF의 실제 GNN 입력 규모보다 오히려 크다.
- **확인(FIRM)**: GNN을 사용하지 않고 SVM 기반 critical path 추출 + RL(actor-critic)로 저수준 자원(CPU/Mem/LLC/IO/Net) 한도 재할당을 선택하는 구조(조치 공간 상세는 D14). 그래프 임베딩 학습이 없어 노드 수 제약이 없고, DeathStarBench(Social Network 36, Media Service 38, Hotel Reservation 15) + Train-Ticket(41) 벤치마크의 전체 서비스 그래프를 그대로 사용.
- **확인(AGQ)**: 메인 비교 실험(Table 3, HAB/MMN/AWS/SLO 등 실제 경쟁 베이스라인과 신뢰구간까지 명시한 핵심 결과)은 Sock Shop(~13개 노드) 규모에서 수행. "수백 개 노드" 규모의 LinkedIn 실험은 메인 베이스라인이 아닌 DCRNN·T-GCN 두 GNN 모델과만 비교한 보조 실험이며, 실제 LinkedIn 데이터가 아니라 공개 아키텍처 설명을 참고해 자체 시뮬레이션한 비공개·비재현 환경.
- **결론**: GNN 기반 선행연구(GRAF, AGQ)의 실질적 핵심 검증 규모는 모두 본 연구의 11개 노드와 같은 자릿수(6~13개)이며, 본 연구가 유독 작은 것이 아님. "AGQ는 대규모에서 검증했다"는 인상은 메인 결과가 아닌 비재현 보조 실험에서 비롯된 것이라 근거로서의 무게가 약함. [docs/proposal.md](../docs/proposal.md) §3, 우려 1에 반영.

### B6. Spring/PostgreSQL 서비스 추가 — 스코프 정합 + 상태성 병목 이중화
- **문제**: 세 가지가 걸려 있었다. **당초 이 항목의 출발점이었던 "Online Boutique에 상태성 병목을 실증할 대상이 없다"는 주장은 사실이 아니다** — §4-5에 cartservice→Redis 경로가 주입 방법까지 명시되어 있었다. 아래가 실제 문제다.
  0. **Read Redirection의 구현 경로 미검증 (1순위 근거)**: [timeline.md](timeline.md) 컷 우선순위상 최후까지 남기는 Actuator 2종은 CB + Read Redirection이다. 그런데 Read Redirection의 유일한 실증 대상이 "Redis primary/replica + Envoy `read_policy`"였고, **Envoy 공식 문서 확인 결과 `read_policy`는 "currently supported for Redis Cluster"로 명시**되어 있다. Online Boutique의 `redis-cart`는 단일 인스턴스라, 이 경로를 쓰려면 `redis-cart`를 Cluster 모드로 전환하고 `cartservice`의 Redis 클라이언트도 cluster-aware로 바꿔야 한다 — **즉 원본 서비스 변형이 필요하다.** 이는 (a) 방식이 지키려던 "원본 보존"(우려 1 방어의 토대)과 정면으로 충돌한다. 즉 최소 실증 세트의 절반이, 원본을 건드려야만 성립하는 경로에 걸려 있었다. (하드웨어 부담이 아니라 **벤치마크 충실도**가 쟁점이다.)
  1. **스코프 불일치**: [docs/proposal.md](../docs/proposal.md) §5는 "Thread-per-request 모델 한정 / Java·Spring 실증 한정"을 선언하고 §4-4는 평가지표에 "톰캣 스레드 덤프"를 넣었는데, **Online Boutique 원본에 이를 충족하는 서비스가 없다.** cartservice는 C#/.NET이고, 유일한 Java 서비스인 adservice는 gRPC라 서블릿 컨테이너가 아니다. 즉 현재 구성으로는 선언한 스코프와 지표를 실증할 수 없었다.
  2. **상태성 병목 단일 지점**: 핵심 차별점(D2, Thundering Herd)의 실증 지점이 cartservice→Redis 하나뿐이라, 그 시나리오가 실패하면 대체재가 없다.
- **확인**: Online Boutique 원본 서비스 구성 기준(frontend·checkoutservice·productcatalogservice·shippingservice는 Go, recommendationservice·emailservice는 Python, currencyservice·paymentservice는 Node.js, cartservice는 C#, adservice는 Java/gRPC). **본 확인은 벤치마크 서비스 목록 기준이며, 실증 착수 전 저장소에서 재확인 대상.**
- **의사결정 과정**: 도입 방식 2안 비교.
  - **(a) 신규 서비스 추가** — Spring + HikariCP + Postgres 서비스를 별도 노드로 붙인다. 원본 미변형, 구현 단순, §5 스코프 충족. 단 fan-in이 낮아 전파 경로가 짧다.
  - (b) productcatalogservice 교체 — Go 구현을 Spring+MyBatis+Postgres로 교체. fan-in 3(frontend·checkout·recommendation)으로 다중 전파가 생기나, 원본 변형 + Go→JVM 지연 특성 변화 + 벤치마크 대표성 지적 소지.
- **결론**: **(a) 신규 서비스 추가로 확정.** 판단 기준은 "fan-in 크기"가 아니라 **"Read Redirection의 구현 경로를 확보하는가"**이며, 이 기준에서 (a)로 충분하다. Postgres primary/replica는 **어차피 새로 붙이는 노드**라 복제 구성이 원본 충실도를 전혀 훼손하지 않고, 스트리밍 복제 + 읽기 라우팅이 표준 구성이라 구현 부담도 낮다. 조치 적용 지점 문제는 E7에서 별도로 다뤄지므로 (b)의 추가 이득이 크지 않은 반면, 원본 변형 비용(우려 1의 "GRAF와 동일 벤치마크" 논거 약화)은 실재한다. 원본 서비스와 호출 관계를 보존하므로 원본 위상이 부분그래프로 남아 우려 1 방어가 유지된다. [docs/proposal.md](../docs/proposal.md) §4-1·§4-5·§5·우려 1에 반영.
- **부수 효과**: Redis 경로는 폐기하지 않는다. 1차 상태성 병목(§4-5)으로 그대로 유지하고, Read Redirection만 Postgres를 1차 대상으로 옮긴다. Redis Cluster 구성이 가능해지면 Redis 경로도 보조 실증으로 살릴 수 있다.
- **잔여(미확정)**: 추가 서비스의 **배치(어느 서비스가 호출하는가)·명칭·API 미정.** 배치에 따라 fan-in과 전파 경로가 달라지므로 실험 환경 구축 착수 전 확정 필요. 확정 후 노드 수 표기(현재 "13~14개", LLM 노드 포함 — B7)를 최종값으로 고정한다.

### B7. 벤치마크 확장 — LLM 추론 서비스(assistantservice) 추가 [채택]
- **문제**: 대상 시스템을 일반 서비스만으로 둘지, LLM 추론 노드를 포함한 혼합 그래프로 둘지 결정.
- **의사결정 과정**: 3안 비교. (A) LLM 에이전트를 Policy Engine으로 사용 — 비결정적 출력이라 반복 실험 기반 정량 비교·재현성 확보 불가, "GNN과 LLM을 왜 둘 다 쓰나"의 설계 정당화 곤란으로 **기각**. (사후 확인: 이 방향을 실제로 수행한 ORACL조차 LLM 결정을 행동 공간 가지치기와 정책 제약으로 감쌌고, MicroRemed 벤치마크는 단독 LLM의 remediation 정확도가 최저 난이도에서도 50% 미만임을 보고한다 — D21.) (B) LLM 서빙 인프라 전용 프레임워크로 전면 전환 — 연구 분야가 LLM serving systems(vLLM·SGLang 계열)로 이동해 기존 확정 사항 대부분(벤치마크·비교 논문 5편·커넥션풀 논거·GAT 근거)이 무효화되고 심사 요구 수준이 KCI 목표 대비 과도해져 **기각**. (C) 혼합 그래프(일반 서비스 + LLM 노드 1개) — **채택**.
- **결론**: `assistantservice` 1개를 추가한다. frontend 하위 + productcatalog 상위에 배치해 상류(스레드풀 고갈)·하류(커넥션풀 소진) 양방향 전파 경로를 만든다. 원본 서비스와 호출 관계는 보존하므로 원본 위상이 부분그래프로 남아 우려 1 방어가 유지된다.
- **주장 범위의 한정 (중요)**: 세 축은 **LLM 없이도 성립한다.** "LLM이 있어야 세 축이 필연이 된다"고 주장하지 않는다 — 심사에서 *"LLM 없이도 필요하다면서 왜 넣었나"*로 되돌아온다. 정확한 위치는 **"세 축의 적용 범위가 동질 워크로드에 한정되지 않음을 보이는 검증 대상"**이다. [docs/proposal.md](../docs/proposal.md) §1·§4-1에 반영.
- **잔여(미확정)**: assistantservice 호출 비율, 프롬프트 소스·길이 분포, 카탈로그 조회 횟수 `N`의 정상 상태값.

## C. 스코프 및 일정

### C1. 스코프(Actuator/장애주입) — "끼워넣기만 하면 되는가?"
- **문제**: GNN은 사전학습 모델, Actuator 5종은 대부분 기성 라이브러리(단 Brownout은 앱 계측 필요), 장애주입은 전용 툴이라 스코프를 축소할 수 있는 것 아닌지 검토.
- **확인**: Resilience4j/Spring Cloud Gateway 등 라이브러리 자체는 기성품이지만, "GNN 출력 → Policy Engine → Actuator 트리거"를 잇는 통합 로직은 직접 구현해야 함. Chaos Mesh/Istio는 장애주입 전용이고 트래픽 생성은 별도 도구(Locust/k6/JMeter/Gatling) 필요.
- **결론**: GNN 레이어 구현·Actuator 개별 세부튜닝은 가벼워지나, Policy Engine 통합 로직·실험 파이프라인 구축은 여전히 무거움. 스코프는 유지하되 우선순위 컷라인을 사전 설정([timeline.md](timeline.md) 참고).

### C2. 일정 타당성 (1학기 종료 시점부터 시작)
- **문제**: 남은 기간 안에 연구를 완료할 수 있는지 검토.
- **확인**: 특수대학원 통상 구조상 남은 시간 약 3~4학기(1~1.5년), 실질 작업 가능 시간은 7~10개월로 추정.
- **결론**: 불가능하진 않으나 타이트함. 우선순위 컷라인 사전 설정 필요([timeline.md](timeline.md) 참고).

### C3. 출판 목표 로드맵 — KCI급 1차 목표
- **문제**: GRAF-FIRM-AGQ 세 축 비교 구도에서 본 연구가 실질적 가치가 있는지, 목표 venue 수준이 어디가 현실적인지 검토.
- **확인**: (작성 당시) 오픈 이슈 4개(신뢰도 산출/비용함수/추론레이턴시/트래픽파라미터) 중 신뢰도 산출만 해결된 상태였으나, 이후 비용함수(G1)·추론레이턴시(G2)도 해결되고 트래픽파라미터(G3)는 실험 설계로 이관되어 **현재 심사 대비 오픈 이슈는 없음**. 벤치마크 규모·시간 제약(7~10개월 겸업)은 스스로 인지하고 있음. GRAF·FIRM은 정규 박사과정+산업협업 리소스로 나온 결과물이라 동일 규모 실증은 애초 스코프 밖.
- **결론**: KCI 등재지를 1차 목표로 설정. 실증 결과가 강하면(특히 커넥션풀 시나리오 실증 성공 시) SCIE 하위권 확장 투고를 후속 목표로 고려.

### C4. LLM 확장에 따른 스코프 재산정
- **추가 작업**: assistantservice 구현 + vLLM 서빙 환경(3~4주, Blackwell sm_120 환경 구축 1~2일 별도), LLM 노드 메트릭 수집 파이프라인(2주, GNN 파이프라인과 통합). 관련연구 추가 검토는 완료.
- **일정 영향**: 기존 7~10개월에 **약 1~1.5개월 추가**. Spring/Postgres 서비스(B6)는 병행 가능으로 합계 불변.
- **컷라인 사전 확정**: vanilla 커버리지 대조 → Actuator 5종→3종 → **S2** 순으로 자른다. 단 S2는 LLM 확장의 유일한 고유 실증이므로(S1·S3는 LLM 없이도 성립), **S2를 컷해야 할 상황이면 컷이 아니라 확장 철회를 검토**한다.
- **결론**: 스코프 확장을 수용하되 위 컷라인을 사전 확정. [timeline.md](timeline.md)에 반영.

## D. 관련연구 비교 및 포지셔닝

### D1. 관련연구 팩트체크 — "GNN 기반 선제 대응 연구가 있는가?"
- **문제**: "기존 연구는 다 사후 대응"이라는 전제가 맞는지 확인 필요.
- **확인**: GRAF(KAIST, CoNEXT'21/ToN'24), Graph-PHPA(LSTM+GNN, 2022), STAAF, Madu(불확실성 인지 선제 오토스케일러), HGraphScale 등 GNN 기반 선제적 자원관리 연구가 이미 다수 존재. "완전히 사후대응"이라는 전제는 틀림.
- **결론**: 차별점을 "GNN 선제대응"이 아니라 더 좁게 재정의해야 함 → (1) 예측 대상(전파경로 vs 지연/CPU), (2) 조치 공간(이질적 vs 스칼라), (3) 신뢰도의 역할(구간별 대응 vs 단순 불확실성 반영)의 3축으로 차별점 재구성.

### D2. 커넥션풀 소진 시나리오 — 차별점 재확인
- **문제**: 자원할당/오토스케일링만 늘리면 상태성 리소스(DB 커넥션풀 등) 병목에서 역효과가 날 수 있다는 논리가 GRAF류와의 차별점으로 유효한지 확인.
- **결론**: 원본 §1에 이미 있던 논거이며, GRAF류(자원할당 중심 접근)와의 가장 구체적이고 방어하기 쉬운 차별점으로 확정. [docs/proposal.md](../docs/proposal.md) §4-3에 GRAF류 baseline을 추가해 이 시나리오에서 실증하기로 함.

### D3. GRAF 신뢰도 검증
- **확인**: KAIST INA Lab(지도교수 Dongsu Han), ACM CoNEXT 2021(승인율 22.7%), IEEE/ACM Transactions on Networking 2024 확장 게재, Toyota와의 산업 협업 포함. 저자 Jinwoo Park은 이 연구로 KAIST 박사학위 취득. 연구실이 관련 주제(PHPA/APNet 2021 등)를 계보로 이어가고 있음.
- **결론**: 신빙성 있는 최상위권 연구로 확인, 관련연구 핵심 비교 대상으로 계속 활용.

### D4. "GRAF가 제일 적합한 선행연구인가?" — FIRM 발견
- **문제**: GRAF 하나만으로 관련연구 비교가 충분한지 검토.
- **확인**: FIRM(USENIX OSDI 2020, UIUC: Qiu, Banerjee, Jha, Kalbarczyk, Iyer) 발견. SVM 기반 감지/localize + RL(DDPG) 기반으로 저수준 자원 한도(CPU/Mem/LLC/IO/Net)를 재할당하는 조치를 선택하나 그래프 구조는 반영하지 않음. OSDI는 시스템 분야 최상위 학회(SOSP와 함께 최상위 2대 학회). (당초 '브라운아웃 포함 이질적 조치'로 기재했으나, 원문 재확인 결과 조치 공간은 전부 자원 프로비저닝에 한정됨 — D14 참고.)
- **결론**: GRAF 하나만으로는 부족함. GRAF(위상 인지, 조치는 자원할당 한정)와 FIRM(학습 기반 적응적 조치 선택, 단 조치는 자원 프로비저닝 한정, 위상 미반영)이 서로 다른 축을 커버하며, 본 연구는 이 둘의 교집합 + 신뢰도 구간별 대응(신규)에 위치. 관련연구는 두 논문을 나란히 비교표로 제시하기로 결정. §4-3 baseline에 FIRM류도 선택적으로 추가.

### D5. AGQ 검토 — 학회 위상/관련도 분리 평가
- **확인**: AGQ(Future Generation Computer Systems, Elsevier Q1, 2026)는 STGNN(dense-connectivity)+Q-learning 결합. 학회 위상은 GRAF/FIRM보다 한 단계 아래(OSDI/CoNEXT 같은 top-tier 컨퍼런스 대비)나, 관련도(예측+학습기반 조치 동시 보유)는 셋 중 가장 높아 심사 방어 시급성이 가장 큼. "AGQ"는 별도 배포 소프트웨어 프레임워크가 아니라 논문 내 제안 방법론에 붙인 이름(GRAF·FIRM과 동일한 성격).
- **결론**: 조치 공간이 스케일링 단일 축에 머물고 신뢰도 구간별 대응이 없다는 점으로 차별화. 비교표에 3번째 행으로 정식 추가.

### D6. AGQ 논문 원문 확인 — 실제 사용 모델 팩트체크
- **문제**: "GAT가 이웃 중요도 불균일 상황에 적합하다"는 GAT 채택 논거가 정확한 문헌 근거에 기반하는지 재확인.
- **확인**: AGQ는 GAT가 아니라 ChebConv(스펙트럴 그래프 컨볼루션) 기반 STGNN + temporal attention + Q-learning을 사용. GRAF는 GAT/GCN이 아니라 자체 설계 MPNN(이웃 균등 합산)을 사용. FIRM은 GNN을 아예 사용하지 않음(SVM+RL).
- **결론**: 이전에 "GAT가 이웃 중요도 불균일 상황에 적합하다"는 논거를 선행연구 실증이 아니라 일반 문헌 근거로 정정. 동시에 "GRAF·AGQ 모두 attention 기반 차등 집계를 쓰지 않았다"는 더 정밀한 문헌적 공백을 GAT 채택 근거로 재정립.

### D7. GraphGRU 발견 및 검증
- **문제**: AGQ의 참고문헌에서 발견한 GraphGRU가 관련연구 비교표에 추가할 만한 가치가 있는지 검토.
- **확인**: AGQ의 참고문헌(He et al. [33])에서 발견. "GraphGRU: A Graph Neural Network Model for Resource Prediction in Microservice Cluster", IEEE ICPADS 2022(2023 게재), 중국과학원 선전첨단기술연구원. GAT 기반으로 마이크로서비스 클러스터 자원 사용량을 예측하며, DTW 알고리즘으로 동적 그래프 구조를 구성. 알리바바 실제 프로덕션 데이터셋 검증, 기존 딥러닝 대비 최대 48.27% 정확도 개선.
- **결론**: 마이크로서비스+GAT 조합을 이미 검증한 가장 직접적인 선행연구로, 관련도 최상위(GraphGRU≈AGQ 공동 1순위)로 재평가. 다만 DTW 기반 동적 그래프(시계열 유사도 기반)이고 예측에서 그쳐(조치·신뢰도 축 없음) 차별점은 유지됨. 비교표에 4번째 행으로 정식 추가.

### D8. FIRM의 참고문헌(MicroRCA, Microscope) — 활용 여부 검토 후 미채택
- **문제**: FIRM 관련연구에 인용된 MicroRCA·Microscope를 "위상 정보 미사용의 한계" 논거로 활용할 수 있는지 검토.
- **확인**: 두 논문 모두 서비스 인과 그래프(causal graph)를 이미 구성해서 사용하며, 다만 신경망이 아니라 그래프 순회/랭킹 알고리즘으로 처리하는 방식. "위상 정보 자체를 안 쓴다"는 논거로 사용하면 부정확한 주장이 됨(FIRM 본체와는 다른 성격).
- **결론**: 정식 비교표·본문에는 포함하지 않기로 결정. 서론 맥락 문장으로 살짝 언급하는 방안도 고려했으나, 비용 대비 효과가 낮고(설득력 기여 미미) 즉석 질문 리스크만 늘어난다고 판단하여 완전히 제외. FIRM 본체만 유지.

### D9. PECD 논문 검토 후 미채택
- **확인**: "Proactive Elastic Circuit Deconstructor(PECD)", International Journal of Advanced Signal and Image Sciences(IJASIS) 게재. ML 기반 이상예측 + 선제적 Circuit Breaker 결합 아이디어이나, 저널 신뢰도가 낮고(색인 불명확, 약탈적 저널 패턴과 유사) GNN(위상 인지)을 사용하지 않음.
- **결론**: 정식 비교표에는 미포함. 신뢰도 문제로 인용 대상에서 완전히 제외.

### D10. 문헌조사 반복 재검증 (4회) — 신규 경쟁논문 없음 확인
- **확인**: "confidence-tiered + 이질적 조치 + GNN 예측" 직접 조합 검색, Kubernetes/AIOps 자동 remediation 검색, 한국어 학위논문 검색, Circuit Breaker+GNN 특정 조합 검색 등 총 4회에 걸쳐 서로 다른 키워드로 재검증.
- **결론(당시)**: GRAF-FIRM-AGQ-GraphGRU 4자 구도를 무너뜨릴 신뢰도 있는 신규 논문 없음. 현재 포지셔닝은 방어 가능한 수준으로 판단.
- **🔺 정정(2026-09-06)**: 이 결론은 **불완전했다.** DeepScaler(ASE 2023)를 놓쳤다 — GNN + 마이크로서비스 오토스케일링 + cascading effect 대응 조합이며 Online Boutique를 벤치마크로 쓰는, 축 ①에서 가장 직접적인 비교 대상이다(D16). 4회 재검증이 모두 "신뢰도 축 + 이질적 조치" 조합을 중심으로 짜여 있어, **축 ①만 다루는 논문은 검색망에 걸리지 않았다.** 교훈: 재검증 키워드를 기여 조합(3축 동시)이 아니라 **축별로 분리해** 짜야 한다. 검색 도구로는 미출판·비공개 연구까지 확인 불가하므로 사람 네트워크 확인은 여전히 권장된다.

### D11. 최종 문헌 포지셔닝 확정 — 4자 비교표 (→ D16에서 5자로 확장)
- **결론**: GRAF·FIRM·AGQ·GraphGRU를 축(예측 모델/조치 공간/신뢰도 구간별 대응)으로 분해한 4자 비교표를 관련연구 서두에 배치하기로 확정. 네 논문 모두 세 축 중 최소 하나 이상을 비워두고 있어, 본 연구의 위치(세 축 모두 충족)는 여전히 비어 있는 자리임을 명시. ([docs/proposal.md](../docs/proposal.md) §3)

### D12. 선행연구 3개의 신뢰도 산출 방식 팩트체크
- **문제**: GRAF·FIRM·AGQ가 각자 신뢰도/불확실성을 어떻게 산출했는지 확인 필요(신뢰도 산출 방식 논의를 위한 선행 조사).
- **확인**: 세 논문 모두 명시적인 신뢰도 산출을 하지 않음. GRAF는 GNN 예측값을 점 추정치로 그대로 자원 할당에 사용, FIRM은 SVM 이분법 분류 + RL argmax 액션 선택을 그대로 실행, AGQ는 Q-learning의 ε-greedy 탐색 확률(ε)을 예측 신뢰도가 아닌 탐색-활용 균형용 하이퍼파라미터로만 사용.
- **결론**: 신뢰도 구간별 대응(축 ③)이 **장애 예측·자원 관리 도메인의 선행연구에서** 비어 있는 자리임을 재확인. (당초 "문헌상 완전히 비어 있다"로 적었으나 검증 범위가 이 3편이므로 도메인 한정 표현으로 정정 — D15.) 동시에 신뢰도 산출 방식은 이 세 논문에서 참고할 선례가 없어, 불확실성 정량화라는 별도 분야의 표준 문헌(Gal & Ghahramani 2016; Lakshminarayanan et al. 2017)에서 근거를 가져와야 함을 확인.

### D13. GRAF Discussion — 확장성 한계 자인 문구 확인
- **확인**: GRAF ToN 2024판 Discussion에서 "the readout phase's neural network input node dimension is linearly dependent on the number of microservices in an application... GRAF's performance may degrade when applied to applications composed of hundreds to thousands of microservices"라고 직접 명시. 원인은 readout 단계에서 노드 임베딩을 flatten해 FC 신경망에 입력하는 구조.
- **결론**: 이 한계는 GNN 위상 인지 자체의 한계가 아니라 GRAF의 readout 설계(flatten) 선택에서 비롯된 것. 본 연구는 이를 반면교사로 삼아 공유 per-node head 기반 노드 레벨 예측을 채택(E5·E6)하고, 이를 [docs/proposal.md](../docs/proposal.md) 우려 1·5의 근거로 사용.

### D14. FIRM 원문 조치 공간 재확인 — 브라운아웃 오기재 정정 + 본 연구 조치 5종 확정
- **문제**: FIRM이 실제로 브라운아웃을 조치로 사용하는지, "brownout으로 FIRM 우려 2을 방어한다"는 논거가 원문에 근거하는지 재확인 필요. (D4에 'FIRM = 수평/수직 스케일링 + 브라운아웃'으로 기재돼 있었음.)
- **확인**: FIRM 원문(arXiv 2008.08509) Table 3(State-action space)과 §3.4~3.5(Action Execution)를 직접 확인. FIRM의 RL(DDPG) Action Space는 **저수준 자원 5종의 한도 재할당** `RLTᵢ, i ∈ {CPU, Mem, LLC, IO, Net}`이며, 실행은 cgroups(`cpu.cfs_*`, `blkio`)·Intel MBA/CAT·HTB로 수행하고, 한도가 상·하한에 닿으면 수평 스케일아웃/인. **브라운아웃은 조치 공간에 없음.** 검색엔진 요약은 'horizontal/vertical scaling + brownout'이라 했으나 원문과 불일치 — 원문 우선(팩트체크 원칙).
- **결론**:
  1. **정정**: 기존 D4·proposal의 'FIRM 브라운아웃 포함' 및 'FIRM 이질적 조치'는 오기재로 정정. FIRM 조치 공간 = 다차원이지만 전부 자원 프로비저닝(비프로비저닝 조치 없음).
  2. **차별점 강화**: 따라서 상태성 병목(커넥션풀/Thundering Herd, D2) 시나리오는 GRAF·AGQ뿐 아니라 **FIRM도 다루지 못함** → 본 연구의 비프로비저닝 조치가 FIRM 대비로도 신규 기여임을 [docs/proposal.md](../docs/proposal.md) 우려 2·§3에 반영.
  3. **Brownout 채택(5번째 조치)**: 브라운아웃은 FIRM 근거와 **무관하게**, Online Boutique의 `adservice`/`recommendationservice`(비핵심 기능)를 dimmer로 차단하는 형태로 **벤치마크에서 실제 구현 가능**하다는 근거로 본 연구의 정식 5번째 조치로 채택(CB/Shedding/Redirection/Scale-up/Brownout). Traffic Shedding(요청 통째 거부)과 달리 요청을 받되 품질만 낮추는 질적으로 다른 레버라 조치 공간 이질성을 넓힘. 단 앱 계측(필수/선택 분리)이 필요해 실증 우선순위는 코어 조치 뒤([timeline.md](timeline.md) 컷 우선순위). [docs/proposal.md](../docs/proposal.md) §2-B·§2-C 반영.

### D15. 신뢰도 축 유일성 — 검증 범위 한정 및 주장 수위 조정
- **문제**: D12의 검증 범위는 GRAF·FIRM·AGQ 3편이었는데 결론은 "문헌상 완전히 비어 있다"는 무한정 주장이었다. 다른 도메인에 "불확실성으로 조치를 가른다"는 선례가 있으면 핵심 기여 축이 심사에서 흔들린다.
- **확인 (2026-09-06, 원문 확인 완료)**: 아래 2편이 표현상 본 연구의 신뢰도 축과 겹친다. 서지사항부터 당초 기재와 달랐다.
  - **CP-Router** — Su, J. et al. *CP-Router: An Uncertainty-Aware Router Between LLM and LRM.* **AAAI 2026**, arXiv:2505.19970. (당초 arXiv ID 미기재였음)
  - **Ramírez, G., Birch, A., Titov, I.** *Optimising Calls to Large Language Models with Uncertainty-Based Two-Tier Selection.* **COLM 2024**, arXiv:2405.02134. — **당초 "arXiv 프리프린트"로 적었으나 COLM 2024 정식 게재. 프리프린트로 낮춰 보면 안 된다.**
- **확인 결과 — 당초 구분 논리 1번은 틀렸다 🔺**: "2티어 선택류는 임계값을 손으로 긋는다"고 적었으나 **사실이 아니다.**
  - CP-Router는 **conformal prediction으로 임계값을 유도**하며 커버리지 보장을 갖는다. FBE(Full and Binary Entropy)로 CP 임계값을 적응적으로 선택하기까지 한다. 손으로 긋지 않는다.
  - Ramírez는 초기 10개 질의로 임계값을 잡은 뒤 **동적 보정**하며, 목표는 비용식 `c = ĉ_s + p_c·ĉ_l`가 정한 예산이다. 불확실성 측도는 margin sampling(최상위 두 토큰 확률 차). 역시 손으로 긋지 않는다.
  - 즉 "불확실성 임계값을 원리적으로 유도한다"는 것만으로는 본 연구의 신규성이 되지 못한다. **이 논거를 그대로 심사에서 쓰면 반박당한다.**
- **살아남은 구분선 (재정의)**: 원문 확인으로 오히려 더 정확한 선이 잡혔다.
  1. **임계값의 개수와 유도 근거** — 두 선례는 단일 불확실성 축 위에 임계값을 **하나** 두고, 그 근거는 통계적 커버리지(CP-Router) 또는 비용 예산(Ramírez)이다. 본 연구는 **조치마다 다른** `θₐ = Dₐ·Rₐ / (mₐ·L − Dₐ(1−Rₐ))`가 유도되며, 근거는 커버리지도 예산도 아닌 **조치별 `mₐ`·`Rₐ`·`Dₐ` 트레이드오프**다(G1). 결과적으로 *장애 유형이 바뀌면 같은 신뢰도에서도 선택이 달라진다*(상태성 병목에서 `m_scale-up` 급락 → Scale-up 자동 배제, D2). 선택지 간 완화효과 차이가 없는 2티어 구조에서는 원리적으로 불가능한 거동이며, **이것이 가장 방어력 있는 선이다.**
  2. **조치 공간** — 확인 결과 두 선례 모두 **이진 동질**(CP-Router는 LLM↔LRM, Ramírez는 small↔large). "무엇을 할까"가 아니라 "누구에게 시킬까"만 고른다. 본 연구는 질적 이질 5종(D14). **이 논거는 확인 후에도 그대로 유효하다.**
  3. **도메인** (1차 방어선) — 두 선례의 과제는 MCQA·QA(수학·논리추론 등)이고 조치 대상은 자기 자신의 추론 경로다. 본 연구는 장애 예측·자원 관리이고 조치 대상은 그래프 상의 다른 노드다(E7). 문제 설정이 겹치지 않는다.
  4. (보조) 불확실성의 종류 — margin sampling·CP 집합 크기(출력 단위 신뢰도) vs Deep Ensemble 분산(에피스테믹). 대상 차이일 뿐이므로 주 논거로 쓰지 않는다.
- **결론**: 주장을 좁힌다. 도메인 무한정 주장("문헌상 완전히 비어 있다")을 폐기하고, **"장애 예측·자원 관리 도메인에서 비어 있다"** + **"이질적 조치 공간 위에서 조치별 임계값이 완화효과·가역성 트레이드오프로부터 유도되는 구조는 비어 있다"**로 한정한다. 두 논문은 경쟁 논문이 아니라 **인접 연구로 관련연구에 명시**하고, 회피하지 않고 정면으로 구분한다(숨기면 "몰랐거나 숨겼다"로 읽힌다). D12 결론, [docs/proposal.md](../docs/proposal.md) §3·참고문헌, [README.md](../README.md), [overview.md](overview.md)에 반영.
- **핵심 교훈**: 원문을 확인하지 않은 채 세운 구분 논리("저쪽은 임계값을 손으로 긋는다")가 **사실과 반대**였다. 확인 없이 심사에 들고 갔으면 핵심 기여 축에서 반박당했을 항목이다. D14(FIRM 브라운아웃 오기재)와 같은 유형의 사고이며, 원문 우선 원칙을 재확인시킨다.
- **잔여**: 없음(확인 완료). 다만 LLM 라우팅 분야는 신규 논문 유입이 빠르므로, 심사 직전 재검색 1회를 권장한다.

### D16. DeepScaler(ASE 2023) 편입 — 4자 → 5자 비교표
- **문제**: D10의 문헌조사 4회 재검증에서 누락된 논문이 확인되었다. DeepScaler는 GNN + 마이크로서비스 오토스케일링 + cascading effect 명시적 대응 조합이고 **벤치마크도 Online Boutique로 겹친다.** ASE 2023(SE 최상위)이라 심사위원이 알고 있을 가능성이 높고, 누락 시 "같은 벤치마크를 쓴 최상위 논문을 몰랐다"는 인상을 준다.
- **확인 (원문·저장소 확인 완료, 2026-09-06)**: Meng, Song, Tong, Pan, Yu (SYSU), IEEE/ACM ASE 2023, arXiv:2309.00859, 코드 공개.
  - **예측 모델**: EM 기반 adaptive graph learning으로 서비스 의존 affinity matrix를 **학습** + attention 기반 GCN으로 시공간 특징 추출. 축 ①에서 GRAF(MPNN 균등 집계)보다 정교하다.
  - **예측 대상**: CPU·메모리 사용률, 응답시간(ms), 요청률 — **연속 수치 회귀** (AGQ·GraphGRU와 같은 계열).
  - **조치 공간**: 자원 프로비저닝 단일(상호작용 서비스를 한 번에 동시 재구성). 비프로비저닝 조치 없음.
  - **신뢰도**: 없음.
  - **벤치마크**: Bookinfo, **Online Boutique(10개 서비스)**, Train-Ticket. SLA 위반 평균 41% 감소.
- **영향 분석**: **3축 포지셔닝은 유지된다.**
  - 축 ①(위상 인지 예측)은 원래도 GRAF류가 차지한 자리로 인정해온 영역이므로 새로 잃는 것이 없다. DeepScaler는 그 자리를 더 정교하게 채운 논문이다.
  - 축 ②(이질적 조치)·축 ③(신뢰도)은 그대로 비어 있다.
  - E1(GAT 채택 논거)은 **무너지지 않는다.** E1의 주장은 "GRAF와 AGQ가 차등 집계를 못 한다"로 두 논문을 특정한 것이고, 비교표에 이미 GraphGRU(GAT)가 있어 애초에 "attention 선례가 없다"는 주장을 하고 있지 않았다.
  - 오히려 우려 1(벤치마크 규모)에는 **유리하다** — 최상위 venue 두 곳(CoNEXT/ToN의 GRAF, ASE의 DeepScaler)이 같은 Online Boutique를 쓴 전례가 된다.
- **새로 답해야 할 질문**: *"DeepScaler는 의존 그래프를 학습하는데 왜 정적 그래프인가."* 답변 — Istio 사이드카가 실제 호출 관계를 직접 제공하는 환경이라 그래프를 추정할 필요가 없고, 관측 가능한 구조를 추정하면 (a) 추정 오차가 예측 오차에 더해지며 (b) 학습된 인접행렬은 해석이 어려워 조치 근거 설명이 약해진다(E3의 RL 미채택 논거와 같은 축). 위상 변경 대응은 우려 8에서 별도로 다룬다. [docs/proposal.md](../docs/proposal.md) 우려 3에 반영.
- **결론**: 4자 → **5자 비교표**로 확장하고 "예측 대상(회귀 vs 분류+불확실성)" 행을 신설해 구분을 명시. [docs/proposal.md](../docs/proposal.md) §2-B·§3·우려 1·우려 3·참고문헌, [README.md](../README.md), [overview.md](overview.md)에 반영.

### D17. LLM 캐스케이드·라우팅 — 경쟁이 아니라 활용 기법으로 채택
- **확인 (원문·서지 확인 완료)**: FrugalGPT(Chen, Zaharia, Zou, **TMLR 2024**, arXiv:2305.05176) — 저렴한 모델부터 순차 질의하고 응답 신뢰도 미달 시 상위 모델로 escalate. RouteLLM(Ong et al., **ICLR 2025**, arXiv:2406.18665) — 선호도 데이터로 학습한 라우터가 강/약 모델을 이진 선택.
  - ⚠️ 초기 검토 시 FrugalGPT를 "프리프린트(정식 게재 없음)"로 기재했으나 **오기재**다. TMLR 2024 정식 게재이며, 프리프린트로 낮춰 인용하면 심사에서 지적당한다. D14·D15와 같은 유형의 서지 오류이므로 인용 전 재확인 원칙을 재확인한다.
- **분석**: 두 논문 모두 판단 근거가 **질의 난이도와 응답 품질**이며 시스템 부하 상태를 사용하지 않는다. 즉 "언제 발동할 것인가"라는 축이 비어 있다.
- **결론**: 경쟁 논문이 아니라 **활용 기법**으로 처리한다. "소형 모델 우회로도 상당 범위에서 품질이 유지된다"를 선행연구가 실증했으므로 이를 Degraded-path Redirection의 구현 근거로 채택하고, 라우팅 기법 자체를 기여로 주장하지 않는다. 이로써 라우팅 효과를 직접 실증할 부담이 제거된다. [docs/proposal.md](../docs/proposal.md) §3-2·참고문헌에 반영.

### D18. 부하 인지 LLM 라우팅(HW-Router) — 인접 연구로 명시적 구분
- **확인**: Kabir, Xue, Zheng, Lou. *HW-Router: Hardware-Aware Routing for Scalable Multi-LLM Serving.* Design Automation Conference (DAC), arXiv:2608.14575. 큐 길이·KV 캐시 사용률·최근 TTFT/TPOT를 경량 지연 예측기에 입력해 SLO 인지 라우팅.
- **분석**: "시스템 상태를 보고 라우팅한다"는 발상이 표면적으로 겹친다. 다만 4축이 모두 다르다 — 관측 범위(단일 LLM 서비스 내부 GPU 배분 vs 서비스 호출 그래프 전체), 시점(반응 vs 예측 선제), 조치 공간(라우팅 단일 vs 5종), 신뢰도(없음 vs `θₐ` 유도).
- **결론**: venue(DAC, 하드웨어 설계 자동화)와 대상 영역이 분리되어 구분이 용이하다. §3-3(a)에 4축 구분표로 정면 기재. S3 시나리오가 이들이 원리적으로 다룰 수 없는 영역임을 실증한다.

### D19. GraphRouter — 명칭·키워드 충돌, 구분 서술 필수
- **확인**: Feng, T., Shen, Y., You, J. *GraphRouter: A Graph-based Router for LLM Selections.* ICLR 2025, arXiv:2410.03834 (UIUC).
- **분석**: 그래프의 정의가 근본적으로 다르다 — GraphRouter는 태스크·질의·LLM의 **적합도 관계 그래프**이고, 본 연구는 **서비스 호출 토폴로지**다. 예측 대상도 라우팅 적합도 vs SLO 위반 위험의 전파로 갈린다.
- **결론**: 저자 Jiaxuan You가 GNN 분야 저명 연구자이고 venue가 ICLR이므로 **심사위원이 알고 있을 가능성이 가장 높은 문헌**이다. 구분 서술을 누락하면 리스크가 가장 크다고 판단해 §3-3(b)에 명시.

### D20. 관련연구 3분할 구조 확정
- **문제**: LLM 확장으로 검토 문헌이 5편 → 9편으로 늘었다. 성격이 다른 문헌을 하나의 비교표에 넣으면 같은 축으로 비교하라는 요구를 받아 방어 부담이 급증한다.
- **결론**: 3분할로 격리한다 — **(1) 비교 대상**(GRAF·FIRM·DeepScaler·AGQ·GraphGRU, 5자 비교표) / **(2) 활용 기법**(FrugalGPT·RouteLLM) / **(3) 인접 연구**(HW-Router·GraphRouter). **5자 비교표에는 LLM 라우팅 연구를 추가하지 않는다** — 세 축 자체가 그들의 문제 설정에 정의되지 않기 때문이다. [docs/proposal.md](../docs/proposal.md) §3에 반영.

### D21. ORACL(TSC 2026) — LLM 기반 오토스케일링 의사결정, 인접 연구로 구분
- **문제**: LLM 확장(B7) 채택으로 "LLM + 마이크로서비스 오토스케일링" 교집합 문헌 확인이 필요해졌다. 확인 대기 목록의 ORACL이 여기 해당한다.
- **확인 (원문 확인 완료, 2026-09-06)**: Bai, H., Islam, M. T., Xu, M., Buyya, R. *ORACL: Optimized Reasoning for Autoscaling via Chain of Thought with LLMs for Microservices.* **IEEE Transactions on Services Computing 2026**, arXiv:2602.05292 (Melbourne·SIAT). 런타임 텔레메트리를 자연어 상태 서술로 변환 → LLM이 추론 트레이스 생성 → 근본 원인 식별 + **행동 공간 가지치기** → 정책 제약 하 자원 할당. 근본원인 정확도 15%↑, 학습 24배 가속, QoS 6%↑.
- **왜 중요한가**: 본 연구가 **B7에서 명시적으로 기각한 방향 (A)**("LLM 에이전트를 Policy Engine으로 사용")를 실제로 수행한 논문이다. 저자 Rajkumar Buyya는 클라우드 컴퓨팅 분야 최고 피인용 연구자 중 하나이고 TSC도 견실한 저널이라, 심사에서 *"LLM으로 의사결정하는 연구가 이미 있는데 왜 GNN인가"*가 제기될 수 있다.
- **분석 — 오히려 기각 근거를 강화한다**: ORACL조차 LLM에 결정을 온전히 맡기지 않고 **행동 공간 가지치기 + 정책 제약**으로 감쌌다. 비결정적 출력을 제어 루프에 넣을 때의 부담을 보여준다. 구분선 5축 — 의사결정 주체(LLM 추론 vs 비용함수 argmin) / 조치 공간(자원 할당 vs 질적 이질 5종) / 신뢰도 축(없음 vs `θₐ`+Safety Guard) / 재현성(LLM 출력 의존 vs 결정적) / **LLM의 위치(의사결정 도구 vs 검증 대상 노드)**.
- **보강 근거**: **MicroRemed**(arXiv:2511.01166) — LLM의 마이크로서비스 remediation 능력을 라이브 환경에서 평가하는 벤치마크로, **가장 쉬운 난이도에서도 단독 LLM이 50% 정확도를 넘지 못한다**고 보고. 조치 실행을 LLM에 맡기는 접근의 현재 한계를 보이는 실증이며 방향 (A) 기각의 외부 근거로 인용 가능하다. (후속 E2E-REME는 FSE 2026 게재 — 분야가 활발함을 보여준다.)
- **결론**: 비교표에는 넣지 않고 **인접 연구로 §3-3(c)에 정면 기재**한다. 5축 구분표와 함께 "본 연구에서 LLM은 조치를 결정하는 주체가 아니라 예측·조치의 **대상이 되는 노드**"라는 위치 차이를 핵심 구분선으로 제시한다. [docs/proposal.md](../docs/proposal.md) §3-3(c)·참고문헌에 반영.

### D22. Graph-PHPA(CloudNet 2022) — 확인 완료, 비교표 미편입
- **문제**: D1에서 언급만 하고 원문을 확인하지 않은 채 남아 있던 문헌.
- **확인 (2026-09-06)**: Nguyen et al. *Graph-PHPA: Graph-based Proactive Horizontal Pod Autoscaling for Microservices using LSTM-GNN.* IEEE CloudNet 2022, arXiv:2209.02551 (DCU). LSTM과 GNN을 결합해 선제적 HPA 수행. **Bookinfo** 벤치마크에서 규칙 기반 K8s를 baseline으로 평가.
- **판정**: 축 ①(위상 인지 예측) + 자원 할당 단일 조치 + 신뢰도 없음으로 **GRAF·DeepScaler·AGQ·GraphGRU와 같은 위치**다. venue(CloudNet)와 검증 범위(Bookinfo, 규칙 기반 단일 baseline)가 이미 비교표에 있는 논문들보다 좁아 **비교표 편입은 불필요**하다 — D16(DeepScaler)과 달리 새로 채우는 자리가 없다.
- **활용 가치**: Graph-PHPA는 LSTM과 GNN을 **결합**했으나 본 연구는 LSTM을 **독립 baseline**으로 둔다. 결합하면 개선이 시간성에서 온 것인지 위상에서 온 것인지 귀속할 수 없기 때문이며, 이 대비가 §4-3 baseline 3의 설계 근거가 된다. [docs/proposal.md](../docs/proposal.md) §4-3·참고문헌에 반영.

## E. 모델 아키텍처 설계

### E1. GCN vs GAT — 최종 모델 GAT 채택
- **확인**: D6에서 확인한 대로 GRAF(MPNN)·AGQ(ChebConv) 모두 이웃 균등/스펙트럴 방식이라 attention 기반 차등 집계를 사용하지 않음.
- **결론**: GAT를 최종 모델로 채택. 근거는 일반 GAT 문헌 우수성이 아니라, "GRAF·AGQ가 실제로 무엇을 안 썼는지"에 기반한 구체적 문헌 공백. 커넥션풀 시나리오(D2)의 실증 근거로도 attention weight를 활용 가능.

### E2. GNN 변형 전수 비교 여부 — 불필요 판단
- **문제**: STGNN, GNN+RL 등 GNN 계열이 매우 많은데 전부 실험해서 비교해야 하는지 검토.
- **결론**: 불필요. "설계 선택(design choice)"은 문헌 인용으로 근거 충분, "핵심 주장(LSTM vs GNN)"만 본인 실험으로 직접 검증 필요. GCN vs GAT 비교 실험도 필수가 아니라 선택(시간 남으면 보강).

### E3. 강화학습(RL) 결합 여부 — 미채택
- **결론**: Policy Engine이 이미 신뢰도 구간별 정책으로 조치를 결정하는 구조라 RL로 액션 선택을 재학습시킬 필요 없음. RL 미사용이 오히려 설명 가능성 강점으로 서술 가능.

### E4. 시계열(STGNN) 결합 여부 — 1차 미채택, 확장 옵션 유보
- **문제**: AGQ·GraphGRU처럼 시계열 결합 모델이 예측 정확도 면에서 유리한 것 아닌가에 대한 재검토.
- **결론**: 목적 자체가 다름(AGQ·GraphGRU는 연속적 수치의 정확한 예측이 목표, 본 연구는 현재 위험 여부+확신도의 즉각 판단이 목표)을 1차 근거로, 추론 지연 최소화라는 설계 철학을 2차 근거로 최종 확정. 1차 모델은 정적 GAT(스냅샷 1장)로 진행. G2(2계층 제어로 해소)의 추론 주기 실측 튜닝 결과에 따라 입력 윈도우 확장 등 최소 침습적 확장을 후속 실험으로 고려 가능.
- **심사 방어 로직**: (1) 문제 정의가 다름 명시 → (2) 설계 트레이드오프임을 명시(정확도보다 낮은 추론지연 우선) → (3) 실측 검증 예정임을 명시.

### E5. 출력(Readout) 방식 — Flatten 회피 (초기 pooling → 최종 노드 레벨 공유 head)
- **문제**: 그래프 크기(노드 수)가 늘어날 경우 모델 구조·학습이 얼마나 영향받는지, GRAF와 같은 확장성 한계를 물려받는 것은 아닌지 검토 필요.
- **확인**: GRAF는 readout 단계에서 각 노드 임베딩을 flatten해 완전연결(FC) 신경망에 통째로 입력하는 구조를 사용하며, D13에서 확인한 대로 이로 인해 확장성 한계를 스스로 인정함.
- **결론**: 핵심은 "flatten을 피해 파라미터가 노드 수와 무관하도록" 두는 것. 초기에는 mean/attention pooling(그래프 전체를 고정 크기 벡터로 압축)을 고려했으나, 이후 Ground Truth 설계(E6)에서 **노드 레벨 예측**으로 확정하면서 출력 방식도 **공유 per-node head(모든 노드에 동일 MLP 적용)**로 최종 결정. 두 방식 모두 파라미터가 노드 수와 무관해 GRAF의 flatten 문제를 피하지만, 노드 레벨은 서비스별 위험도를 직접 산출해 Actuator 타겟팅과 직결된다는 이점이 추가됨. 확장성 논거(파라미터가 노드 수에 종속되지 않음)는 그대로 유지되며, 근거가 "pooling"에서 "파라미터 공유"로 정밀화됨. GAT 채택(E1)과는 별개의 설계 축.

### E6. Ground Truth 정의 — 4갈래 확정
- **문제**: GNN 지도학습을 위한 라벨 정의(§4-2)가 스텁으로 비어 있어, "무엇을 연쇄장애 위험으로 라벨링할 것인가"가 미정. 갈래 1이 나머지를 좌우하므로 순서대로 결정.
- **의사결정 과정**:
  1. **라벨 단위(갈래 1)**: 그래프 레벨 / 노드 레벨 / 이중 head 중 **노드 레벨** 채택. 근거 — Actuator는 특정 서비스에 조치하므로 "어디에" 정보가 모델에서 나와야 함(그래프 레벨은 localization을 외부 bolt-on으로 붙여야 함). 노드 레벨은 신뢰도 구간별 대응을 서비스 단위로 세밀화하고 위상 인지 우위를 가장 잘 드러냄. 공유 per-node head라 확장성도 유지(E5 갱신).
  2. **위험 정의(갈래 2)**: SLO 위반 / 리소스 포화 / 가용성 중 **SLO 위반**(P99·에러율) 채택. 평가지표(§4-4)와 정합, 리소스 지표는 입력 feature로 분리해 누수 방지.
  3. **refinement**: positive를 "전파성 위반"으로 한정(이웃 선행 열화 시). 랜덤 주입된 1차 장애 onset은 입력에 선행 신호가 없어 예측 불가능한 노이즈이므로 제외/유예 — 모델이 위상으로만 예측 가능한 전파를 학습하게 해 LSTM 대비 우위를 선명화. (갈래 2에서 "1차 장애는 입력에 나타나니 손라벨 불필요"라 했던 것을 정정: 주입 직전 스냅샷은 신호가 없다는 점을 반영.)
  4. **예측 지평(갈래 3)**: 단일 고정 Δ 이진 채택(다중 지평은 후속 확장, 정적 GAT·분류 결정과 정합). Δ 하한=폐루프 응답시간(§2-D), 값은 실측 튜닝.
  5. **파이프라인(갈래 4)**: 장애주입+트래픽 → 지표 시계열·스냅샷 기록 → 자동 역라벨링(수작업 없음, 재현 가능). 클래스 불균형 대응 + 장애주입 커버리지(커넥션풀 시나리오 필수, mₐ 측정과 동일 실험).
- **결론**: 위 4갈래로 §4-2 확정. 노드 레벨 결정에 따라 E5(출력 방식)를 pooling → 공유 per-node head로 갱신. 구체 수치(Δ, 임계값, 샘플링 간격, 장애 파라미터)는 §4-5 실측 이월. 신뢰도는 지도 라벨이 없어 calibration으로 간접 검증. [docs/proposal.md](../docs/proposal.md) §4-2·§2-A에 반영.

### E7. 조치 적용 지점(apply_point) 명시 — §2-C와 §2-E 알고리즘의 불일치 해소
- **문제**: [docs/proposal.md](../docs/proposal.md) §2-E 의사코드는 `emit(대상=v, …)`로 조치 대상을 **위험 노드 자신**으로 고정했다. 그러나 §2-C의 Actuator 서술은 이미 "조치 지점 ≠ 위험 지점"이었다 — Brownout은 위험 노드(adservice·recommendationservice)가 아니라 **frontend**가 호출을 생략하는 방식이고, Read Redirection은 병목(Redis primary)이 아니라 **cartservice** 이그레스에 EnvoyFilter를 주입한다. Circuit Breaker도 Resilience4j 특성상 호출자 측에 있다. 즉 같은 문서 안에서 알고리즘과 구현 서술이 어긋나 있었고, 심사에서 의사코드를 제시하면 "Brownout을 adservice에 겁니까"라는 자기모순이 드러난다.
- **의사결정 과정**: (조치, 대상 노드) 쌍을 후보 집합 위에서 탐색하는 안(예: 위험 노드의 k-hop 상류를 후보로 두고 순이득 argmax)을 검토했으나 **기각**. 이유 두 가지. (1) 조치별 적용 지점은 탐색 대상이 아니라 조치 종류에 따라 **구조적으로 결정**된다 — 이미 결정된 것을 다시 탐색하는 과잉 설계다. (2) 순이득 argmax 형태는 현재 `argmin E[비용]` 구조와 달라, 채택하면 `θₐ` 유도와 Safety Guard를 함께 버려야 한다(G1·G4 역행).
- **결론**: 사상(mapping) `apply_point(a, v)`를 §2-C에 표로 명시하고, §2-E 의사코드를 `emit(대상=apply_point(a*, v), …)`로 고친다. CB·Shedding·Redirection·Brownout은 호출자/인그레스 측, Scale-up만 위험 노드 자신. **비용함수는 불변**(`p̄_v`·`u_v`·`p_eff`·`θₐ`·`mₐ` 그대로). 부수 효과로 "위상 인지가 예측에만 쓰이고 조치 선택에는 안 쓰인다"는 예상 반론에 대한 답이 생긴다. §4-2의 "어느 서비스에 조치할지" 문구도 "어느 서비스가 위험한지"로 정정(예측 대상과 적용 지점의 분리). [docs/proposal.md](../docs/proposal.md) §2-C·§2-E·§4-2에 반영.

### E8. 이질적 노드 피처 표현 — 의미 기준 공통 슬롯 + 타입 임베딩
- **문제**: 일반 서비스와 LLM 추론 노드는 원시 지표가 다르다(커넥션풀 vs KV 캐시, RPS vs 토큰 처리율). 한 벡터에 어떻게 담을 것인가.
- **기각안**: 노드 타입별 전용 차원 + 제로 패딩. 13~14개 노드 중 LLM이 1개뿐이라 전용 차원이 90% 이상의 노드에서 0이 되고, 이 값이 GAT attention 연산에 참여해 노이즈로 작용한다. 단일 노드 분량의 신호로 전용 차원을 학습시키는 것도 비현실적이다.
- **결론**: **의미 기준 공통 슬롯 6종**(상태성 자원 포화율 / 큐 대기율 / 처리량 대비 용량비 / 지연 분위수 / 자원 사용률 / 에러율) + 학습 가능한 노드 타입 임베딩(4~8차원). 정보 손실이 아니라 **의미 정렬**이다.
- **TA-GAT 보존**: 각 슬롯은 현재값만이 아니라 슬라이딩 윈도우 통계량(평균·slope·표준편차)을 함께 갖는다. 이를 빠뜨리면 H5 결정과 §4-3의 시계열 보강 ablation이 함께 무효화된다.
- **부수 효과**: f1에서 **DB 커넥션풀 소진과 KV 캐시 소진이 "스케일아웃으로 해소되지 않는 유계 자원의 포화"라는 동일 현상으로 통합 표현**된다. D2 논거와 이질적 워크로드 논거가 하나로 결합되어, 피처 설계가 문제 인식을 반영한다는 근거가 된다.
- **잔여**: `type=llm` 임베딩의 학습 신호가 노드 1개에서만 온다(G6).

### E9. Actuator 5종 유지 + LLM 노드 매핑, 개명 1건
- **문제**: LLM 노드를 포함하면 조치 공간을 어떻게 조정할 것인가. 초기 검토에서 4종으로 축소하는 안이 나왔으나, 그 경우 D14에서 원문 팩트체크를 거쳐 채택한 Brownout이 누락된다.
- **결론**: **5종 그대로 유지한다.** 축소가 아니라 유지했을 때 매핑이 오히려 자연스럽다 — LLM의 `max_tokens` 상한·RAG top-k 축소가 **Brownout(품질 저하)에 정확히 대응**하고, 소형 모델 라우팅이 Redirection(경로 변경)에 대응한다. 5종 이질성이 LLM 노드에서도 유지되므로 "이질적 조치 공간" 기여가 확장 구성에서 선명해진다.
- **개명 1건**: `Read Redirection` → **`Degraded-path Redirection`**. "DB 읽기 한정"으로 읽혀 모델 다운그레이드를 포괄하지 못하기 때문이다. 나머지 4종은 LLM 맥락에서도 명칭이 통하므로 유지한다(초기 검토의 4건 일괄 개명은 실익 없이 전체 치환만 유발해 미채택).
- **`apply_point`에 노드 타입별 분기 추가 (중요)**: 일반 서비스에서 Redirection·Brownout은 **호출자** 측 레버지만(cartservice 이그레스의 EnvoyFilter, frontend의 dimmer), LLM 노드에서는 모델 라우팅·토큰 제한이 **서빙 노드 자신의 요청 파라미터**이므로 `apply_point = v`가 된다. E7의 사상을 (조치 종류 × 노드 타입)의 함수로 확장했다. [docs/proposal.md](../docs/proposal.md) §2-C에 반영.
- **단일 Policy Engine 유지**: LLM 전용 엔진을 두지 않는다. 분리하면 "LLM 노드에 위험이 예측되었으나 조치는 다른 노드에 적용해야 하는" 경우(S3)를 처리할 수 없다. 노드 타입별 차이는 Actuator 레이어에서 전략 패턴으로 흡수한다.

### E10. GAT 채택 논거 보강 — 혼합 그래프에서의 구조적 근거
- **기존 논거(E1)**: GRAF(MPNN 균등 집계)·AGQ(ChebConv)가 이웃 간 차등 중요도를 학습하지 못한다는 문헌 대비 + "서비스별 중요도가 균일하지 않다"는 일반론.
- **보강**: 혼합 그래프에서는 이웃 간 중요도 불균일이 **구조적 사실**이 된다. 동일 노드의 이웃에 밀리초 단위 stateless 서비스와 초 단위 LLM 노드가 공존하므로, 균등 합산은 성질이 다른 두 신호를 같은 무게로 섞는다.
- **선택 확장**: attention weight 시각화로 "LLM 노드가 실제로 더 큰 가중치를 받는가"를 검증(해석 가능성 보강, 선택 항목).
- **유의**: 기존 E1 논거를 **대체하지 않고 보강**한다. 실측이 기대와 다르게 나오면 이 논거를 철회하고 E1의 문헌 근거로 복귀한다.

## F. 학습·평가 전략

### F1. 신뢰도 산출 방식 — Deep Ensemble(N=5) 채택
- **문제**: 후보 3개(MC Dropout/Deep Ensemble/Softmax Entropy) 중 택1 필요.
- **확인**: 세 방식을 추론 시 필요 연산·레이턴시 영향·신뢰성·구현난이도 기준으로 비교. MC Dropout은 추론 시 동일 모델 반복 순전파(N회)가 필요해 즉각반응 타이밍 문제(G2)와 정면충돌. Deep Ensemble은 N개 모델을 병렬 배치하면 단일 모델과 큰 차이 없는 추론 시간 확보 가능. Softmax Entropy는 연산 부담이 가장 적으나 "확신의 그림자"에 가까워(OOD 상황 과신 경향) 신뢰도 구간별 대응이라는 핵심 개념의 근거로 쓰기엔 설득력이 약함.
- **근거**: (1) Lakshminarayanan et al.(2017)이 Deep Ensemble이 MC Dropout보다 신뢰할 수 있는 불확실성 추정치를 제공함을 실증. (2) GRAF·FIRM·AGQ 모두 신뢰도 산출 자체를 하지 않아(D12) 참고할 선례가 없으므로, 불확실성 정량화 분야의 표준 문헌(Gal & Ghahramani 2016; Lakshminarayanan et al. 2017)에서 근거를 가져옴. (3) 벤치마크 그래프가 11개 노드로 작아(A3) N=5 모델 학습 비용 부담이 낮음.
- **결론**: Deep Ensemble(N=5)을 1차 방향으로 확정. N개 모델의 예측 분산을 신뢰도 구간(고/중/저) 판정에 사용하는 구체적 임계값 설계는 비용함수(G1)와 연계하여 추후 진행.

### F2. 실험 결과 통계 처리 방식
- **문제**: "통계적으로 개선되었다"를 어떻게 리포팅할지 — 정식 유의성 검정(t-test 등)이 필요한지 검토.
- **결론**: 개선율 리포팅(기술통계)은 필수, 정식 유의성 검정(추론통계)은 KCI급에서 필수 아님(선택 보강). 반복 실행 간 안정성은 평균±표준편차(또는 5회 미만 시 min-max 범위)로, 레이턴시처럼 우측으로 꼬리가 긴 분포는 표준편차 대신 P50/P90/P99 백분위수로 리포팅한다.

### F3. 그래프(데이터셋) 규모 증가에 따른 학습 시간 영향 분석
- **문제**: "데이터셋이 늘어날수록 학습이 오래 걸리는가?"에 대한 명확한 답 필요(우려 5 대응 근거).
- **확인**: "그래프 크기(노드 수)"와 "학습 샘플 수"를 구분해서 봐야 함.
  1. **그래프 크기 증가**: GAT는 실제 엣지에 대해서만 attention을 계산하는 sparse 연산(PyTorch Geometric 기준)이라 레이어당 연산량이 노드/엣지 수에 대략 선형(O(N+E)). Deep Ensemble(N=5)도 단일 모델 학습시간의 상수배(×5)일 뿐 그래프 크기와 무관. E5·E6에서 공유 per-node head(노드 레벨 예측)를 채택했기 때문에 출력층 파라미터도 그래프 크기와 무관하게 고정됨.
  2. **학습 샘플 수 증가**: 통상적인 선형 스케일(에폭당 소요시간 증가)로, 배치 처리로 완화 가능.
- **진짜 병목**: GNN 모델 학습 자체가 아니라 실측 데이터 수집 과정. 노드가 늘어나면 (a) K8s 클러스터의 컨테이너 수가 늘어 로컬 하드웨어 메모리 부담이 커지고(A3), (b) 노드 수만큼 가능한 장애/부하 조합(상태 공간)이 커져 충분히 커버하려면 필요한 실측 샘플 수도 늘어남. 이는 GPU 연산 시간이 아니라 트래픽 생성+장애주입+측정을 반복하는 물리적 수집 시간이 늘어나는 것.
- **결론**: "학습이 오래 걸리냐"는 질문에는 "모델 자체의 학습 연산은 11~수십 개 규모에서 문제 안 되고, 실제 병목은 라벨 데이터 실측 수집의 인프라 제약"이라고 답변. B2·A3와 정확히 같은 논리.
- **보강**: 전용 장비(A3)에서도 이 결론은 그대로다. 병목은 GPU 연산 시간이 아니라 **클러스터를 실제로 구동해 라벨을 얻는 물리적 수집 시간**이며, 여기에 CPU 경합으로 인한 유효 에피소드 손실(A5)까지 더해진다.

### F4. LLM 품질 저하 비용의 처리 — `D_downgrade` 민감도 분석
- **문제**: 모델 다운그레이드의 비용을 어떻게 정량화할 것인가. 응답 품질의 절대 측정은 LLM 평가 방법론이라는 별개 영역이며 스코프를 벗어난다.
- **기각안**: 비용함수에 품질 축 `w_q·Q`를 신설. 현재 비용식에서 품질 저하 비용이 들어갈 자리는 **이미 `Dₐ`**(조치의 즉시 비용)이고 Brownout이 `Dₐ = 중`으로 자리를 잡고 있다. 새 항을 두면 G1이 기각한 가중합 구조로 되돌아가 `θₐ` 유도와 Safety Guard를 잃는다.
- **결론**: 비용함수 구조를 바꾸지 않고 §2-B 표에 LLM 조치 3행을 추가한다. 모델 다운그레이드의 `Dₐ`(=`D_downgrade`)를 **운영자가 설정하는 정책 파라미터**로 두고 민감도 분석을 수행 — 값을 변화시키며 조치 선택 분포 변화와 다운그레이드→Scale-up·차단 전환의 **`θₐ` 교차점**을 제시한다. 품질을 측정하지 않고도 품질-지연 트레이드오프를 정량으로 보인다.
- **순환 논리 방어**: 상수 하나를 흔든 것으로 읽히지 않도록, 동일 질의에 대한 주 모델/폴백 모델 응답 대조 **정성 사례 1~2건**을 부록에 제시한다. 정량 평가가 아니므로 스코프 부담이 없다.
- **심사 대응**: "품질을 어떻게 측정했나" → "측정하지 않았고, 운영자가 설정하는 비용 파라미터로 두고 그 영향을 분석했다."

## G. 오픈 이슈 및 해소 기록

### G1. 비용함수(Cost Function) 구체화 — [해결됨] 초안 골격 확정
- **이슈**: "가용성 손실/되돌리기 난이도/오탐 피해를 저울질"이라는 서술이 수식/모델 없이 선언적임.
- **의사결정 과정**:
  1. **함수 형태**: 후보 3안(기대비용 최소화 / 가중합 스코어 / FIRM식 reward 차용) 중 **기대비용 최소화형** 채택. 신뢰도 p가 확률 가중치로 자연스럽게 들어가 "왜 신뢰도가 조치를 가르는가"가 수식으로 정당화되고, 조치별 임계값 θₐ가 유도되어 신뢰도 구간(고/중/저)이 자동 생성되기 때문. FIRM식 reward는 RL 미채택(E3) 결정과 서사 충돌 위험으로, 가중합 스코어는 구간별 대응의 필연성이 약해 기각.
  2. **변수 축**: 3축(가용성 손실 L / disruption Dₐ / 가역성 Rₐ) 유지, 오탐 피해는 Dₐ·Rₐ로 파생 정의.
  3. **완화효과 mₐ 포함 여부**: 포함으로 결정. mₐ가 핵심 기여(신뢰도 구간별 대응)를 격상시키는 것은 아니나(구간 메커니즘은 mₐ 없이도 성립), 커넥션풀 차별점(D2)을 비용함수 외부 하드코딩 규칙이 아니라 **내부에서 유도**되게 만드는 역할을 함. mₐ를 변수로 두면 비용함수가 "조치 비용 계산기"에서 "장애 유형 인지형 의사결정기"로 격상. 측정 부담(장애 유형별 mₐ 추정)은 실험 설계(§4-5, 구 G3)와 연계해 실험 이월.
- **결론**: 기대비용 최소화형 비용함수 `E[비용|a] = p·[(1−mₐ)·L + Dₐ] + (1−p)·[Dₐ·Rₐ]`, `E[비용|보류] = p·L`, 유도 임계값 `θₐ = Dₐ·Rₐ / (mₐ·L − Dₐ·(1−Rₐ))`로 초안 골격 확정. L·D·R·m 실제 수치는 실험 튜닝으로 이월. F1(Deep Ensemble)의 신뢰도 구간 임계값 설계도 θₐ 유도로 함께 해결됨. [docs/proposal.md](../docs/proposal.md) §2-B에 반영.

### G2. GNN 추론 레이턴시 vs 즉각 반응 필요성 — [해결됨] 2계층 제어로 방향 확정
- **이슈**: Circuit Breaker/Traffic Shedding처럼 즉각 반응이 필요한 조치가 GNN 추론 주기에 묶이면 오히려 반응이 느려질 위험.
- **의사결정 과정**:
  1. 초안: "CB를 로컬 전용으로 빼고 GNN은 다른 조치만" 검토 → 이질적 조치가 차별점인데 CB를 조치 공간에서 빼는 것이 아깝다는 판단으로 기각.
  2. 대안: CB를 GNN 조치로 유지하되 로컬 반응층과 공존시키는 2계층 구조 채택. 두 층이 같은 액추에이터를 건드리는 중복 충돌 우려는 "OR 의미론 + GNN escalate-only + lease TTL" 규칙으로 해소(한 액추에이터에 사실상 단일 중재 보장). Resilience4j의 `FORCED_OPEN` 상태로 구현 가능해 이국적 메커니즘이 아님.
- **결론**: 트리거 경로를 이원화한다. **Tier 1(로컬 반사, 상시 on)**이 CB·Shedding을 ms 단위로 반응시켜 급속 장애를 잡고, **Tier 2(GNN 선제, N초 주기)**가 위상 인지 예측 + 신뢰도 구간별 비용함수로 5종을 선택(CB·Shedding은 force-open/force-shed, Redirect/Scale/Brownout은 단독). **5종 이질적 조치는 CB 포함 그대로 유지.** CB 임계값 pre-arm은 확장 옵션. GNN 추론 주기 파라미터 실측 튜닝은 실험 이월. E4(시계열 미채택)와 정합. [docs/proposal.md](../docs/proposal.md) §2-D·우려 6에 반영.

### G3. 트래픽 프로파일 파라미터 + mₐ 측정 — [이관] 실험 설계(§4-5)로 이동
- **이슈**: A4에서 도구(Locust/k6 + Istio/Chaos Mesh)는 확정했으나 구체적 프로파일 조합(정상/버스트/점진증가 파라미터)이 미상세화. 여기에 G1에서 도입된 mₐ(완화효과)의 측정 방식도 연계됨.
- **결론**: 두 항목 모두 (a) 프로포절 심사 필수가 아니고 (b) 실측 없이 미리 확정하면 근거가 약한 값(F2와 동일 논리)이라, '오픈 이슈'가 아니라 **실험 설계 내용으로 이관**. 방향만 확정하고 구체 수치는 실험 단계로 미룸:
  - 트래픽 = 정상/버스트/점진증가 3종 프로파일, 클러스터 용량 맞춤 캘리브레이션.
  - mₐ = (장애 유형 × 조치) 대조 실험으로 추정, 조치 전후 SLO 회복분을 대리 지표로 사용. 상태성 병목에서 Scale-up mₐ가 낮게 나오는지는 §4-3 baseline 실험의 부산물로 함께 확인 → 별도 실험 아님.
  - [docs/proposal.md](../docs/proposal.md) §4-5에 반영. 이로써 프로포절 심사 대비 오픈 이슈는 모두 해소/이관됨.

### G4. 문제 정의 정형화(B) + Policy Engine 알고리즘화(A) + 비용함수 p 정의 정정 — [반영]
- **배경**: 설계 결정은 모두 끝났으나 조각(예측/비용함수/2계층/Safety Guard)이 산문으로 흩어져 "입력→조치"를 한 흐름으로 꿴 정형이 없었음. 문제 정의(§3 학술 표기)도 산문이라 비용함수(수식)와 비대칭. B(기호 정의)→A(알고리즘) 순으로 형식화.
- **정형화 중 발견한 불일치(핵심)**: §2-B 변수표가 p를 "신뢰도 = 1 − 정규화 분산"으로 정의했으나, 같은 절의 `E[비용|보류] = p·L`은 p가 **위반 발생 확률**일 때만 성립한다(1−분산은 확률이 아님). 즉 p 정의가 자기 절 내 수식과 모순.
- **해소**: 앙상블 출력을 두 기호로 분리 — 위험 확률 `p̄_v`(멤버 평균, P(위반) 점추정)와 불확실성 `u_v`(멤버 분산). 의사결정에는 불확실성 할인값 `p_eff = max(0, p̄_v − κ√u_v)`를 사용(비용식의 p ≔ p_eff). 효과: (1) 수식-정의 모순 제거, (2) "불확실성↑ → p_eff↓ → 보수적"이라는 Safety Guard가 비용함수 하나에서 유도됨(G1의 '구간을 손으로 긋지 않고 유도' 철학 강화), (3) κ=0이면 순수 기대비용으로 환원돼 하위호환. §4-2의 두 축 분리(p̄→ECE / u→Drop Rate)와도 정합.
- **A(알고리즘)**: Tier2 선제 루프(앙상블 추론→집계→p_eff→비용함수 argmin→escalate+lease) + Tier1 반사 루프 + OR/escalate-only/lease 병합을 단일 의사코드로. 심사의 "실제로 어떻게 동작하냐"에 대한 단일 답.
- **반영**: [docs/proposal.md](../docs/proposal.md) §2-0(문제정의) 신설, §2-B(변수표 정정+p_eff+Safety Guard), §2-E(알고리즘) 신설. **설계 변경이 아니라 기존 결정의 형식화 + 표기 버그 정정**(G1 골격·조치 5종·2계층 모두 불변).

### G5. 조치 실행 리드타임(ℓₐ)의 비용함수 반영 — [이관] 실험 단계
- **이슈**: G1의 비용식에서 `Dₐ`(disruption)·`Rₐ`(가역성)·`mₐ`(완화효과)는 모두 조치의 *결과*를 다루며, 조치가 실제로 완료되기까지 걸리는 **실행 리드타임**이 들어 있지 않다. §2-B 표의 "대상 전파속도" 열은 장애 쪽 속도이지 조치 쪽 속도가 아니다. 리드타임이 긴 조치(K8s Scale-up: 인스턴스 기동·워밍업)는 `θₐ`를 넘긴 시점에 발동해도 완료 시점에는 이미 늦을 수 있다.
- **검토 방향**: 신뢰도 티어 표를 손으로 다시 긋는 방식은 채택하지 않는다(G1의 "구간을 손으로 긋지 않고 유도" 철학에 역행). 대신 조치별 리드타임 `ℓₐ`를 예측 지평 `Δ`와 비교하는 제약(`ℓₐ < Δ`)으로 넣는다 — §4-2가 이미 "Δ의 하한 = 폐루프 응답시간"이라 적고 있으므로, 이를 **조치별로 분해**하는 자연스러운 확장이 된다.
- **결론**: `ℓₐ`는 조치별 실측 없이 확정할 수 없으므로 **실험 설계로 이관**(G3와 동일 논리 — 실측 없이 미리 확정하면 근거가 약한 값이 된다). 프로포절 심사 필수 항목은 아니다. [docs/proposal.md](../docs/proposal.md) §2-B에 미반영 항목으로 명시.
- **✅ 원문 확인 완료 (2026-09-06)**: GRAF ToN'24 원문 §Ⅱ에서 직접 확인했다. 인용된 수치가 **정확하다.**
  > *"**Cascading effect.** Figure 1 shows the time it takes to create instances. Across microservices, it takes **5.5 seconds on average to create a single instance**. Under circumstances where multiple instances are created at once, the creation time increases even more. Furthermore, in production settings, operators set an **interval (e.g., 15 seconds)** of how often the autoscaler makes scaling decisions to prevent the number of instances from being fluctuated. This instance creation time and control interval makes the autoscaler slow at perceiving changes in the microservices of an application."*
  - **인용 시 함께 밝힐 측정 조건(각주 2)**: *"We create instances of microservices in [28] on a single worker node and ignore the network delay to download the container images."* — 단일 워커 노드, 이미지 다운로드 네트워크 지연 제외. 즉 **하한값**이며 실제 환경에서는 더 길다.
  - GRAF는 이 절의 제목을 직접 **"Cascading effect"**로 달았다. 본 연구가 같은 용어로 문제를 지칭하는 것이 원문 용법과 일치한다.
  - **사용 가능**: 본문 인용 가능하다. [docs/proposal.md](../docs/proposal.md) §1 다섯 번째 한계 2번에 반영.
- **LLM 확장 반영(B7)**: `ℓₐ` 대상에 LLM 조치(추론 용량 파라미터 증대, 모델 로드)를 포함한다. 로컬 환경에서 실측 가능한 리드타임은 **모델 로드 시간**이며, 실증 방법 선택은 G7에서 다룬다.

### G6. [오픈] LLM 노드가 1개뿐인 구조적 한계
- **문제**: E8에서 제로 패딩을 기각한 근거가 "단일 노드 분량의 신호로 전용 차원을 학습시키는 것은 비현실적"이었다. 그런데 **노드 타입 임베딩도 같은 문제를 일부 겪는다** — `type=llm` 임베딩의 학습 신호가 노드 1개에서만 온다. "임베딩은 되고 전용 차원은 안 되는 이유가 무엇인가"라는 반문이 가능하다.
- **부분적 반론**: 임베딩은 차원이 작고(4~8) 시간축으로 다수의 샘플이 쌓이므로 전용 피처 차원보다 유리하다. 다만 완전한 답은 아니다.
- **검토할 대안**: LLM 노드를 2개로 확장(예: assistantservice + 임베딩/요약 전용 서비스). 타입 임베딩 학습 신호가 늘고 "이질적 노드가 서로 다른 위치에서 각각 전파를 일으킨다"는 그림도 강해지나 구현 부담과 일정이 추가된다.
- **상태**: 오픈. **1차는 1개로 진행하고, 학습 결과에서 타입 임베딩이 유의미하게 학습되지 않으면 2개로 확장**하는 단계적 접근.

### G7. [오픈] 추론 자원 리드타임 논거의 실증 방법
- **문제**: §1의 다섯 번째 한계 2번("추론 인스턴스 기동 리드타임이 길다")과 G5의 `ℓₐ` 논의가 이 수치에 걸려 있는데, 단일 로컬 GPU 환경에서는 클라우드 GPU 인스턴스 프로비저닝 시간을 실측할 수 없다.
- **선택지**: (a) 문헌값 인용 + 주장 수위를 "설계상 고려"로 하향, (b) 인위적 기동 지연을 주입해 모델링, (c) **모델 로드 시간 실측** — 가중치를 디스크에서 VRAM으로 올리는 데 걸리는 시간(수 초)은 컨테이너 재기동 관점의 리드타임으로 방어 가능하며, 문헌값 인용보다 낫다.
- **상태**: 오픈. **(c)를 우선 검토.** S2 시나리오 설계 전 결정 필요.

## H. 외부 피드백 검토 (2026-08, [docs/feedback/0802_optimization.md](../docs/feedback/0802_optimization.md))

선행연구 4편 기반으로 받은 외부 피드백 5건을 원문·자체 설계와 대조해 하나씩 검토했다. 수치는 선행연구 기반 팩트로 전제하되, attribution·타깃·프레이밍은 우리 설계에 맞게 교정해 조건부로 전부 반영했다. **핵심 원칙: 피드백을 100% 수용하지 않고, 우리 확정 설계(F1/G1/G2/GT)와 충돌·자해 지점을 교정한 뒤 채택.**

### H1. 앙상블 N=5 추론 오버헤드 — [채택, 프레임 교정]
- **피드백**: N=5가 골든타임 안에 끝나는지 증명하라(FIRM 1.2ms, AGQ 0.4s, GRAF 6.7s 인용) + 병렬추론 + TensorRT/ONNX.
- **교정**: "골든타임 sub-100ms 증명" 프레임은 G2(2계층 제어)와 층위가 안 맞음 — GNN은 골든타임 경로에 없고(Tier 1이 담당) Tier 2 선제 층이다. 따라서 프레임을 "GNN 결정지연 < GRAF 6.7초 기준선, N초 주기 안에 충분"으로 재해석해 흡수.
- **팩트 확인**: GRAF 원문(ToN'24 PDF) 직접 확인 — "gradient descent algorithm's 90%-tile latency to reach the target tolerance threshold takes about **6.7 seconds**". 즉 6.7초 = 자원할당 최적화 solver 수렴 시간이지 GNN 추론 시간이 아님(피드백 프레이밍 교정의 근거). 병렬추론은 채택, TensorRT/ONNX는 후속 옵션 각주로만.
- **반영**: [docs/proposal.md](../docs/proposal.md) 우려 7 신설.

### H2. Read Redirection 비침습 구현 — [채택(a), 타깃·메커니즘 둘 다 교정]
- **피드백**: ProductCatalog의 읽기 부하를 read-replica로, Istio VirtualService/DestinationRule 동적 변경으로 분산.
- **팩트 확인**: Online Boutique 원문 확인 — `productcatalogservice`는 **DB 없이 로컬 JSON**을 읽어 read-replica 개념이 성립하지 않음(→ 이 타깃이면 단순 스케일아웃과 구분 불가, 조치 이질성 붕괴). `cartservice`는 **Redis**를 backing store로 사용.
- **교정**: 타깃 ProductCatalog→**cartservice/Redis**, 메커니즘 VS/DR→**Envoy Redis proxy `read_policy`(EnvoyFilter 주입)**. 이 교정으로 (1) 진짜 read/write 분리 성립, (2) primary에 커넥션 안 쌓고 상태성 병목 완화 = **D2(커넥션풀/Thundering Herd) 차별점을 조치 레벨에서 실증**. Brownout(기능 생략)·Shedding(요청 거부)과 구분: 기능 유지+일관성 일시 약화(stale read).
- **주의**: Envoy `read_policy` read/write 분리 지원은 실증 착수 전 재확인 대상. Read Redirection은 5종 중 OB 실증이 가장 애매했던 조치였으나, 타깃 교정으로 오히려 D2 실증 조치로 승격.
- **반영**: [docs/proposal.md](../docs/proposal.md) §2-C·§2-B·§4-5.

### H3. 신뢰도 지표(ECE) + 오탐/Drop Rate + Safety Guard — [채택, 우리가 원래 필요했던 것]
- **피드백**: ECE로 신뢰도 타당성 입증 + 불필요한 Shedding으로 인한 정상요청 Drop Rate 비교 + 분산 임계 시 극단조치 유보(Safety Guard).
- **교정**: 피드백이 "분산 기반 신뢰도"로 뭉뚱그린 것을 **두 축으로 분리** — (1) 실패확률 p → ECE로 보정 검증(비용함수 입력 정당화), (2) 분산-신뢰도 → Drop Rate로 운영 검증(핵심 기여 정량화). Safety Guard는 신규가 아니라 기존 "저신뢰=보류"(비용함수 §2-B)에 이름 부여.
- **평가**: §4-4에 ECE도 Drop Rate도 없던 빈칸을 채움 → 피드백 중 순이득이 가장 큼. ECE는 클래스 불균형(§4-2)으로 표본이 얇아질 수 있어 reliability diagram 병기.
- **반영**: [docs/proposal.md](../docs/proposal.md) §4-4·§4-2·§2-B(Safety Guard 명명).

### H4. 정적 GAT(위상) 타당성 — [채택(A), FIRM attribution 교정]
- **피드백**: 논리적 위상 안정성(GRAF·FIRM 증명) + 노드 feature에 상태 주입(AGQ식) + 대규모 변경 시 FIRM 전이학습.
- **팩트 확인**: FIRM 전이학습 사용 여부 확인(D14 전례로 재검증) — FIRM은 실제로 전이학습 사용(마이크로서비스별 RL 에이전트를 이전 경험에서 전이, from-scratch보다 빠른 수렴). 단 **FIRM은 GNN이 아님(SVM+RL)**.
- **교정**: 위상 안정성은 "GRAF·FIRM 증명"으로 과잉 귀속하지 않고 MSA 일반 성질로 서술. 전이학습은 "FIRM이 GNN에 했다"가 아니라 **선례로만 인용**하고 개념을 GAT fine-tuning에 적용(attribution 정확히 — D14 재발 방지). 이 우려는 우려 3(시간축 논쟁)과 다른 공간/위상 논쟁이라 별도 항목.
- **반영**: [docs/proposal.md](../docs/proposal.md) 우려 8 신설 + FIRM 참고문헌 각주.

### H5. TA-GAT(시계열 통계 feature) — [채택, 브랜딩·자해 지점 교정]
- **피드백**: 무거운 STGNN 대신 노드 feature에 슬라이딩 윈도우 통계량 주입([현재 부하, 최근 평균, slope, std, 직전 SLO 위반 여부]).
- **평가**: 우리가 이미 열어둔 "입력 윈도우 확대"(E4)의 구체적 방법. 채택.
- **교정 2건**: (1) **"TA-GAT" 명명은 서술 편의 라벨로만 유지**, 신규 모델·핵심 기여로 내세우지 않음(사용자 요청: 시계열 포함 사실을 드러내되 과대포장 회피). (2) **"self 직전 SLO 위반 여부" feature는 제외** — 위상 없이도 아는 자기상관 신호라 "이미 위반→계속 위반" 지름길로 위상 학습을 우회, LSTM 대비 우위 근거를 자해. feature 윈도우는 라벨창 [t,t+Δ]과 겹치지 않게 t 이전으로만(누수 방지).
- **부수 이득**: GAT에 시계열 정보를 주면 GAT-vs-LSTM 비교의 변수가 위상 하나로 정제됨(단 LSTM이 보는 시퀀스를 초과하지 않게 통제). 스냅샷 전용 vs 시계열 보강 GAT를 ablation으로 → 실증 기여 추가.
- **반영**: [docs/proposal.md](../docs/proposal.md) §2-A·§4-2·§4-3(ablation 6번)·우려 3.

### H6. 통합 검토 결론
- 5건 모두 기존 확정 설계(F1/G1/G2/GT)와 **충돌 없음**. H2·H5는 오히려 핵심 차별점(D2·위상 우위) 강화, H3·H4는 비워둔 자리(신뢰도 검증·위상 변경 방어) 보완, H1만 프레임 충돌을 2계층으로 흡수.
- **필수 통합 조건 4가지(문서에 명시)**: ① D2 시나리오를 Read Redirection 타깃(cartservice→Redis)과 동일 자원에 정렬(§4-5), ② Read Redirection vs Brownout 이질성 명시(§2-C), ③ self-SLO feature 제외 + 라벨창 경계(§4-2), ④ ECE 클래스 불균형 주의(§4-4).
- **프로젝트 리스크(이론 아님)**: H2(Redis replica+EnvoyFilter)·H5(시계열 파이프라인+ablation)·H3(ECE+drop-rate)이 실험 매트릭스를 키움. 심사엔 설계로 제시하고 실증은 ②③ 단계 예산 보고 취사선택([timeline.md](timeline.md) 컷 우선순위).
- **실증 착수 전 재확인 2건**: Envoy `redis_proxy read_policy`의 read/write 분리 지원(H2), (참고) FIRM 1.2ms·AGQ 0.4s 지연 수치는 방어 시 인용 전 원문 재확인 권장.

## I. 산출물 위치 설정 (Positioning)

### I1. 도메인 온톨로지(ontology_temp) — 보조 도구, 연구 기여 아님 [결정]
- **문제**: 연구 도메인을 온톨로지(`ontology_temp/`, OWL/Turtle + classes/properties/individuals)로 정형화한 뒤, 이를 논문/발표에서 어떻게 위치시킬지 결정 필요. "온톨로지를 구성해 연구를 수행했다"는 프레이밍이 타당한가.
- **분석**:
  1. **자기참조성**: 이 온톨로지는 도메인을 독립적으로 형식화한 것이 아니라 **본 proposal에서 추출해 proposal을 다시 표현**한 것이다. 온톨로지가 연구를 이끈 게 아니라 이미 끝난 설계 결정을 사후 정리한 것이므로, "온톨로지로 무엇을 발견/도출했다"는 성립하지 않는다.
  2. **기여로 내세울 때의 방어 부담**: "아키텍처 다이어그램이 못 하는 무엇을 하는가 / 추론(reasoning)을 돌렸는가 / 재사용·외부검증이 있는가"에 현재 강한 답이 없다. Method/Contribution에 배치하면 스코프 부풀리기로 읽히고, 3축 공백→신뢰도 구간별 Policy Engine이라는 핵심 서사를 흐린다. 특수대학원 ML/시스템 심사에서 온톨로지/시맨틱웹은 다른 하위분야라 마찰만 늘어난다.
  3. **정직성**: AI로 proposal에서 단기간에 생성한 산출물을 "온톨로지를 구축하며 연구했다"로 서술하면 신뢰도 리스크.
- **결론**: **보조 도구(설계 정합성 관리·개념 정형화·발표 시각화)로만 위치시킨다. 연구 기여로 내세우지 않는다.**
  - **배치**: 본문 Method/Contribution ❌ → **부록** 또는 **각주 한 줄** + **발표 보조 슬라이드 1장**(선행연구 3축 포지셔닝 시각화).
  - **서술 상한**: "설계 과정에서 도출된 개념·조치·비교축을 도메인 온톨로지(OWL)로 정형화해 용어·정의 일관성을 관리하고 설계 공간을 명시적으로 표현했다. **온톨로지는 연구 기여가 아니라 설계 정합성 관리를 위한 보조 표현물이다.**" (마지막 문장으로 "왜 여기 있냐" 질문을 선제 차단 → rigor로 읽히게)
  - **금지 프레이밍**: "온톨로지 기반 방법론 제안" / "온톨로지를 통해 ~ 도출" 류.

가용 시간 실측이 기존 계획과 6~9배 어긋나면서 수행한 재설계의 결정 기록이다. 전체 경위·대안 검토·미채택 안은 [0923_scope_redesign_proposal.md](../docs/feedback/0923_scope_redesign_proposal.md).

### J1. 발단 — 시간 예산 실측

- **보조 증거**: 커밋 33개가 전부 `docs:`/`chore:`이고 **코드 커밋이 0개**였다(2026-07-19 ~ 09-07). timeline이 *"몇 시간, 로컬 CPU, K8s 불필요"* 로 명시한 게이트 ① 스모크 테스트조차 미착수였다.

### J2. GNN 강등 — 제거가 아니라 검증 대상화

- **문제**: GAT를 주력 예측기로 두면 (a) 14~20노드 규모에서 정당화가 어렵고, (b) GAT가 baseline을 이기지 못하면 논문 전체가 무너지는 **단일 실패점**이 된다.
- **검토**: 완전 제거(안 G)를 검토했으나 *"관계를 학습한다"* 는 축이 주장 없이 사라진다. 반면 **B5의 관찰**(GRAF·FIRM·AGQ 모두 작은 그래프를 사용)을 뒤집으면 연구 질문이 된다.
- **결론**: GAT를 **주장의 근거에서 측정 대상으로 강등**하고, 위상 정보의 기여도를 3단계로 분리 측정한다.

  | 단계 | 예측기 | 측정되는 것 |
  |---|---|---|
  | ① | 규칙/임계값 (위상 없음) | — |
  | ② | **GBM + 이웃 집계 feature** (주력) | ①→② = **위상 정보 자체의 기여** |
  | ③ | GAT (위상 학습) | ②→③ = **위상 표현 학습의 기여** |

- **부수 효과**: 이기든 지든 결과이므로 단일 실패점이 사라진다. GPU 환경(E1 Blackwell sm_120) 의존도 제거된다 — 14~20노드 GAT는 **CPU로 충분**하다.
- **절감**: 약 90h (GPU 환경 15h + 앙상블 축소 30h + 타입 임베딩·확장성 검증 15h + 동적 그래프 처리 20h + PyG CPU 빌드 10h). **그래프 구성 파이프라인은 절감 대상이 아니다** — ②의 이웃 집계에도 필요한 공통 비용이며, 이것이 GAT 복원 비용(+30h)이 낮은 이유다.
- **연쇄 효과**: 호출관계 그래프의 **실시간** 추출이 불필요해져(정적 스냅샷으로 충분) **Istio의 주 용도가 소멸**한다. 조치(CB·Bulkhead)는 Resilience4j로 앱 레이어에서 수행한다.
- **주장 수위 한정**: [Are GNNs Actually Effective for Multimodal Fault Diagnosis in Microservice Systems?](https://arxiv.org/abs/2501.02766)가 위상 비의존 baseline(DiagMLP)으로 GNN과 동등한 성능을 보고했다. 따라서 *"선행연구가 하지 않은 분리"* 라고 주장하지 않는다. 다만 해당 연구는 ①vs③ 2단 비교이며 중간 단(②)이 없고, 대상이 **사후 진단**인 반면 본 연구는 **선제 예측**이다. 역으로 이 논문은 **GNN 강등 결정을 방어하는 인용**이 된다.

### J3. 기여 서술 — "나열"에서 "결합"으로

- **문제**: 선제 대응과 신뢰도 기반 조치 선택은 **각각 선점되어 있다.** 선제 대응은 GRAF·DeepScaler·AGQ·LTFP가, 조치 선택은 Safe Remediation(J6)이 다룬다. 둘을 나열하면 *"둘 다 이미 있는데 합친 것"* 이라는 반격을 받는다.
- **분석**: 두 요소를 결합할 때 **사후 복구에는 없는 제약**이 발생한다. *(아래 세 항목 중 첫 번째는 **J15 결함 3에서 독립 제약이 아닌 것으로 정정**되어 (a)의 설명으로 내려갔다. 현재 유효한 것은 **두 제약**이다.)*

  | | 사후 복구 | 선제 대응 |
  |---|---|---|
  | 불확실성 | 진단 후 — RCA가 증거 확보 | **예측 — 아직 발생하지 않음** |
  | 오탐 비용 | 없음 (장애가 실재) | **존재** (H5) |
  | 조치 리드타임 제약 | 없음 | **`ℓₐ < L_pred`** (H6) |

- **결론**: 기여를 *"이 제약 하에서 조치별 임계값 `θₐ`를 유도하는 Policy Engine"* 으로 서술하고, **(b)·(c)를 실측**한다. 이 서술에서 선제 대응은 *"이미 있는 것"* 이 아니라 **"문제를 발생시키는 조건"** 의 자리를 차지한다.
- **성립 조건**: 산문으로 *"선제는 다르다"* 고만 쓰면 논거가 서지 않는다. H5·H6 측정이 **컷 불가 항목**인 이유다.

### J4. 가설 구조 재편 — 증명 1개, 측정 4개

- **문제**: 종전은 3축(위상 인지 예측 / 이질적 조치 / 신뢰도 구간별 대응)을 **동시에 증명**해야 했다.
- **결론**:

  | | 가설 | 위상 변화 |
  |---|---|---|
  | H1 | 위상 정보의 기여 / 표현 학습의 우월성 | 주장 → **측정 질문** (J2) |
  | H2 | 신뢰도 차등이 무차별 실행보다 낫다 | 3축 중 1 → **유일한 증명 대상** |
  | H3 | 이질적 조치가 프로비저닝 단일 축보다 낫다 | 유지 (5종 → 4종) |
  | H4 | 증설이 역효과인 병목(S1)과 불가능한 병목(S2)이 실재 | 부차 논거 → **핵심 주장의 절반** |
  | **H5** | 증상 동형 구간에서 오선택이 **무조치보다 나쁘다** | **신설** — H2의 실증적 근거 |
  | **H6** | `ℓₐ < L_pred`일 때만 선제 조치가 성립 | **신설** — 선제 vs 사후 구분의 근거 |

- **논증 구조**: 종전은 `H1 ∧ H2 ∧ H3`를 동시 증명하는 구조라 H1 실패 시 전체가 붕괴했다. 신규는 **H5를 실측 → 그 귀결로 H2가 필연**이 되는 구조다. *"틀린 조치가 무조치보다 나쁘다"* 를 먼저 측정하면 *"확신이 없으면 보류한다"* 가 임의의 설계가 아니라 데이터에서 유도된 결론이 된다 — **전제가 결론의 자리로 내려온다.**

### J5. LLM 노드 — 역할 승격, 구축 방식 경량화

- **문제**: B7에서 LLM 노드를 *"이질적 워크로드 예시"* 로 채택했으나, vLLM + Blackwell(sm_120) 환경 구축에 3~4주(120~160h)가 잡혀 있어 **단일 항목으로 가장 비쌌다.**
- **재발견**: LLM 노드의 진짜 가치는 이질성이 아니라 **"Scale-out이 물리적으로 불가능한 노드"** 라는 점이다. GPU가 단일하면 레플리카를 늘릴 수 없으므로 *"자원을 증설하라"* 는 처방이 원천 차단된다.

  | 병목 | 오토스케일링의 운명 | 비용함수 표현 |
  |---|---|---|
  | S1 커넥션풀 고갈 | **역효과** | `m_scale-out < 0` → 분모 음수 → 자동 배제 |
  | S2 LLM 포화 | **불가능** | `m_scale-out = 0` → `θ → ∞` → 원천 배제 |

- **결론**: 역할을 승격하고 구축 방식을 바꾼다 — **vLLM 2티어 캐스케이드 → Ollama + Qwen2.5 3B(4bit) 단일 모델.**
  - 2티어 캐스케이드는 Degraded-path Redirection(모델 다운그레이드)을 위한 구성이었으나 **해당 조치가 4종에서 제외**되면서 폴백 모델의 존재 이유가 사라졌다(J8).
  - 본 연구가 LLM 노드에서 관측하는 것은 응답 품질이 아니라 **자원 특성**(긴 지연·낮은 동시성 한계·큐 적체·품질-지연 트레이드오프)이므로 Ollama로 충분하다.
  - `max_tokens` 축소가 실제로 지연을 줄이므로 **Brownout이 실측으로 성립**한다.
  - **레플리카 1 고정은 제약이 아니라 설계 요구사항**이다.
- **절감**: 120~160h → **10h.** 재설계 전체에서 **단일 최대 절감 항목**이며, GNN 강등(90h)보다 크다.
- **소멸**: E1(vLLM sm_120 빌드 실패)·E2(양자화 커널 호환)·G7(추론 자원 리드타임 실증 방법)이 함께 해소된다.

### J6. Safe Remediation 원문 확인 — D14·D15에 이은 세 번째 성과

- **문제**: 가설 재배치 후 문헌을 재검색한 결과 [Safe Remediation as Risk-Constrained Intervention Decision in Microservice Systems](https://arxiv.org/abs/2607.20005) (arXiv:2607.20005, 2026-07)가 발견되었다. 위험 3축 중 2축(reversibility, epistemic uncertainty)이 본 연구와 일치하고, **동기 문장이 곧 H5**였다 — *"the cost of an incorrect repair often exceeds the cost of no action at all."*
- **원문 확인 결과 (abstract + HTML v1 본문 대조)**:

  | 확인 항목 | 결과 |
  |---|---|
  | **조치 공간** | `𝒜 = 𝒜_exec ∪ {escalate, wait, no-op}`, `𝒜_exec`는 **런북 도출 인프라 복구 조치 12종**(`restart_stateful`, `drain_connections` 등, 장애 유형당 4~6종). **본 연구의 트래픽·품질 제어 조치와 성격이 다르며, Brownout은 런북 집합에 부재** |
  | **개입 시점** | **명확히 사후** — 상태가 *"the diagnosed root cause and confidence (from an upstream RCA module)"* 를 집계하며, 장애 주입 후 90초 창 안의 **이미 발생 중인** incident가 대상 |
  | **임계값 유도** | `π(s) = arg max_a Q(s,a) s.t. r(s,a) ⪯ 𝝉(s)`, `r = [b, 1−ρ, u]ᵀ`. **`𝝉(s)`는 상태 의존이나 조치 간 균일**(action-agnostic). 조치 속성은 **피연산자**이지 임계값을 유도하지 않는다 |
  | **완화효과 축** | **없음** — `b`·`ρ`·`u` 3축뿐. *"이 조치가 이 병목에 효과적인가"* 는 `Q`에 암묵적일 뿐 임계 유도에 미사용 |
  | 불확실성 산출 | `u(s,a) = (1/M)Σ‖f_m − f̄‖₂`, **M=5 부트스트랩 앙상블** — 본 연구 원안과 방식·크기가 동일 |
  | Baseline | Rule-Runbook · LLM-Remed · BC · CQL · CPO · CMDP-vanilla + ablation 3종. 벤치마크는 Train Ticket + Chaos Mesh + RCAEval |

- **🔴 필수 수정 — "신뢰도 축 공백" 주장 폐기**: [proposal.md](../docs/proposal.md) §3의 결론 *"신뢰도 구간별 대응은 장애 예측·자원 관리 도메인의 선행연구에서 비어 있는 자리"* 는 **무효화되었다.** D15가 *"다른 도메인에는 선례가 있다"* 로 한정한 주장을 **"같은 도메인에도 선례가 있다"로 한 번 더 좁힌다.**
- **재정의된 구분선 3가지** (D15의 2가지를 대체):
  1. **선제 vs 사후** (최강 논거) — 오탐 비용·조치 리드타임 제약이 사후 구조에는 정의상 부재하다
  2. **임계값의 유도 구조** — 조치 속성이 피연산자인가 임계값을 유도하는가. **완화효과 `mₐ` 축의 유무**가 실질 차이이며, D15의 *"장애 유형이 바뀌면 같은 신뢰도에서도 선택이 달라진다"* 논거가 Safe Remediation에 대해서도 그대로 성립한다
  3. **조치 공간의 성격** — 런북형 인프라 복구 vs 트래픽·품질 제어(Brownout 포함), 그리고 증설 불가 노드의 존재
- **부수 효과**: Safe Remediation이 M=5 앙상블을 쓰므로 **앙상블 기반 불확실성 산출은 같은 도메인에 선례가 확립**된 셈이다. 우려 4의 방어 부담이 줄어든다. 또한 baseline에 **LLM-Remed가 포함**되어 있어 LLM 진단기 축을 뺀 결정(J9)이 적절했음을 뒷받침한다.
- **교훈**: D14(FIRM 브라운아웃 오기재)·D15(CP-Router 논리 역전)에 이은 **세 번째 원문 확인 성과**다. 확인 없이 심사에 갔다면 §3의 핵심 결론이 반박당했을 항목이며, **원문 우선 원칙**을 재확인시킨다.

### J7. 실험 환경 — K3s → 표준 K8s, Istio·Chaos Mesh 제거

- **K8s 배포판**: K3s → **kubeadm(폴백 minikube)**. baseline이 HPA인 이상 그 HPA가 현장에서 쓰이는 것과 같은 컨트롤 플레인 구성 위에서 동작해야 하며, 실무 전이 측면에서도 표준 배포판이 직접적이다. **실작업 12h 내 미기동 시 minikube 전환**(A3 정정, E4).
- **Istio 제거**: J2의 연쇄 효과로 호출관계 실시간 추출이 불필요해졌고, 조치는 Resilience4j로 앱 레이어에서 수행한다. 사이드카 메모리(서비스당 ~100MB)와 설정 복잡도가 통째로 빠진다. **절감 40~60h.**
- **Chaos Mesh 제거**: 앱 레벨 장애 주입(Spring 필터 — 지연 주입, HikariCP 풀 축소, 에러율 주입)으로 대체한다. **통제력이 더 높다**(정확한 지점·정확한 크기). **절감 20~30h.**
- **자원 전제 해제**: [environment.md](environment.md) §1의 *"RAM 32GB·VRAM 8GB 고정 제약"* 을 해제한다. 자원은 증설·대여로 해소 가능한 탄력적 제약이며 구속 제약은 시간이다. **예외는 CPU 코어 수** — A5의 라벨 오염은 자원 부족이 아니라 측정 타당성 문제이며 증설로 직접 해소된다. **증설 우선순위는 RAM이 아니라 코어.**

### J8. 벤치마크 — 자작 Spring 구성(주) + Online Boutique(보조)

- **문제**: 이 실험은 **커넥션풀 크기·스레드풀·재시도 정책·타임아웃을 실험 변수로 조작**해야 한다. Online Boutique는 그 목적으로 설계되지 않았고(상태성 DB 병목 부재 — B6가 Spring 서비스 추가를 계획한 이유), 다국어 구성이라 계측·주입 지점이 서비스마다 달라진다.
- **핵심 분석 — "선행연구와 같은 벤치마크"의 가치 재평가**: **벤치마크를 공유해도 수치 비교는 성립하지 않는다.** 워크로드·주입 방식·메트릭 정의·하드웨어가 모두 달라 선행연구 수치를 그대로 인용할 수 없으며, baseline은 어느 쪽이든 자체 환경에서 재구현해야 한다([timeline](timeline.md)이 "GRAF**류** baseline"이라 쓴 이유). 즉 표준 벤치마크가 주는 것은 **서술적 정당성이지 비교 가능성이 아니다.** 덧붙여 이 분야에 통일된 단일 표준도 없다(FIRM=DeathStarBench, DeepScaler=별도 구성, Safe Remediation=Train Ticket).
- **결론**: 주 실험을 **자작 Spring 6~7개 구성(의존 깊이 4단)** 으로 교체하고, Online Boutique는 **외부 타당성 보조 검증**(장애 1~2종, 컷 1순위)으로 내린다. 전체를 공개해 재현성을 확보한다.
- **규모 논거의 전환**: 연쇄 장애의 성립 조건은 노드 개수가 아니라 **의존 사슬의 깊이와 피드백 루프**다. metastable failure도 2~3개 컴포넌트에서 재현된다. 노드 수를 늘리는 대신 **깊이 4단 + 재시도 경로**로 증폭 조건을 만든다.
- **B6 재정의**: Spring/Postgres 서비스는 이제 *"추가 노드"* 가 아니라 **벤치마크 그 자체**다. B6의 1순위 근거였던 Degraded-path Redirection 구현 경로 확보는 해당 조치가 제외되며 소멸했다(J9).

### J9. 조치 5종 → 4종, 시나리오 3종 재정의

- **원칙**: 조치의 **개수가 아니라 성격의 이질성**이 H3의 근거다. 네 성격(차단 / 동시성 제한 / 자원 증설 / 품질 저하)을 유지하면서 구현 비용이 큰 둘을 제외한다.

  | 변경 | 내용 |
  |---|---|
  | **추가: Bulkhead** | **S1의 정답 조치.** 풀 획득 대기가 문제이므로 입구 거절(Shedding)보다 **동시 진입 제한**이 기전상 정확하다. Resilience4j 내장이라 비용이 낮다 |
  | **제외: Traffic Shedding** | Bulkhead와 기능 중복(둘 다 유입 제어). 기전상 더 정확한 쪽을 택함 |
  | **제외: Degraded-path Redirection** | 대체 경로 **사전 구축** 필요(Postgres primary/replica). 남은 4종으로 네 성격이 커버되므로 실익이 낮다 |
  | **개명: K8s Scale-up → Scale-out** | 본 연구가 다루는 것은 수직 증설이 아니라 **레플리카 증가**다. HPA baseline과의 대응을 명확히 한다 |

- **시나리오 3종 — S1↔S3 증상 동형 쌍이 핵심**:

  | # | 시나리오 | 정답 조치 | 검증 |
  |---|---|---|---|
  | S1 | DB 커넥션풀 고갈 | **Bulkhead** | H4 전반 — 증설이 역효과 |
  | S2 | LLM 노드 포화 | **Brownout** | H4 후반 — 증설이 불가능 |
  | **S3** | **다운스트림 지연** | **Circuit Breaker** | **H5 — S1과의 증상 동형 쌍** |

- **S3를 신설한 이유**: S1 단독으로는 **오선택을 시연할 대상이 없다.** 다운스트림 지연은 커넥션풀 고갈을 2차 유발하므로(지연↑ → 풀 점유↑ → 획득 대기 → 타임아웃 → 재시도) 관측 증상이 유사한데 **정답이 상충한다** — S1에 CB를 걸면 재시도 증폭으로 악화(`mₐ < 0`), S3에 Bulkhead를 걸면 근본원인 미해소. 이 쌍이 없으면 *"신뢰도에 따라 조치를 가른다"* 의 필요성이 실증되지 않는다. **S3는 S1보다 먼저 자를 수 없다.**
- **비용**: +15h.

### J10. `ℓₐ` 승격 — 이월 항목에서 필수 측정 항목으로

- **문제**: G5는 조치 실행 리드타임 `ℓₐ`를 *"실측 없이 확정할 수 없다"* 며 실험 단계로 이월했다.
- **변경 근거**: J3의 결합 논증이 **(c) 조치 리드타임 제약**을 근거로 삼는다. 측정하지 않으면 기여가 *"선제 + Policy Engine"* 이라는 나열로 되돌아간다.
- **결론**: 필수 측정 항목으로 승격한다.

  ```
  선제 집행 가능 조건:   ℓₐ < L_pred
  ℓₐ ≥ L_pred 인 조치  →  선제 집행 대상에서 자동 배제 (사후 집행만 가능)
  ```

- **측정 방법**: 조치 트리거 시각 ↔ 효과 발현 시각의 차이. **실험 부산물로 확보되며 별도 실험이 불필요**하다(+5h).
- **기대 결과**: **Scale-out의 `ℓₐ`가 가장 클 것**으로 예상된다(파드 스케줄링 + 이미지 풀 + JVM 기동 + 워밍업). GRAF가 일반 마이크로서비스 인스턴스 생성에 평균 5.5초를 실측했다(G5, 원문 확인 완료). 확인되면 **"자원 증설은 역효과일 뿐 아니라 애초에 늦다"** 가 H4의 두 번째 논거가 된다 — 즉 `ℓₐ` 실측은 부수 작업이 아니라 **핵심 주장을 직접 지지한다.**
- **부수 효과**: 2계층 제어(§2-D)의 필요성이 같은 축에서 재설명된다. Tier 1이 담당하는 CB·Bulkhead는 `ℓₐ`가 짧아 사후 반사로도 유효하고, Tier 2 단독인 Scale-out은 `ℓₐ`가 길어 **선제가 아니면 의미가 없다.**

### J11. LLM 진단기 비교축 — 검토 후 미채택

- **검토안**: 관측 데이터를 LLM에 주고 병목을 진단시켜 ①②③과 비교하는 네 번째 축.
- **미채택 사유**:
  1. **실험 축 억제** — 원 설계의 약점 중 하나가 *"변수가 많아 개선을 특정 요인에 귀속시킬 수 없다"* 였다. GAT를 검증 대상으로 되살린 이상 예측기 축은 **3단 사다리로 고정**한다. LLM을 넣으면 사다리가 아니라 나열이 된다.
  2. **AI 축은 이미 확보** — GAT가 검증 대상으로 남고, LLM 노드는 **피험 대상**으로 존속한다.
  3. **재현성 부담** — temperature 고정·N회 반복 보고 등 방어 장치가 추가로 필요하다.
  4. J6에서 확인했듯 Safe Remediation이 이미 **LLM-Remed를 baseline으로 포함**하고 있어 신규성도 낮다.
- **절감**: 20~30h.

### J12. 자체 검수 백로그 A1·A2 해소

[0908_review_backlog.md](../docs/feedback/0908_review_backlog.md)가 "높음" 심각도로 올린 두 항목을 해소했다. **이 둘은 재설계와 무관하게 어느 방향으로 가든 답해야 하는 항목**이었다.

**A1 — 전파성 판정 규칙**: 종전에는 *"이웃의 선행 열화에 뒤따를 때"* 라는 산문 서술뿐이라 자동 역라벨링 코드를 작성할 수 없었다.

```
positive(v, t) ⟺ v 가 [t, t+Δ] 구간에 SLO 위반
                 ∧ ∃ u ∈ 1-hop 상류 : u 가 [t−W, t] 구간에 선행 열화

선행 열화   = u 의 p95 지연 또는 에러율이 정상 구간 기준선 대비 임계 초과
허용 시간창 = 상류 열화 시점 이후 30초 이내
hop 범위    = 1-hop 직접 상류
```

- **hop 범위가 feature의 2-hop과 다른 이유**: 목적이 반대다. feature는 정보를 넓게 모을수록 유리하지만, **라벨 판정은 좁고 엄격해야 한다** — 판정 범위를 넓히면 우연한 동시 열화를 전파로 오인해 라벨 전체가 오염된다.
- 임계값·`Δ`·`W`·30초는 실측 조정 대상이며 E6 이월 항목에 포함된다. **A1이 요구한 것은 규칙의 존재**였고 이로써 해소된다.

**A2 — train/val/test 분할**: 종전 문서에는 분할 설계가 **전혀 없었다**(`split`·`hold-out`·`교차검증` grep 0건). 1Hz 샘플링에서 인접 스냅샷은 거의 동일하므로 **랜덤 분할하면 test 샘플의 이웃이 train에 존재해 사실상 답을 보고 맞히게 된다.** §4-2가 feature 윈도우 ↔ 라벨 창 누수는 정확히 막아두었으나 분할 누수는 비어 있었다.

- **결론**: **주입 지점 단위 분할** — train에서 한 번도 장애를 주입하지 않은 서비스의 에피소드를 test로 사용한다. 랜덤 분할과 시점 단위 분할은 금지한다.
- **부수 효과**: *"본 적 없는 장애 지점에도 일반화된다"* 를 주장할 수 있게 되어, 누수 방지를 넘어 기여가 된다.
- **컷 불가**: 미해결 시 예측 성능 수치 전체가 무효가 된다.

#### J6 판정의 정정 — 구분선 3번

J6은 *"조치 공간 구분선 생존"* 으로 판정했으나 **abstract만 보고 내린 결론이었다.** 본문에서 Safe Remediation은 이질성을 명시적 과제로 제기한다 — *"execution actions carry variable risk and reward, escalation is reliable but costs on-call bandwidth, and wait trades delay for evidence; a single scoring function cannot capture these asymmetries."*

**다만 이질성의 축이 다르며, 재서술하면 구분선은 살아남는다.**

| | Safe Remediation | 본 연구 |
|---|---|---|
| 이질성의 축 | **개입 방식** — 실행 / 에스컬레이션 / 대기 | **기전** — 차단 / 동시성 제한 / 증설 / 품질 저하 |
| 조치 간 관계 | 위험 프로파일이 다름 | **정답이 상충함** |
| 문제의 소재 | *"the bottleneck is **not the what** but the whether and when"* (원문) | **"the what"이 문제** |

원문이 스스로 *"무엇을 할까는 문제가 아니다"* 라고 명시하며, 세 근거가 이를 뒷받침한다 — (a) `𝒜_exec` 12종 중 장애 유형당 4~6종만 적용 가능, (b) 위 인용문, (c) 위험 벡터에 **완화효과 축 부재**. **(c)는 구분선 2와 같은 뿌리다** — "what"이 문제가 아니므로 `mₐ`가 필요 없었던 것이다.

> **결론**: 구분선 3을 *"이질적 조치 공간을 다룬다"* 에서 ***"조치 간 정답이 병목 유형에 따라 상충한다"*** 로 재정의한다. 강등이 아니라 재서술이다.

#### 결론 — 기여의 재정의

여섯 가설이 모두 부분적으로 선점된 이상, *"새로운 완화 기법을 제안한다"* 는 주장은 성립하지 않는다. **남는 자리는 하나다.**

> **선행연구는 전부 "진단이 주어진 것"을 전제한다.** Safe Remediation은 상류 RCA 모듈을, R2Act는 진단 정확도 91~99%를, Retry Amplification은 조치가 하나로 고정된 상황을 전제한다.
>
> **본 연구는 진단이 원리적으로 어려운 구간을 구성한다** — S1↔S3는 증상이 동형이고 한쪽이 다른 쪽을 2차 유발하며 정답이 상충한다. **그 조건에서 조치 오선택의 비용을 통제 실험으로 분리 측정하는 것**이 비어 있다.

이것은 **경계조건 연구(boundary condition study)** 이며, *"선행연구가 전제한 조건을 풀었을 때도 그 접근이 성립하는가"* 를 묻는 정당한 장르다. 새로운 기법의 제안이 아니라 기존 접근의 **적용 한계 실측**이 본 연구의 성격이다.

#### 부수 발견 — 실험 통제 이슈 (Resilience4j aspect 순서)

Resilience4j는 데코레이터를 **고정 순서**로 적용한다 — `Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead → Method`. **CB와 Bulkhead를 동시에 켜면 CB가 먼저 평가되어 두 조치의 효과가 분리되지 않는다.**

- **대응**: 실험 조건마다 조치를 **상호 배타적으로 활성화**한다. Policy Engine도 시점당 하나를 선택하므로 설계와 정합한다([proposal.md](../docs/proposal.md) §2-C).
- **더 중요한 점**: Retry가 가장 바깥이므로 **재시도 설정을 통제하지 않으면 S1의 재시도 증폭(`m_CB < 0`)이 재현되지 않거나 과대 재현된다.** 재시도 정책(횟수·백오프·지터)을 명시 고정하고 모든 조건에서 동일하게 유지한다. **H5의 핵심 시연이 이 설정에 걸려 있다.**

### J15. 핵심 주장 검증 — 결함 4건 정정 (2026-09-24)

반영 완료 후 README의 핵심 주장 문장을 절 단위로 재검증한 결과 **결함 4건**을 발견했다. 그중 하나는 **실험 결과를 바꾸는 종류**다.

#### 🔴 결함 1 — S1의 병목 위치가 의도와 어긋나 있었다

**문제**: 종전 S1 정의는 *"HikariCP `maximumPoolSize` 축소 + 슬로우 쿼리"* 였다. 그러나 **`maximumPoolSize` 축소는 앱 측 제약**이므로, 인스턴스가 2→4개로 늘면 총 풀 용량이 20→40으로 증가해 **scale-out이 오히려 대기를 줄인다.**

| 병목 위치 | Scale-out의 효과 |
|---|---|
| 앱 측 풀이 작아서 대기 | 총 풀 용량↑ → **도움됨** |
| **DB가 커넥션·CPU 한계** | 총 커넥션 요구↑ → **역효과** |

**이 정의로는 H4 전반부(`m_scale-out < 0`)가 재현되지 않는다.** 그리고 H4가 무너지면 H5b의 가장 확실한 셀(S1 + Scale-out)도 함께 무너진다 — J13에서 *"둘이 하나에 묶여 있어 완전 실패 확률이 낮다"* 고 했으나, **묶여 있다는 것은 같이 실패할 수도 있다는 뜻**이었다.

**확인**: 원래 의도는 **애플리케이션이 HPA로 스케일아웃되면서 DB 측 커넥션이 고갈되는 것**이었다. 정의가 의도를 반영하지 못했던 것이다.

**정정 — 제약을 DB 쪽에 둔다**:

```
총 DB 커넥션 요구 = 인스턴스 수 × maximumPoolSize

부하↑ → 커넥션 점유시간↑(슬로우 쿼리) → CPU·지연 상승 → HPA 발동
      → 인스턴스↑ → 총 커넥션 요구↑ → PostgreSQL max_connections 도달
      → 연결 거부 · DB CPU 포화 → 전 인스턴스 동시 악화
```

| 설정 | 값 |
|---|---|
| PostgreSQL `max_connections` | **낮게 고정** (예: 25) |
| DB CPU | cgroup으로 제한 |
| 슬로우 쿼리 | 커넥션 점유시간 증가 → HPA 유발 |
| 앱 `maximumPoolSize` | **정상값(넉넉하게)** — 앱을 조이면 H4가 뒤집힌다 |

`maximumPoolSize`는 S1의 주입 수단이 아니라 **Bulkhead 조치가 작동하는 지점**으로 위치가 바뀐다. 구체 수치는 게이트 ②에서 캘리브레이션한다([environment.md](environment.md) §6-2-1).

#### 🔴 결함 2 — 제약 (b)의 논리가 어긋났다

**문제**: *"장애가 오지 않았을 때의 오탐 비용"* 을 **선제 고유 제약**으로 선언해놓고, 실제로 측정하는 H5는 *"증상 동형 구간에서의 오선택"* 이었다. 오탐에는 두 종류가 있다.

| | 종류 | 선제 고유인가 |
|---|---|---|
| (i) | 장애가 **안 왔는데** 조치 | ✅ 선제 고유 |
| (ii) | 장애는 왔는데 **틀린 조치** | ❌ 사후에도 존재 (Safe Remediation의 FRR) |

**정정 — H5를 둘로 분리**:

- **H5a**: 장애 미발생 구간에 조치했을 때의 순손실 → **제약 (a)를 직접 지탱. 선제 고유**
- **H5b**: 증상 동형 구간에서 오선택했을 때의 손실 → **H2의 근거.** 사후에도 존재하나 **진단이 원리적으로 불확실한 조건에서 측정한 것이 기여**

둘 다 무조치(A4) 대비로 같은 실험에서 나오므로 **추가 비용은 없다.**

#### 🟠 결함 3 — 제약 (a)는 측정되지 않으며 독립 제약도 아니다

**문제**: *"예측 불확실성이 진단 불확실성보다 크다"* 를 세 제약 중 하나로 세웠으나, 두 불확실성을 같은 척도로 비교하려면 **사후 진단 baseline을 구현해야 하는데 하지 않는다.** 더 근본적으로 **(a)는 (b)의 원인이지 독립 제약이 아니다** — 불확실성이 크니까 오탐이 생기는 것이다.

**정정**: *"세 제약"* → **"두 제약"**. 예측 불확실성은 제약 목록에서 빼고 **(a)의 설명으로 내린다.** 측정하지 않는 것을 제약으로 세우면 *"그건 어떻게 보이셨나요"* 에 답할 수 없다.

#### 🟠 결함 4 — 주장의 비교 대상이 약했다

**문제**: *"이질적 조치를 선택하는 정책이 **단일 조치 정책보다** 우월하다"* — 선택지가 많으면 최소한 같거나 나으므로 **거의 자명하다.**

진짜 비자명한 비교는 **A5(제안) vs A6(신뢰도 미사용 ablation)** 이며 실험 설계에 이미 있었다. **주장 문장이 약한 비교를 내세우고 강한 비교를 숨기고 있었다.**

**정정**: *"…**신뢰도를 무시하고 고르는 정책보다** 우월하다"*. A3(단일 조치)는 H4 실증용 **보조 비교**로 내린다.

#### 검증 통과한 부분

| 항목 | 판정 |
|---|---|
| 제약 (b) 조치 리드타임 | ✅ 타당. 단 *"사후에는 없음"* 은 과한 표현 — **"선택 제약으로 작동하지 않는다"** 가 정확하다 |
| 선점 구도 서술 | ✅ 정확. GRAF·DeepScaler·AGQ = 선제 + **단일 조치**, Safe Remediation = **사후** + 이질 조치 + 신뢰도. 빈 칸이 *선제 + 이질 조치 + 신뢰도*라는 프레이밍이 성립한다 |
| LLM 노드 증설 불가 | ✅ 타당. GPU 1장이면 기계적으로 성립 |

#### 교훈

**J6~J14는 전부 "선행연구 대비" 검증이었고, J15는 "주장 자체의 내적 정합성" 검증이다.** 결함 1은 문헌을 아무리 확인해도 나오지 않았을 항목이다 — **주장 문장을 절 단위로 쪼개 각각이 실험으로 뒷받침되는지 따로 물어야** 드러난다. 특히 *"기전이 실제로 그 방향으로 작동하는가"* 는 설계 문서를 아무리 다듬어도 검증되지 않으며, **게이트 ②의 실측이 유일한 확인 수단**이다.
