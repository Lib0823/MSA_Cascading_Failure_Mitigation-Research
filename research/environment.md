# 연구 환경 (Research Environment)

> 최종 갱신: 2026-09-24 (범위 재설계 반영 — [0923_scope_redesign_proposal.md](../docs/feedback/0923_scope_redesign_proposal.md))
> 실험을 수행할 장비 사양과, 그 사양에서 실험을 유효하게 유지하기 위한 제약·프로토콜을 정리한다. 의사결정 경위는 [challenges.md](challenges.md) A2·A3·A5.
>
> **2026-09-24 주요 변경**: (1) *"RAM 32GB·VRAM 8GB 고정 제약"* 전제를 **해제**했다 — 자원은 증설·대여로 해소 가능한 탄력적 제약이며 구속 제약은 시간이다. (2) K3s → **표준 K8s 배포판(kubeadm)**. (3) **Istio·Chaos Mesh 제거**, vLLM → **Ollama**. (4) 벤치마크가 Online Boutique에서 **자작 Spring 구성**으로 교체.

## 1. 하드웨어 사양

실험은 **전용 데스크톱**에서 로컬로 수행한다.

| 구성 | 사양 |
|---|---|
| CPU | AMD Ryzen 5 7500F — **6코어 12스레드** |
| 메인보드 | ASRock B650M-HDV/M.2 (AM5) |
| RAM | DDR5-5600 **16GB × 2 = 32GB** |
| GPU | ZOTAC RTX 5060 Ti Twin Edge OC — **8GB GDDR7**, 448GB/s, 180W |
| SSD | 1TB NVMe PCIe 4.0 |
| 파워 | 700W 브론즈 |

> **자원은 고정 제약이 아니다 (2026-09-24 변경).** 종전에는 *"RAM 32GB·VRAM 8GB를 상수로 두고 설계를 맞춘다"* 고 선언했으나, 이 전제를 해제한다. 자원은 로컬 증설 또는 클라우드 대여로 해소 가능한 **탄력적 제약**이며, 실제로 설계를 구속하는 것은 **시간**이다(주 4시간 기준 총 400~500h).
>
> **다만 CPU 코어 수는 예외다.** §3-1의 라벨 오염은 자원 부족이 아니라 **측정 타당성** 문제이며, 증설로 직접 해소된다. 증설이 필요해지면 **RAM이 아니라 코어를 우선**한다(AM5 소켓이므로 CPU 교체로 대응 가능).

**보조 장비**: 부하 생성기(Locust)는 대상 시스템과 CPU를 공유하지 않도록 **별도 노트북에서 원격 실행**한다(§3-1·§4).

**소프트웨어 구성**: Linux 네이티브 + **표준 K8s 배포판(kubeadm, 폴백 minikube) 단일 노드**. 종전의 K3s에서 변경했다 — baseline이 HPA인 이상 현장에서 쓰이는 것과 같은 컨트롤 플레인 구성 위에서 동작해야 하고, 실무 전이 측면에서도 표준 배포판이 직접적이다. Windows + WSL2 + Docker Desktop 조합은 오버헤드가 커 채택하지 않는다.

> **kubeadm 컷 기준**: 단일 노드 kubeadm은 CNI 선택·cgroup driver 정합·swap 비활성화에서 막힐 수 있다. **실작업 12h 내에 클러스터가 서지 않으면 minikube로 전환**한다. minikube도 내부적으로 kubeadm 부트스트랩을 사용하므로 컴포넌트 구성은 표준과 동일하다.

## 2. 자원 배분 계획

### 2-1. 시스템 메모리

**현 장비 기준 참고치**다. §1에 따라 자원은 구속 제약이 아니며, 부족하면 증설한다.

| 구성 | 종전 계획 | **재설계 후** |
|---|---|---|
| OS | 2GB | 2GB |
| 컨트롤 플레인 | K3s 통합 1~1.5GB | **kubeadm 2~2.5GB** (etcd 분리) |
| kubelet + CNI | 포함 | **0.3~0.5GB** |
| 대상 서비스 | Online Boutique 11개 + Istio 사이드카 + istiod 3~4GB | **자작 Spring 6~7개 (JVM) 2.5~3GB** |
| PostgreSQL | 1.5GB (Spring 포함) | 1GB |
| Prometheus | 1~2GB (14노드) | **1GB** (7노드) |
| Chaos Mesh | 0.5GB | **제거** |
| LLM 서빙 | vLLM 호스트 ×2, 3~4GB | **Ollama 1GB** |
| **합계** | 11~15GB | **약 8~9GB** |

컨트롤 플레인이 분리되며 1~1.5GB가 늘지만, **Istio(1.5~2GB)와 Online Boutique(1.5GB) 제거분이 이를 상쇄하고도 남는다.** 메모리는 쟁점이 아니다.

Prometheus 스크레이프 대상은 노드 피처 f1~f6에 필요한 지표로 제한하고 리텐션을 짧게 잡는다.

### 2-2. VRAM (LLM 서빙) — **Ollama 단일 모델로 변경**

종전 계획은 vLLM 2티어 캐스케이드(주 모델 1.5B + 폴백 0.5B, FP16, 합계 6.6GB로 여유 0.6GB)였다. **Ollama + 단일 소형 모델로 교체한다.**

| 항목 | 크기 |
|---|---|
| Qwen2.5 3B (4bit 양자화) | 약 2GB |
| KV 캐시 | 0.5~1GB |
| **합계** | **약 3GB / 8GB** |

여유가 5GB로 늘어 VRAM은 더 이상 제약이 아니다.

**변경 근거**: 2티어 캐스케이드는 Degraded-path Redirection(모델 다운그레이드)을 위한 구성이었으나, **해당 조치가 4종에서 제외**되면서 폴백 모델의 존재 이유가 사라졌다([proposal.md](../docs/proposal.md) §2-C). 본 연구가 LLM 노드에서 관측하는 것은 응답 품질이 아니라 **자원 특성**(긴 지연·낮은 동시성 한계·큐 적체·품질-지연 트레이드오프)이므로 단일 모델로 충분하다.

> KV 캐시 용량이 작은 것은 이 연구에서 불리하지 않다. 장애 시나리오 S2가 LLM 노드 포화를 주입하는 것이므로 **캐시가 작을수록 포화 유도가 쉽고 통제하기 좋다** — HikariCP `maximumPoolSize` 조이기와 같은 방식이다.

## 3. 이 사양에서 오는 제약

### 3-1. CPU 6코어 — 측정 유효성의 핵심 제약 ⚠️ **[가장 중요]**

6코어 12스레드를 아래가 함께 사용한다.

- 자작 Spring 서비스 6~7개 (JVM)
- **K8s 컨트롤 플레인** — kubeadm 구성에서 apiserver·etcd·controller-manager·scheduler가 분리 프로세스로 동작하며 **idle에도 0.3~0.5코어를 상시 점유**한다
- Prometheus 스크레이핑
- PostgreSQL
- Ollama 호스트 측 처리

> **재설계로 나아진 부분과 나빠진 부분이 함께 있다.** Envoy 사이드카 11개와 Chaos Mesh가 사라져 CPU 압력이 크게 줄었으나, K3s 통합 바이너리에서 표준 컨트롤 플레인으로 바뀌며 상시 점유분이 늘었다. 순효과는 개선이지만, 아래 완화책은 그대로 유지한다.

**왜 심각한가 — 라벨 오염**

[proposal.md](../docs/proposal.md) §4-2의 positive 정의는 *"이웃(상류) 서비스의 선행 열화에 뒤따르는 SLO 위반"*, 즉 **전파에 기인한 위반**으로 한정된다. 그런데 호스트 CPU가 포화하면 **모든 서비스의 지연이 동시에 증가**한다. 이는 전파와 시간적 패턴이 유사해 보이지만 전파가 아니며, 자동 역라벨링이 이를 positive로 잡으면 **가짜 양성이 학습 데이터에 섞인다.**

결과적으로 GNN이 "위상을 통한 전파"가 아니라 "호스트 부하"를 학습하게 되고, 이는 LSTM 대비 우위라는 핵심 주장의 근거를 흐린다. **실험이 실패로 보이지 않기 때문에 발견도 늦다** — 결과는 그럴듯하게 나온다.

**완화책 4종** (§4 실험 프로토콜로 확정)

1. **부하 생성기 분리** — Locust를 별도 노트북에서 실행해 네트워크로 부하를 주입한다. 대상 시스템과 CPU를 공유하지 않게 한다.
2. **CPU 헤드룸 캘리브레이션** — 본 실험 전에 부하를 단계적으로 올리며 호스트 CPU 사용률을 측정하고, **포화 이전 구간**으로 실험 부하 범위를 제한한다. 컨트롤 플레인 상시 점유분(0.3~0.5코어)을 헤드룸 계산에서 먼저 제한다.
3. **에피소드 유효성 기준** — 매 에피소드마다 호스트 CPU·메모리 사용률을 함께 기록하고, 임계(예: CPU 85%)를 넘긴 구간은 **라벨링에서 제외하거나 에피소드를 폐기**한다.
4. **[신규] cpuset 분리 또는 코어 증설** — 컨트롤 플레인과 Prometheus를 특정 코어에 고정해 피험 서비스와 분리한다. 그래도 헤드룸이 부족하면 **코어를 증설한다**(§1). 자원 투자가 실제로 값을 하는 유일한 지점이다.

> 3번을 실험 프로토콜에 명시하면 심사에서 *"측정 환경이 결과를 오염시키지 않았음을 어떻게 보장하나"*에 대한 직접적인 답이 된다.

### 3-2. 단일 노드 클러스터

단일 노드이므로 **노드 간 스케줄링·네트워크 지연은 재현되지 않는다.** 본 연구의 대상은 서비스 호출 그래프 상의 전파이므로 문제 설정과 충돌하지 않으나, 한계 섹션에 명시한다. (이 한계는 배포판과 무관하게 단일 노드이기 때문이다 — K3s에서 kubeadm으로 바뀌어도 동일하다.)

### 3-3. GPU 단일 — **제약이 아니라 연구 설계의 일부**

GPU가 한 장이므로 LLM 노드의 레플리카를 늘릴 수 없다. **이것을 제약으로 서술하지 않는다.**

재설계에서 LLM 노드의 역할이 *"이질적 워크로드 예시"* 에서 **"Scale-out이 물리적으로 불가능한 노드"** 로 승격되었으므로([proposal.md](../docs/proposal.md) §0·§4-6 S2), **레플리카 1 고정은 구현해야 할 설계 요구사항**이다. 비용함수에서는 `m_scale-out = 0 → θ_scale-out → ∞`로 표현되어 Scale-out이 원천 배제된다.

> 종전 문서는 *"VRAM이 부족해 레플리카 증설 대신 vLLM 용량 파라미터 조정으로 대체한다"* 고 서술했다. 재설계 후에는 **용량 파라미터 조정도 하지 않는다** — LLM 노드에서 Scale-out은 *"작게라도 할 수 있는 것"* 이 아니라 *"할 수 없는 것"* 이어야 H4의 후반부가 성립한다. 남는 레버는 Brownout(`max_tokens` 축소)이다.

## 4. 실험 프로토콜

실험을 유효하게 유지하기 위한 규칙이다.

| # | 규칙 | 근거 |
|---|---|---|
| 1 | **부하 생성기를 별도 머신으로 분리** | CPU 경합에 의한 측정 오염 방지(§3-1) |
| 2 | **호스트 CPU·메모리를 에피소드마다 기록**, 임계 초과 구간은 라벨링 제외 | 가짜 양성 차단(§3-1) |
| 3 | **학습과 실험 실행을 시간적으로 분리** | 학습 부하가 지연 측정을 오염시키지 않도록. 측정 무결성 목적이다 |
| 4 | **일반 서비스 레플리카 1개를 기본값으로** | 실험 통제 목적. 단 Scale-out 조치와 HPA baseline 실험에서는 의도적으로 증가시킨다 |
| 5 | **LLM 노드 레플리카 1개 고정 · HPA 대상 제외** | **설계 요구사항**(§3-3). S2에서 Scale-out이 불가능함을 보장한다 |
| 5-1 | **PostgreSQL `max_connections` 하향 고정 + DB CPU를 cgroup으로 제한** | **S1의 설계 요구사항.** 앱이 HPA로 스케일아웃될 때 **총 커넥션 요구(인스턴스 수 × 풀 크기)가 DB 한계를 넘도록** 만들어야 `m_scale-out < 0`이 성립한다. 앱 측 `maximumPoolSize`는 **넉넉하게** 둔다 — 앱을 조이면 scale-out이 오히려 도움이 되어 H4가 뒤집힌다([proposal.md](../docs/proposal.md) §4-5) |
| 6 | **Linux 네이티브 구성** | WSL2/Docker Desktop 오버헤드 회피(§1) |
| 7 | **[신규] 실험 실행은 무인 야간 배치로** | 주 4시간 시간 구조에서 wall-clock 시간을 사람 시간과 분리한다 |
| 8 | **[신규] 조치 실행시간 `ℓₐ` 계측** | 조치 트리거 시각 ↔ 효과 발현 시각. H6 검증에 필수([proposal.md](../docs/proposal.md) §4-4) |
