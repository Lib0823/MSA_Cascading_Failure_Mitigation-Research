## 1. 하드웨어 사양

| 구성 | 사양 |
|---|---|
| CPU | AMD Ryzen 5 7500F — **6코어 12스레드** |
| 메인보드 | ASRock B650M-HDV/M.2 (AM5) |

> **RAM 32GB·VRAM 8GB는 고정 제약으로 둔다.** 견적상 RAM이 GPU 다음으로 큰 항목이라 사후 증설 비용이 크고, VRAM은 애초에 증설이 불가능하다. 설계는 이 두 값을 상수로 두고 맞춘다.

**보조 장비**: 기존 맥북에어(16GB)는 **부하 생성기 전용**으로 분리 운용한다(§4 참조).

## 2. 해소된 기존 제약

| 기존 제약 (맥북에어 16GB) | 현재 |
|---|---|
| K8s 클러스터 + 장애주입 + 트래픽 생성 동시 구동 시 메모리 부담(A3) | **해소.** 32GB면 컨테이너 25개+ 구동에 여유가 있다 |
| GPU 부재 → LLM 로컬 서빙 불가 | **해소.** 5060 Ti로 소형 모델 2티어 로컬 서빙 가능 |
| LLM 확장 시 학습 데이터를 에뮬레이션으로 대량 수집해야 함 | **불필요해짐.** 실측 수집이 가능하므로 에뮬레이터·전이 검증 부담이 사라진다 |
| 보조 실험(Train Ticket 서브셋)에 VPS 단기 대여 필요 | **재검토 대상.** 서브셋 15~25개 서비스면 로컬 수용 가능성이 있다 |

**메모리 개산** (LLM 확장 포함 최대 구성 기준)

| 구성 | 예상 |
|---|---|
| OS + K3s | 2~3GB |
| Online Boutique 11개 + Istio 사이드카 + istiod | 3~4GB |
| Prometheus (14노드, 1Hz 수집) | 1~2GB |
| PostgreSQL + Spring(JVM) | 1.5GB |
| Chaos Mesh | 0.5GB |
| vLLM 호스트 프로세스 ×2 | 3~4GB |
| **합계** | **11~15GB** |

32GB 대비 여유가 있으나 넉넉하지는 않다. **Linux 네이티브로 구성한다** — Windows + WSL2 + Docker Desktop 조합은 4~6GB를 추가로 소모해 이 여유를 상당 부분 잠식한다.

**VRAM 개산** (LLM 확장 채택 시, 2티어 FP16, 헤드리스 기준 가용 ~7.2GB)

| 항목 | 크기 |
|---|---|
| CUDA 컨텍스트 × 2 프로세스 | 1.0GB |
| 1.5B 주 모델 (FP16) | 3.1GB |
| 0.5B 폴백 모델 (FP16) | 1.0GB |
| KV 캐시 — 주 모델 (동적 범위 확보용) | 1.2GB |
| KV 캐시 — 폴백 | 0.3GB |
| **합계** | **6.6GB** |

FP16으로 수용 가능하되 여유가 0.6GB로 얇다. 부족하면 주 모델만 Q4로 내려 약 2GB를 확보한다. 다만 **Q4를 플랜 A로 잡지 않는다** — Blackwell(sm_120)에서 양자화 커널 호환 표면이 하나 더 늘기 때문이며, FP16으로 먼저 세팅한 뒤 필요 시 내린다(§5).

> KV 캐시가 작은 것은 이 연구에서 불리하지 않다. 노드 피처 f1이 "KV 캐시 점유율"이고 장애 시나리오가 그 포화를 주입하는 것이므로, 캐시가 작을수록 포화 유도가 쉽고 통제하기 좋다 — Redis `maxclients`·HikariCP `maximumPoolSize` 조이기와 같은 방식이다.

## 3. 이 사양에서도 남는 제약

### 3-1. CPU 6코어가 새로운 병목이다 ⚠️ **[가장 중요]**

메모리 제약이 풀리면서 **병목이 CPU로 옮겨갔다.** 6코어 12스레드를 아래가 함께 사용한다.

- Online Boutique 11개 서비스 + **Envoy 사이드카 11개** (고부하에서 사이드카 CPU가 앱을 넘어설 수 있다)
- Locust 부하 생성 (동시 사용자 수에 비례해 CPU 소모)
- Chaos Mesh, Prometheus 스크레이핑
- Spring(JVM) + PostgreSQL
- vLLM 호스트 측 토크나이징·스케줄링

**왜 심각한가 — 라벨 오염**

[proposal.md](../docs/proposal.md) §4-2의 positive 정의는 *"이웃(상류) 서비스의 선행 열화에 뒤따르는 SLO 위반"*, 즉 **전파에 기인한 위반**으로 한정된다. 그런데 호스트 CPU가 포화하면 **모든 서비스의 지연이 동시에 증가**한다. 이는 전파와 시간적 패턴이 유사해 보이지만 전파가 아니며, 자동 역라벨링이 이를 positive로 잡으면 **가짜 양성이 학습 데이터에 섞인다.**

결과적으로 GNN이 "위상을 통한 전파"가 아니라 "호스트 부하"를 학습하게 되고, 이는 LSTM 대비 우위라는 핵심 주장의 근거를 흐린다.

**완화책 3종 (§4 실험 프로토콜에 반영)**

1. **부하 생성기 분리** — Locust를 맥북에어에서 실행해 네트워크로 부하를 주입한다. 대상 시스템과 CPU를 공유하지 않게 한다.
2. **CPU 헤드룸 캘리브레이션** — 본 실험 전에 부하를 단계적으로 올리며 호스트 CPU 사용률을 측정하고, **포화 이전 구간**으로 실험 부하 범위를 제한한다.
3. **에피소드 유효성 기준** — 매 에피소드마다 호스트 CPU·메모리 사용률을 함께 기록하고, 임계(예: CPU 85%)를 넘긴 구간은 **라벨링에서 제외하거나 에피소드를 폐기**한다.

> 3번은 실험 프로토콜에 명시하면 심사에서 "측정 환경이 결과를 오염시키지 않았음을 어떻게 보장하나"에 대한 직접적인 답이 된다.

### 3-2. 단일 노드 클러스터

K3s 단일 노드이므로 **노드 간 스케줄링·네트워크 지연은 재현되지 않는다.** 본 연구의 대상은 서비스 호출 그래프 상의 전파이므로 문제 설정과 충돌하지 않으나, 한계 섹션에 명시한다.

### 3-3. VRAM 8GB — LLM Scale-up 구현 범위

가중치 4.1GB를 점유한 상태에서 주 모델 레플리카를 추가할 여유가 없다. LLM 노드의 Capacity Scale-up은 **레플리카 증설이 아니라 vLLM 용량 파라미터 조정**(`max_num_seqs`, KV 캐시 블록 수)으로 구현하고, 레플리카 증설은 스코프 밖으로 명시한다.

> 이것이 논거를 약화시키지는 않는다. 이 연구에서 Scale-up은 "잘 되는 것"이 아니라 상태성 병목에서 `mₐ`가 급락해 **비용함수가 자동 배제하는 것**을 보이는 조치다(D2). 오히려 KV 캐시 포화 상태에서 `max_num_seqs`를 늘리면 시퀀스 간 캐시 경쟁으로 preemption이 늘어 지연이 악화되므로, **커넥션풀 Thundering Herd의 LLM 대응물**이 그대로 재현된다.

## 4. 실험 프로토콜 제약

이 사양에서 실험을 유효하게 유지하기 위한 규칙이다.

| # | 규칙 | 근거 |
|---|---|---|
| 1 | **부하 생성기를 맥북에어로 분리** | CPU 경합에 의한 측정 오염 방지(§3-1) |
| 2 | **호스트 CPU·메모리를 에피소드마다 기록**, 임계 초과 구간은 라벨링 제외 | 가짜 양성 차단(§3-1) |
| 3 | **학습과 실험 실행을 시간적으로 분리** | 32GB로 동시 실행은 가능하나, 학습 부하가 지연 측정을 오염시킨다. **이유가 "메모리 부족"에서 "측정 무결성"으로 바뀌었을 뿐 규칙은 유지** |
| 4 | **레플리카 1개 유지** | 자원 절약이 아니라 **실험 통제** 목적으로 재해석. 레플리카가 늘면 조치 효과의 귀속이 어려워진다 |
| 5 | **Linux 네이티브** | WSL2/Docker Desktop 오버헤드 회피(§2) |
| 6 | **디스플레이는 내장 그래픽으로 출력** | GPU VRAM 0.5~1GB 절약(§2) |
