## ⚠️ 시간 예산 — 이 문서의 전제

**종전 이 문서의 "8~11.5개월" 추정은 주당 투입 시간을 명시하지 않은 채 세워졌다.** 역산하면 주 30~40시간(사실상 전업)을 가정한 수치로 **1,000~1,800시간**에 해당한다. 실제 가용 시간과 6~9배 어긋났으며, 이것이 범위 재설계의 직접적 원인이다.

## 구현·실험 단계별 접근 (①→②→③)

리스크가 낮은 것부터 3단계로 쌓는다. 각 단계는 다음 단계의 전제를 검증하는 게이트이며, 앞 단계가 통과되기 전에 뒤 단계에 자원을 투입하지 않는다.

### ① 모델 스모크 테스트 — 코드 실현 가능성
- **목적**: 예측 계층 설계가 코드로 성립하는지 확인
- **방법**: 가짜 6~8노드 그래프 + 랜덤 feature로 ②GBM·③GAT forward pass. K8s 불필요, **CPU만 사용**
- **확인 항목**: 텐서 shape 정합 / 노드별 다중 클래스 출력 + 불확실성 / 노드 수를 바꿔도 파라미터 불변
- **비용**: 몇 시간, 로컬 CPU. **성능·정확도는 검증 대상 아님**(랜덤 데이터)
- **게이트**: 통과해야 ②의 입력 스펙(feature 차원·그래프 포맷)이 확정됨

### ①.5 S1 미니 캘리브레이션 — 핵심 주장의 부호 확인

- **목적**: `m_scale-out < 0`(H4 전반부)이 실제로 재현되는지를 **K8s 구축에 착수하기 전에** 확인한다
- **방법**: Docker Compose로 PostgreSQL 1개(`max_connections` 하향 + CPU 제한 + 슬로우 쿼리) + 단일 이미지 Spring 서비스. 부하를 건 상태에서 인스턴스 2개와 4개를 비교. 하네스는 [code/calibration/](../code/calibration/)
- **⚠️ 대조군이 필수다**: 인스턴스를 늘리면 **호스트 CPU 경합만으로도** 지연이 악화되어 H4가 재현된 것처럼 보인다([proposal.md](../docs/proposal.md) §4-1의 가짜 양성). 따라서 **DB를 조이지 않은 대조군**을 함께 돌려, 대조군에서는 2→4가 개선되고 실험군에서만 악화되는지로 효과를 DB에 귀속시킨다
- **1단계는 부하 구간 탐색이다**: 대조군이 2→4에서 개선되는 부하 수준을 먼저 찾는다. 그런 구간이 없으면 해당 머신에서는 **판정 불가**로 결론내고 실험 데스크톱으로 이월한다 — 이 경우에도 12h에서 멈춘다
- **비용**: 약 12h. K8s·HPA 불필요하며 노트북에서 가능. 여기서 만드는 서비스는 §4-1의 단일 이미지 그대로이므로 **버려지는 코드가 없다**
- **게이트**: 부호가 재현되지 않으면 S1 정의를 재설계한다. 이 답을 **K8s 구축(60h) 이전에** 얻는 것이 이 게이트의 존재 이유다

> **하네스 착수 (2026-09-27)**: [code/calibration/](../code/calibration/) — Compose 하네스 + 폐루프 부하기 + 판정 실행기. 설계에서 두 가지가 바뀌었다.
> - `--scale app=N` 대신 **app1~app4 를 명시하고 프로파일로 선택**한다. 호스트 포트가 고정되어 부하기가 인스턴스에 결정론적으로 균등 분배하며, 로드밸런서 프로세스가 호스트 CPU 를 먹지 않는다.
> - **두 군은 `max_connections` 하나만 다르다.** DB CPU 상한까지 군마다 다르게 주면 조건별 호스트 CPU 총량이 달라져 대조군이 대조군 역할을 못 한다. DB CPU 제한은 두 군에 동일하게 건다.
>
> 첫 시운전에서 부하 성형 기본값을 실측으로 고쳤다 — 슬로우 쿼리를 20,000행 해시로 잡으니 요청당 DB CPU 가 약 50ms 라 **DB CPU 가 먼저 천장**(2코어 → 약 50 rps)이 되었다. 그 상태에서는 대조군에서조차 증설이 무의미해 부호를 커넥션에 귀속시킬 수 없다. 점유시간(`pg_sleep`)을 올리고 CPU 소모를 낮추는 쪽으로 재조정했다.

## 컷 우선순위 (위에서부터 먼저 제외)

| 순위 | 항목 | 절감 | 손실 |
|---|---|---|---|
| 1 | Online Boutique 보조 검증 | 30h | 외부 타당성 방어 약화. **주 실험은 무손상** |
| 2 | 예측기 ③ GAT | 30h | ②→③ 비교 소멸. **①→② (위상 정보 기여) 측정은 보존** |
| 3 | 신규 문헌 중 🟢 등급 | 10h | 인용 두께 감소. 🔴 Safe Remediation은 **컷 불가**(확인 완료) |
| 4 | **S2 (LLM 노드 포화)** | **50~55h** | 시나리오 25h + **LLM 노드 구축 25~30h**. S2 를 자르면 LLM 노드의 존재 이유가 없어지므로 둘이 함께 빠진다. ⚠️ LLM 노드의 유일한 고유 실증이며, GNN 축이 얇아진 만큼 AI 쪽을 채우는 부분이다. 여기까지 오면 컷이 아니라 **LLM 노드 철회**를 검토할 것 |

> **최소 관측 집합 분석(H7)을 컷 목록에서 뺐다 (2026-10-13).** 종전에는 컷 3.5순위(25h)였다. 두 가지가 바뀌었다.
> - **유일하게 배포 위험 없이 적용 가능한 산출이다.** Policy Engine은 *"예측에 따라 자동으로 조치한다"* 라 현업 도입 장벽이 높지만, H7은 *"이 지표를 추가로 수집하면 S1과 S3가 구분된다"* 이므로 **수집만 늘리면 끝**이다. 1순위 목표가 실무 역량 전이인 이상 여기를 먼저 자르는 것은 목표와 역행한다.
> - **②를 주력으로 고른 근거가 H7이다.** GBM을 쓰는 이유는 성능이 아니라 feature 중요도로 최소 관측 집합을 뽑을 수 있어서인데(§2-A), H7을 자르면 *"왜 GBM인가"* 도 함께 흐려진다.
>
> 다만 **컷 불가 항목으로 올리지는 않는다.** 자른다고 §0의 핵심 주장이 무너지지는 않기 때문이다. 컷 목록에서 빼되 컷 불가에는 넣지 않는 **중간 상태**로 두고, 예산이 터지면 S2(컷 4)와 **같은 선에서** 비교한다.
>
> 예비 실측은 이미 확보했다 — 풀 획득 대기가 S1과 S3를 350배로 가른다([§4-4](../docs/proposal.md), 2026-10-05). 남은 25h는 그 구분자를 **체계적으로 찾는 절차**(feature 중요도·순차 선택)에 쓴다.

> **vLLM 채택(2026-09-27, [J16](challenges.md))으로 컷 4순위가 최대 절감 항목이 됐다.** LLM 노드 구축이 10h → 25~30h 로 오르면서, S2 를 자를 때 함께 빠지는 양이 35h → **50~55h** 가 되어 컷 1순위(Online Boutique 30h)를 넘는다. **순서는 바꾸지 않는다** — 컷 순서는 절감액이 아니라 **주장 손상도**로 정해야 하고, S2 는 *"증설이 불가능한 병목"* 이라는 H4 후반부의 유일한 실증이기 때문이다. 다만 예산이 실제로 터질 때 가장 큰 단일 레버가 여기라는 점은 기록해 둔다.

### 컷 불가 항목

자르면 연구 주장이 성립하지 않는다.

- **Policy Engine** (신뢰도 기반 조치 선택) — 유일한 증명 대상(H2)
- **K8s + HPA baseline** — *"오토스케일링만으로는 안 된다"* 의 비교 대상
- **S1 + S3 쌍** — 증상 동형 쌍이 깨지면 H5b의 근거가 사라진다. **S3는 S1보다 먼저 자를 수 없다**
- **조치 4종** — 차단/제한/증설/품질저하 중 하나라도 빠지면 이질성 논증(H3)이 무너진다
- **개입 비용(H5a·H5b)과 `ℓₐ`(H6) 측정** — 기여가 *"선제 + Policy Engine"* 이라는 나열로 되돌아간다
- **train/val/test 주입 지점 단위 분할** — 미해결 시 예측 성능 수치 전체가 무효

- GPU 클라우드는 고려하지 않는다 (vLLM + Qwen2.5 3B AWQ 는 가중치 약 2GB, 잔여 4~5GB 가 KV 캐시로 8GB 에 여유 있게 들어간다)
